# M2 · 直播间评论随机关注（编写计划）

> 前置决策（已确认）：**直播间由用户手动进入**。脚本不负责搜索直播间、不负责进直播间，
> 只做「读当前直播间评论 → 随机挑一个人 → 关注 → 回直播间」这个循环。
> 起跑前提：抖音在前台，且你已经停在目标直播间里。

---

## 1. 为什么引擎执行模型必须改

M1 的 `TaskEngine.start(context, steps: List<Step>)` 只能跑**静态序列**：
「第几步点哪里」在启动时就固定了。

M2 做不到——它要「读到什么就决定做什么」：评论里有几个名字、挑哪一个、点开后是资料卡还是主页、
有没有已经是「已关注」，全都是运行期才知道的。用静态列表表达只能靠 `if` 塞进 Step，等于把业务塞进引擎。

**改法**（M1 的 `Step` 原语全部保留，不浪费）：

```
TaskEngine.start(context, flow: Flow)
                    │
                    ├── StepFlow(steps)        ← M1 自检流程、后续线性流程复用
                    └── FollowFromLiveFlow()   ← M2 新增业务闭环
```

`Flow` 只有一个方法，`FlowContext` 负责把能力递给业务：

| FlowContext 成员 | 作用 |
|---|---|
| `actions` / `detector` / `config` / `settings` / `humanizer` | 与 M1 同源，业务层直接可用 |
| `guard()` | 查风控，命中抛 `AnomalyStopException`（引擎捕获后置 `STOPPED_ANOMALY`） |
| `settle(baseMs)` | 随机化等待，**等待结束自动再查一次风控** |
| `publish(...)` | 回写状态条 / 通知 / 悬浮窗 |
| `awaitResume()` / `stopped()` | 暂停与停止 |
| `waitForPage(...)` | 等页面（带超时、带风控轮询） |

引擎的职责收缩为：生命周期、状态发布、风控/熔断的兜底、终态判定。

## 2. 单轮链路

| # | 动作 | 失败处理 |
|---|---|---|
| 0 | 前置检查：抖音在前台；今日剩余额度 > 0 | **直接中止并说明原因**，不降级硬跑 |
| 1 | 采集评论里的昵称（见 §3） | 采集为空 → **等新评论进来**（不滑动，原因见下），连续 4 次空则中止 |
| 2 | **随机**挑一个候选 | 候选集为空同上 |
| 3 | 重新定位该昵称节点 → 在其 bounds 内**随机点**（不用控件中心） | 定位不到 → 丢弃该名字，下一轮 |
| 4 | 等「关注 / 已关注」按钮出现（≤6s，带位置过滤） | 没出现 → 关掉弹层，丢弃该名字 |
| 5 | 已存在「已关注」 → 记入已关注集合，关闭弹层，**不计数** | — |
| 6 | 点「关注」 | 点击失败 → 关闭弹层，不计数 |
| 7 | **等「已关注」真的出现**（≤3s） | 未出现 → 记 WARN，**不计数**（不允许假成功） |
| 8 | 关闭弹层（优先点关闭按钮，退化系统返回） | — |
| 9 | 计数 +1 → 写已关注集合 + 日计数 +1 → `publish(followed)` | — |
| 10 | 每 N 个休息 X 秒；否则随机间隔 `scanInterval×(1±抖动)` | — |

> **为什么候选为空时不滑动**：抖音直播间里全屏上下滑是**切换直播间**，不是滚动评论列表。
> 滑一下就可能离开你选的直播间，而直播评论本身在持续刷新——等 2.5 秒就有新名字进来。
> 原计划写的「上滑评论区重采」是个错误假设，已改掉。

## 3. 评论昵称怎么采集（三级，全部可配置）

不确定抖音直播评论的节点结构，所以**不写死任何一种**：

1. **主路径**：`targets.live_comment_nickname`（配置 `type`+`value`，初版是待校准的 id）。
   命中的节点取 `text`，没有则取 `contentDescription`，即昵称。
2. **兜底**：主路径采集为空时，用 `targets.live_comment_line`（`textContains "："`）收整行文本，
   **按 `：` / `:` 切分取前段**当昵称。
3. **过滤**：长度 1–24、非纯数字、非空白、不在黑名单（自己/主播/作者等，配置里给）、
   不在本轮已处理集合、不在持久化「已关注」集合。

采集去重后为空的三种原因分开记录日志——「没采到」和「采到了但全是已关注的」是两种故障，不能混。

## 4. 为什么不用「页面判定」等资料卡

点昵称弹出的是**半屏资料卡**，和主播主页的可访问性特征高度重合（都有 `粉丝` `获赞` `关注` `作品`），
硬做页面分类必然在两者之间反复误判，`waitForPage(USER_PROFILE)` 会随机超时。

改用**意图一致的判据**：直接等「关注」或「已关注」按钮出现。有没有关注按钮，就是这个弹层到底能不能操作、
能不能用来判断已关注状态的唯一依据。判据即意图，不引入中间层，也就不引入中间层的错误。

## 5. 反风控（继承 M1 五条，M2 补三条）

- M1 已有：随机延迟、点击偏移、多段滑动、逐字输入、**异常即停不重试**。
- M2 新增：
  1. **候选随机化**——不在评论列表里按顺序从上往下点（那是明显的机器特征），而是每次从候选集里随机取。
  2. **昵称点击前重新定位**——直播弹幕滚动快，采集时的坐标早已失效；按昵称重新查节点，
     失效就丢弃，绝不使用陈旧坐标。
  3. **每轮 guard + settle 后自动 guard**——把风控检查嵌进等待里，业务代码想漏都漏不掉。

## 6. 去重与日限额（新增持久化）

`FollowedStore`（SharedPreferences）：

| 键 | 内容 | 说明 |
|---|---|---|
| `followed_names` | `\n` 分隔的昵称集合 | 上限 3000，先进先出淘汰（老的挪出记忆） |
| `day_key` | `yyyy-MM-dd` | 跨天自动清零 |
| `day_count` | 当日已关注数 | 与 `Settings.dailyLimit` 比较 |

**限制**：去重靠昵称，遇到同名不同人会误杀。这是可访问性能拿到的唯一稳定标识（拿不到 uid），
记录在案，不假装准确。

## 7. 界面改动

- 「自动关注」页的「开始服务」→ 启动 `FollowFromLiveFlow`；启动前弹窗说明「需先手动进入直播间」。
- 状态条 / 悬浮窗显示 `已关注 x/目标`（复用 `EngineProgress.followed/target`）。
- 自检菜单保留「搜索链路自检」（`StepFlow` + `SmokeFlow`），M2 之后仍然有用。

## 8. 必须真机校准的点（M2 完成≠可用）

| 项 | 现状 | 怎么校准 |
|---|---|---|
| `live_comment_nickname` 的 id | 占位值，大概率不命中 | `uiautomator dump` 抓评论节点，填真实 id |
| `live_comment_line` 的冒号形态 | 假设是 `昵称：内容` | 同上，确认全角还是半角 |
| 昵称节点是不是独立节点 | 若整条评论是一个节点，点击会落在整行上 | dump 里看昵称有没有单独的 `text` 节点；没有就需要按坐标比例点行首 |
| 弹层关注按钮的 y 阈值 | `TOP_EXCLUDE_RATIO = 0.30` | 日志若稳定出现「没等到弹层里的关注按钮」，先调这个值 |
| 「关注」按钮文案 | `关注` / `已关注` | 个别版本是「回关」或纯图标 |

缺省配置全部带 `_unverified` 标记，第一次跑必然要在真机上调到这里能用为止。

## 9. 验收（真机）

1. 手动进入一个直播间 → 点开始 → 状态条 `已关注` 逐个递增，日志能看到「挑中谁 / 为什么跳过」。
2. 遇到已经是「已关注」的人 → 跳过且不计数（日志有记录）。
3. 关注后 3 秒内没等到「已关注」→ 记 WARN 不计数（人为把网络断开可复现）。
4. 达到目标数 / 日上限 → 停止，通知与悬浮窗自动消失。
5. 停止键 200ms 内生效；暂停期间不产生任何点击。
6. 人为让界面出现「操作过于频繁」→ 一个状态周期内 `STOPPED_ANOMALY`，且**不重试**。

## 10. 真机实测记录（抖音 40.8.0 / Android 16，2026-10-26）

首轮真机联调**推翻了编写阶段的三个假设**，均已改代码/改配置。

### 10.1 假设错在哪

| 编写假设 | 实测事实 | 后果（若不改） |
|---|---|---|
| 评论昵称是独立节点，可用某个 id 定位 | 40.8.0 的 `resource-id` 全是混淆短码，且评论是**一整行一个节点**（`昵称：正文`） | `find(TEXT, 昵称)` 永远命中不了 → 每个人都判成「已滚出屏幕」→ **一个也关注不了** |
| 点整行任意位置都能打开资料卡 | 整行宽达 800px，**正文区点击不弹资料卡** | 点偏了 → 等不到弹层 → 每轮都 UNKNOWN 跳过 |
| 用 `descContains "关闭"` 关资料卡 | 直播间右上角那颗 `关闭 按钮` 是**退出直播间** | 弹层一消失就点到它 → **被踢出直播间**，之后全在错误页面空跑 |

### 10.2 另外三个只在真机才暴露的问题

1. **评论文本以 U+200E 零宽字符开头**（`‎紫丽丽：…`）。不去掉会导致去重失效、回查节点匹配不上。
   已加 `sanitize()` 统一剔除。
2. **表情是文本化的**（`[调皮][比心]`）。昵称过滤增加「不以 `[` 开头」。
3. **点击「开始时抖音必然在后台」**。`isDouyinForeground()` 若只判一次，
   每次正常启动都会被误杀成「抖音不在前台」。已改为最多等 10 秒 + 900ms 窗口稳定。

### 11.2 这次修掉的四个问题（都会导致「看起来在跑但一个也关注不了」）

1. **`followed_button` 文案错了**。原写「已关注」，抖音 40.8 实际是 **「取消关注」**
   （对方也关注你时是「互相关注」）。不改则每轮都「点关注成功 → 校验超时 → 不计进度」，
   永远停在 0。已在配置里改为「取消关注」，代码里额外兜底「互相关注」。
2. **残留的 `text="关注"` 节点**。已关注状态下节点树里仍然留着那个「关注」TextView，
   于是 `follow_button` 依旧命中，一旦第 1 条漏判就会走到 FOLLOWABLE 分支，
   而点击坐标正好压在「取消关注」上 —— **会把已关注的人取关**。
   现在 `awaitCard` 先查「已关注证据」再查「可关注」，「已关注」有多重判据。
3. **点评论行的纵向落点**。评论行 bounds 高度随内容差异极大（纯文本 32px，带等级/多行 117px）。
   原来取 `centerY`，在高行上会落到**文字下方空白**，抖音把它当成「点空白」，
   弹出快捷操作栏（资料卡/喜欢/不喜欢/@TA/更多）而不是资料卡。改为 `y = top + min(h/2, 24)`。
   另外 `awaitCard` 增加了兜底：真弹了操作栏就点它的「资料卡」入口。
4. **采集/回查没有过滤屏幕外节点**。评论是 RecyclerView，滚出屏的行仍留在节点树里，
   bounds 已失效。后果有两个：回查时「已滚出屏幕」白跑；更糟的是命中屏幕外旧节点、
   拿旧坐标去点，**落点压在礼物按钮上打开了礼物面板**，之后整页 UNKNOWN 空转。
   已在 `Actions.find/collect` 统一加屏幕可见性过滤。

### 11.3 平台侧两个坑

1. **Android 11+ 包可见性**：Manifest 不声明 `<queries>` 时，
   `getLaunchIntentForPackage("com.ss.android.ugc.aweme")` 返回 null，
   `DouyinLauncher.isInstalled()` 恒为 false，点「开始服务」直接报「未检测到抖音」。
   已加只含抖音包名的 `<queries>`（不用 `QUERY_ALL_PACKAGES`）。
2. **抖音冷启动要 10 秒以上**（Splash → 首页 → 恢复上次的 `LivePlayActivity`）。
   前台等待原来 10 秒，正常启动也会被误杀，已放宽到 20 秒。

### 11.4 仍存在的已知限制

- **候选回查靠昵称**：采集到候选后按昵称回查节点，评论滚动太快时命中不了，
  日志表现为「已滚出屏幕，跳过」。属于可接受的空转，不影响正确性（宁可不点，不点错）。
- **同名不同人会被去重误杀**：拿不到 uid，只能按昵称去重。
- 单次会话观察到的浮层误开（礼物面板/操作栏）已由 `ensureLiveRoom` 每轮兜底，
  但它只能关一层，极端情况下仍需人工把界面拉回直播间。

### 11.5 跑通后的调用链（供后续排查对照）

```
EngineController.start → 预检 → ControlService(specialUse FGS) → 拉起抖音 → TaskEngine → 悬浮窗
FollowFromLiveFlow:
  awaitDouyinForeground(≤20s) → ensureLiveRoom → collectCandidates(冒号切分)
  → 随机挑人 → find(TEXT_CONTAINS, 昵称) → tapNickname(y=top+24)
  → awaitCard(先查取消关注/互相关注，再查关注) → tapNode(关注)
  → awaitFollowedState(≤3s，等「取消关注」出现) → back() 关资料卡 → 计数 + 去重落盘
```

## 12. 「关注后回到最新评论」（2026-10-27 真机实测后补）

### 12.1 问题

跑起来之后发现：第一个人关注得对，之后挑的人却不像是「刚说话的」，更像在补关注几分钟前就在屏上的人。
原因是这一屏评论的**存活时间很长**——实测直播间里 9 行评论同时挂在屏上，y 从 1195 一直到 2170，
覆盖好几分钟；而旧实现是对**整屏候选 random()**，所以每次都有很大概率挑到早期的评论者。

### 12.2 先搞清楚「能不能滑到最新」——不能

抖音直播间的评论列表是**自下往上堆**的（最新一条恒在最底部），本来就不需要滚。但为了确认，做了三次真机实验：

| 实验 | 结果 |
|---|---|
| 评论区内 550px 纵向滑动（y1900→1350，x=350） | ❌ **切到了下一个直播间**（主播从「毛里求斯黑猩猩」变成「迅猛龙特…」，画面变成 PK 房） |
| 评论区内 120px 短滑 | 不切房间，但评论行 y **完全没变**（顶部仍 1942）→ 列表根本不可滚 |
| 同上，反向下滑 120px | 同上，没有出现更早的评论 |

结论：**任何纵向滑动都不能用来滚评论区**。铺在全屏上的 ViewPager 会抢手势，滑多了直接换直播间；
滑少了没有位移。所以「下拉到最新」只能实现成「**等列表自己滚到最新**」。

### 12.3 现在的做法

1. **锚点 = 列表最底那一行的文案**。列表满屏时每行的 y 是固定的（旧行被顶掉、新行补在底部），
   所以「y 变大」不是有效信号，而每行文案包含评论正文，换人必然换文案。
2. 每轮（`ensureLiveRoom` 之后、采集之前）调用 `awaitNewestChanged()`：轮询到最底那行换人，
   才算「列表已经推进到比上一轮更新的评论」。超时 6s（冷清房间）则降级为「当前屏最新处」取人，
   并写一条 W 日志，不假装成功。
3. 采集时给每个候选带上行下边缘 `bottomY`，**按 y 从新到旧排序**，并过滤掉压到输入栏的行
   （> 输入栏顶 - 8px；实测输入栏 `[72,2188]`、最新一行底部 2170，点歪会弹键盘）。
4. 挑人只在**最新 3 个可用候选**里 random——保留随机性（不做「永远点最上面那条」这种机器特征），
   但随机范围收敛到刚说话的那几个。
5. 同一个人连发几条时，保留**最新**那条对应的节点（旧实现保留第一次出现的，也就是最旧的一条）。

### 12.4 实测证据（OPPO PLB110 / 抖音 40.8.0）

```
22:02:43 采集：原始 3 条 → 可用 3 人；最新 3 人 A@y2090、B@y1965、C@y1862
22:02:43 候选 3 人（最新窗口 3 人），随机挑中 B  → 已关注 B，进度 1/10
22:02:53 评论区底行已换：「三缺一：饼饼大厨说得好」→「Rattle🌻」
22:02:53 评论区已推进到新评论，按最新一屏采集
22:02:54 最新 3 人 D@y2090、E@y2010、F@y1877 → 随机挑中 D
```

### 12.5 顺带修掉的两个坑（都会让「关注成功」不计数）

**坑 1：校验窗口只有 3 秒，而一次校验要跑 3 趟全树遍历。**
`findFollowedButton` 原来对 `取消关注` / `互相关注` / 配置项**各跑一次 `collect`**，
这台真机一趟遍历 1.4s ⇒ 一次判断要 4 秒多，3 秒窗口里经常连一次采样都没完成，
于是「画面明明弹出『关注成功』，进度却不涨」。
修法：改成**一趟快照 + 内存比对**（`isAlreadyFollowed`），并把窗口放宽到 6 秒。
实测：走「快捷操作栏 → 资料卡」这条路 4 秒内就能确认成功（改之前这条路几乎必失败）。

**坑 2：点完「资料卡」只等 500ms 就去点关注。**
卡片是滑入动画，500ms 时按钮还在移动，拿动画中的 bounds 去点会点空。
现在等 900ms 再找按钮。

**坑 3（安全）：礼物面板的按钮叫「赠送」。**
实测一次误触把礼物面板打开了，面板里选中一个 **2999 钻**的礼物，唯一可点的按钮是「赠送」——
而 `PAID_HINTS` 里只有「小心心/支付/充值/购买/打赏/送礼」，**没有「赠送」**。
已补 `赠送 / 送礼物 / 钻 / 钱包 / 余额`。这条守卫在 `Actions.tapNode` 最底层，
只要漏一个词就是真实扣款，所以宁可多列。

### 12.6 仍未解决

- **点评论行可能打开礼物面板**：评论行上方常飘着礼物/送礼动效，它们可点且会盖在评论行上。
  实测一轮里连续三次点击都打开了礼物面板（页面变 UNKNOWN 0/6），只能靠 `ensureLiveRoom` 按返回恢复。
  恢复本身有效，但每轮白花十几秒。要根治得判断「落点最上层是谁」，无障碍拿不到 z 序，暂未做。

### 12.7 「追最新」真正的病根：评论区会脱离底部（2026-10-28 实测）

上一节（12.3）的做法在真机上只对了一半。补做的取证把根因翻了出来，结论比"等列表自己滚"具体得多。

**现象**：关注完第一个人之后，评论列表**不再滚动**——屏幕上是同一批评论，2 分钟内一字未变。

**真相**：抖音的评论区在**被点过一次**之后会脱离底部（用户在阅读位置），新评论不再上滚，
全部堆在底部一个浮出来的浮标后面：

```
[36,2031][598,2103] 春梅3046 关注了主播
[36,2111][351,2170] 小莲 关注了主播
[54,2107][299,2160] Button  text="99+条新消息"  id=r66   ← 就是这个
```

**这个「99+条新消息」按钮就是唯一的"刷新评论/回到最新"入口**（滑动是不行的，见 12.2）。
点它之后 3 秒内列表就跳到了最新一屏：

```
19:57:47.615 D 发现新消息浮标：text="30条新消息"
19:57:47.668 D 点击 新消息按钮 @ (209,2127)
19:57:50.651 D 扫描：原始 8 → 评论行 8（首见 7）→ 可用新人 7
```

**不点它会怎样**：干等它自己恢复，实测等了 **123 秒**才等到新评论
（`19:53:05 等到新评论：等了 123s`）——这就是"关注完一个就再也追不到最新"的直接原因。

**由此修掉的两个设计错误**：

1. **"等 6 秒没等到就降级按当前屏取人"是错的**。日志统计：76 轮里 43 轮（57%）走了降级，
   而 22 轮（29%）在最新的人都处理过之后**静默下滑**，挑到 `y=1805` 这种第 4~5 新的老行。
   现在删除该降级路径，改为**只从"本轮首见"的评论行里挑人**，没有就等。
2. **判据从「底行换人」改为「行级首见」**。底行会因为插入动画/节点复用短暂读不到
   （采样中 9 行曾掉到 7 行），"最底那一行"这个锚点本身就会抖。

**现在的完整链路**：

```
每轮：
  1. 采集一次（单趟遍历）→ rows（屏上几行）/ freshRows（首见几行）/ candidates（首见且未处理）
  2. 有候选 → 取最新 3 人加权随机
  3. 没候选 → 若底部有「N条新消息」浮标，点它跳回最新（12s 内最多点一次，不盲点坐标）
              没有浮标 → 继续等；每 5s 在悬浮窗上报「等新评论 12s（屏上 9 行都已处理）」
              读不到任何评论行连续 4 次 → 判定定位失效并中止
              连续 5 分钟没有任何新评论 → 如实中止并提示换房间（不自动换）
```

**实测结果**（不求人直播间，连续两轮 4/4、2/2 全部成功）：

```
20:01:43 评论区未跟进最新，已点「99+条新消息」回到最新
20:01:47 等到新评论：等了 4s，屏上 6 行、首见 6 行、可用 6 人
20:01:47 挑中「水墨人」（y=1965，窗口内最新）
20:02:17 本轮完成：关注 2 人，达目标 2（其中 1 轮为新评论等待过，累计 4s）
```

**顺带修掉**：评论区跳回最新时会短暂插一行 `加载中……`，实测被当成昵称收进了候选
（`候选窗口`里出现过 `* * 加载中……@y2150`），已加入系统消息过滤词。

## 13. 私密账号：关注只发申请，必须立刻跳过（2026-10-29，vc16 / 1.2.9）

### 现象

用户反馈：**关注了私密账号，关注人数没有增加**，人却还停在那儿。

抖音官方口径很明确——「开启私密账号后，**所有关注操作都会变成提交申请，不会直接关注成功**，
需等待对方手动通过」。对脚本来说这是一次**完全白干的动作**：

1. 粉丝数不增加（用户看到的「人数没涨」）；
2. 占掉一次抖音的**单日关注额度**（200 人/天，很宝贵）；
3. 旧逻辑还会为它**白等满 6 秒**（`VERIFY_TIMEOUT_MS`）才判「未变成已关注」，
   然后才 `continue` 下一个人——一轮净亏 6 秒。

### 判定（配置驱动，全等匹配）

`douyin_locator.json` v12 新增顶层数组 `privateAccountHints`：

```jsonc
"privateAccountHints": ["私密账号", "私密帐户", "申请关注", "已申请", "已提交请求",
                        "等待通过", "请求关注", "已发送关注请求", "关注请求已发送",
                        "已发送申请", "申请已发送"],
```

**必须全等匹配**：改成包含匹配会让「关注」命中「申请关注」，把所有人都判成私密账号。

#### 结构性安全：这个分支不可能误伤正常账号

`awaitFollowOutcome` 每轮只跑**一趟**快照（`ttl = 0`），三个判据在内存里比对，**顺序固定**：

```
① 已关注（取消关注 / 互相关注）→ FOLLOWED   ← 正常账号永远先命中这一条
② 私密（privateAccountHints）  → PRIVATE
③ 都没有                       → 继续轮询 / 超时
```

所以 PRIVATE **只在「点了关注但没出现取消关注」时才可能命中**——那本来就不算关注成功。
不存在「关注成功了却被判成私密账号」的路径。

### 两个触发点

| 时机 | 行为 |
|---|---|
| 点关注**之前**（资料卡带「私密账号 / 申请关注」标记） | 直接跳过，**连那一次点击都不做**（连申请都不发） |
| 点关注**之后**（按钮变成申请态） | **申请文案一出现就返回**，不等满 6 秒；同样不计进度 |

两种都走 `skipPrivate()`：写日志 → `store.markPrivate(nickname)` → 面板提示
「「xxx」是私密账号，已跳过」 → 关弹层 → 下一轮。

### 为什么私密名单要单独存

`FollowedStore` 里新开一个 `private_names`（不是并进 `followed_names`）：

- 并进去会让**「已关人数 / 今日已关注」两个数字说谎**，`remainingToday` 也会算错额度——
  用户要的正是「人数没增加」这个事实被正确对待；
- 但**去重必须共享**：同一个人会在评论区反复说话，不记就得反复点开、反复发申请。
  所以 `scanOnce` 里多了一条 `if (store.isPrivate(name)) continue`。

### 未收录文案怎么办

超时分支会把**弹层里所有 ≤8 字的短文案**打进日志：

```
「xxx」点关注后 6000ms 内未变成「已关注」，按未成功处理，不计入进度；
弹层文案：关注、私密账号、粉丝、127、私信、…
```

抖音的申请态文案在版本间来回改过（已申请 / 已提交请求 / 等待通过…）。与其猜，
不如让真机把实际文案吐出来——照着补进 `privateAccountHints` 即可，不用改代码。

### 真机验证（vc15 机制包 + vc16 回归）

私密账号在直播间里可遇不可求，所以用**两个包**分开证：

1. **vc15（临时把判据改成「关注」= 把每个人都当私密账号）**
   ```
   面板：● 运行中 0/300   本场 0   今日 31   已关 41
   说明行：「* 离信」是私密账号，已跳过
   随后：等新评论 17s（屏上 8 行都已处理）   ← 已经在下一个人/下一批评论上
   ```
   证明：识别 → 跳过 → **不计数** → **不原地磨**，四件事一次跑通。
   （该包不进发布链路，`version` 临时为 99，测完即恢复。）
2. **vc16（正式判据）** 跑 70 秒：`1/300 → 2/300`，正常账号照常关注、照常计数，
   没有出现误判跳过。

## 14. 关注成功后立刻刷新评论（2026-10-29，vc20 / 1.3.3）

### 现象

用户反馈：**「点击关注后需要立马刷新评论，不要有卡顿现象」**。

翻 vc18 的真机日志，这是可量化的：从「已关注」到评论区真的跳回最新，中间隔着 **12~15 秒**：

```
22:04:16.549 已关注「* * 世界观影角」
22:04:31.232 发现新消息浮标：text="3条新消息"      ← 14.7 秒后才刷新
22:04:41.752 挑中「* Tears」                       ← 再 10.5 秒才轮到下一个人
```

一个完整周期 **25~26 秒**，其中 15 秒屏幕上是**冻住的旧评论**。原因有两层：

| 层 | 问题 |
|---|---|
| 触发时机 | 刷新只发生在 `awaitFreshScan` 里，而它要等**扫描间隔（默认 30 秒 / 现场 10 秒）先走完**、扫描发现「一个人都不新」才去点浮标 |
| 每次动作太贵 | 点浮标用「对 2 个文案各跑一次 `find`」（没找到就是 2 趟全树遍历 ≈2.8s）；关资料卡用「`collect` 找关注按钮 + `snapshot` 判已关注」（≈2.8s），而这两趟在关注成功路径上完全多余 |

### 关键机制：评论区为什么会「冻住」

点开一次评论行 → 评论区**脱离底部**（抖音只在底部贴边时才自动上滚）→ 新评论全部堆在浮标后面，
屏幕上永远是同一批旧人。要让它重新贴回底部，**只有一条路**：点那个「N条新消息」浮标。

所以「关注完卡顿」的本质是：**列表已经冻住了，而我们在等一个跟刷新无关的间隔**。

### 改法（四点）

1. **刷新挪到关注动作刚结束的 2.5 秒后**，不再等间隔：
   ```
   已关注 → closeCard → settle(2.5s) → 探浮标 → 点它 → settle(1.2s) → 补足剩余间隔
   ```
   为什么不「关注一落定就点」：抖音要**攒够几条**才浮出浮标，刚关掉资料卡时常常还是 0 条
   （vc20 真机 10 次里有 4 次探不到，就是紧跟在上一次刷新之后、列表还贴着底部）。
   2.5 秒是热门房里攒到 1~3 条的典型时长。

2. **探测耗时算在扫描间隔里**（`waitAfterFollow` 里 `rest = interval - elapsed`），
   所以整条节奏**不会比用户设置的间隔更长**，不必为刷新牺牲拟人化间隔。

3. **探测改成一趟快照**：`snapshot()` 里在内存比对「条新消息 / 回到最新」，
   取**面积最小**的那个（容器和文本节点都带这串字，点容器会偏），
   再用新加的 `Actions.tapRect(rect)` 落点——它与 `tapNode` 共用同一条拟人化手势通道
   （矩形内随机取点），而不是固定点几何中心。找不到浮标直接返回，**绝不盲点坐标**。

4. **关资料卡不再重复探测**：关注成功路径传 `knownOpen = true`（上一行刚在弹层里读到「已关注」），
   省掉整趟遍历；其余路径把「关注按钮还在 / 已关注」合并成**一趟快照**判断。
   ⚠️ 不能无条件跳过探测：盲按返回会**退出直播间**。

### 触发点

| 时机 | 是否刷新 |
|---|---|
| 关注成功 | ✅ 2.5s 后探，探到就点（主要路径） |
| 跳过「已关注」的人 | ✅ 立即探一次（不打额外等待，避免房间全是已关注时每人都多 2.5s） |
| 私密账号跳过 | ✅ 同上 |
| 每个休息点之前 | ✅ 只刷新、不等（`intervalMs = 0`），歇几分钟期间评论会自己滚 |
| 扫描间隔 < 3s | ⏭ 跳过探测，交给下一轮的即时刷新兜底 |

### 真机实测（vc20 / 1.3.3，同一台机、同一档 10 秒间隔）

```
23:07:14.269 已关注「* * KAI」
23:07:21.197 → 已点「19条新消息」把评论区拉回最新（耗时 2411ms）   ← 6.9 秒（含 2.5s 攒评论）
23:07:26.829 挑中「* 晚上吃什么」                                ← 12.6 秒后已是下一位
```

| 指标 | vc18 | vc20 |
|---|---|---|
| 已关注 → 评论区刷新 | 12~15 秒 | **5~7 秒**（探到浮标时） |
| 已关注 → 下一次挑中 | 25~26 秒 | **11~20 秒** |
| 每次关注的总耗时 | ~26 秒 | **~15 秒** |

10 次关注里 6 次探到浮标（`19条 / 12条 / 3条新消息`）、4 次本来贴底（日志「列表还贴着底部，无需刷新」），
两种都正常推进，没有一次空转。

## 15. 评论区刷新改为双通道：浮标优先，没浮标就滚容器（2026-10-29，vc26 / 1.3.7）

### 需求

「评论刷新目前是靠新消息实现，人少的直播间也要能下滑；关注一个马上刷新，两种方式并用，
没有新消息就手动下滑，**注意不要切换到别的直播间**。」

这确实是 vc20 的漏洞：以前只认「N条新消息」浮标，而抖音**要攒够几条新评论才浮浮标**，
人少的直播间经常一整分钟都浮不出来——关注完一个人，屏幕上还是那几条旧评论，看着像卡住。

### 关键决定：用 `ACTION_SCROLL_FORWARD`，不用手势

抖音直播间的整页是竖向 ViewPager，**手指从下往上就是「切下一个直播间」**
（docs/M2 §12.2 实测 550px 就切房，120px 又完全没有位移——手势两头都不成立）。
所以这里不发任何手势，而是把 `ACTION_SCROLL_FORWARD` **直接发给评论容器**：
动作只作用于那个控件内部，物理上不可能触发全局翻页。

真机取证确认评论容器是可滚动的：`com.ss.android.ugc.aweme:id/r68`。

### 三道保险

1. **只接受「像评论区」的容器**：`isScrollable` + 中心点落在评论区区域 + **高度 ≤ 55% 屏高**。
   最后一条是为了排除整页 ViewPager——它也是 scrollable，滚它就是切房。
2. **滚动区域本身就避开危险区**：x 取 6%~62%（右侧那一列是点赞/礼物/分享），
   y 从 42% 屏高到输入栏顶（复用 `rowBottomLimit`，与「评论行不能被输入栏压住」同一条线）。
3. **滚完比对主播名**：`CurrentRoomAnchor` 前后不一致就立刻 `pauseForRecovery` 并报错，
   绝不在别人的房间里继续点。

### 方向取证（真机，必须验，验错了就是在关注老观众）

滚前滚后各抓一趟快照，比较共同评论行的 y 变化：

```
容 com.ss.android.ugc.aweme:id/r68，共同行 1 条、平均 y 变化 -231（负=内容上移/更靠最新），新增 2 行、消失 3 行
容 …                                    共同行 3 条、平均 y 变化 -103
容 …                                    共同行 1 条、平均 y 变化 -236，新增 2 行、消失 3 行
```

三次都是**负值 = 内容上移 = 底部露出更靠后的（更新）评论**，方向正确。
若哪天抖音把评论顺序反过来，这里的 y 变化会变正——`SCROLL_DIAGNOSE = true` 打一个包就能重新取证。

⚠️ 取证用的两趟快照要 2.8 秒，方向确认后已把 `SCROLL_DIAGNOSE` 默认关掉，
否则每人多花 3 秒（实测关注间隔会从 18s 涨到 20s 以上）。

### 两个触发点

| 时机 | 动作 |
|---|---|
| 关注成功 / 跳过已关注 / 私密账号跳过之后 | 先点浮标；**没浮标就滚容器** |
| 等待新评论时的「12 秒体检」（原本只点浮标） | 同样：浮标 → 滚动 |

### 「滚不动」是正常状态，不是失败

列表本来就贴着最新一屏时，`performAction(ACTION_SCROLL_FORWARD)` 直接返回 false：

```
00:13:01.477 评论区未跟进最新 → 系统拒绝了滚动动作（列表已到最新一屏），本轮不下滑
00:13:43.626 关注「* 橙子皮」成功 → 系统拒绝了滚动动作（列表已到最新一屏），本轮不下滑
```

这说明**确实没有更新的内容可看**（房间安静），此时正确做法就是继续等，不做任何多余动作。
日志里如实写「列表已到最新一屏」，不要写成「下滑失败」——那是两回事。

### 真机实测（vc26，PK 房间，评论 5~7 条）

```
00:13:01.477 评论区未跟进最新 → 系统拒绝了滚动动作（列表已到最新一屏）   ← 12 秒体检触发的
00:13:13.106 评论区停在旧位置 13s → 系统拒绝了滚动动作（列表已到最新一屏）
00:13:25.960 已关注「* * 望京山⛰️」，进度 3/183
00:14:06.222 发现新消息浮标："7条新消息"                                ← 有浮标时仍优先点浮标
00:14:43.627 跳过已关注的「* 👌」 → 系统拒绝了滚动动作（列表已到最新一屏）
```

- 关注间隔 **18~20 秒**（与只有浮标通道的 vc23 一致，滚动没拖慢节奏）；
- 主播名全程是「饱饱」，**没有切房**；
- 滚动成功那几次（vc25 取证包）确实「新增 2 行、消失 3 行」，露出来的就是更新的评论。

### 遗留

整屏手势下滑永远不做。它在这个页面上等价于「切下一个直播间」，
而 `ACTION_SCROLL_FORWARD` 已经能把「往下看更新的评论」这件事做完，没有理由再冒切房风险。

### 15.1 把「关注后下滑」压到 1 秒内（vc32 / 1.4.3）

第一版（vc26）实测 700ms~1.4s，用户要求「起码一秒以内」。逐段量出来，瓶颈全在**遍历**上：

| 环节 | 原始做法 | 耗时 | 改法 |
|---|---|---|---|
| 找「N条新消息」浮标 | `snapshot()` 全量快照 | ~1.4s | `findFirst()` 只比文案（不建快照）→ 约 0.6~0.9s |
| 找评论容器 | Kotlin BFS 遍历 | ~0.7~1.2s | `findAccessibilityNodeInfosByViewId("r68")`（framework 原生）→ **3~14ms** |
| 输入栏位置 | `rowBottomLimit` 一次快照 | ~1.4s（缓存过期时） | 改用屏幕比例（42%~90%），0 成本 |
| 滚动后等待 | `ctx.settle(900ms)` | 900ms + **1.4s**（settle 末尾会 `guard()`） | `delay(180ms)`；关注后这条路连 180ms 都不用 |
| 防切房校验 | `CurrentRoomAnchor` 前后各一次 | ~2s | 只在 `SCROLL_DIAGNOSE` 取证模式做 |

最后一步是**顺序调整**：关注后**先滚、再找浮标**。找浮标那趟遍历（600~900ms）是最大的单项，
而滚动命中容器缓存只要几毫秒；滚动与点浮标在效果上等价（都是让新评论露出来），
点击浮标那条通道保留在等待期的 12 秒体检里（那里有预算）。

两个踩过的坑，都值得记住：

1. **`performAction(ACTION_SCROLL_FORWARD)` 返回 false ≠ 节点失效**。
   列表贴着最新一屏时系统同样会拒绝。第一版把 false 当成「缓存失效」→ 每次都白重建容器，
   实测多花 600~900ms。判活要用 `node.refresh()`（约 1ms）。
2. **`ctx.settle()` 末尾会跑 `guard()`**，那是一次全量快照（1.4s）。
   在没有点击类动作的路径上（滚动）改用裸 `delay()`，风控交给主循环每轮的 `guard()`。

vc32 真机（同一直播间，连续 4 次关注）：

```
00:48:03.669 关注「Lᴏve ᴛ꯭ᴏ꯭.」成功 → 已下滑评论（命中容器缓存，共 12ms）
00:48:20.865 关注「* * ✨小幸运」成功 → 已下滑评论（命中容器缓存，共 6ms）
00:48:36.301 关注「* * 1111」成功 → 已下滑评论（命中容器缓存，共 9ms）
00:49:05.820 关注「* 博費氣」成功 → 已下滑评论（命中容器缓存，共 6ms）
```

冷启动那一次（缓存还没建立）仍需 600~900ms，但**预热已经挪到任务启动时**：
`评论容器已预热：com.ss.android.ugc.aweme:id/r68（3~14ms）`——用户点「开始服务」那一刻完成，
不在关注路径上。

## 17. 卡顿根因：不是等待设错，是无障碍遍历被系统节流到 5~16 秒（2026-10-30，vc36 / 1.4.7）

### 现象与取证

用户反馈「刷新评论还是会卡顿」。拉真机日志 `R-20261030-A88080`（vc33，21:02~21:05）后一眼看到：

```
20:20:21 快照耗时  5245ms（遍历  142 节点）
21:02:41 快照耗时  8426ms（遍历  584 节点）
21:03:48 快照耗时 11757ms（遍历  604 节点）
21:04:05 快照耗时 16099ms（遍历  610 节点）
21:04:47 快照耗时 10325ms（遍历  611 节点）
21:05:19 快照耗时  7835ms（遍历  615 节点）
```

**142 个节点也要 5.2 秒** ⇒ 每节点 26~37ms，是健康值（≈2ms）的 10~15 倍。
`Actions.snapshot` 每个节点要 7 次跨进程调用（text / desc / id / editable / bounds / childCount / getChild），
在被节流时一次全树就是 10 秒量级。

⚠️ 这不是「偶发抖动」：`docs/M2 §10` 记的 1.4s/647 节点是**健康状态**下的数字，
而**直播间在播视频**时稳定落在 5~16 秒（视频播放导致无障碍树持续失效重建，
系统对 IPC 做了限速）。养号视频页早就记录过同样现象（1173 节点 / 5~20s）。

### 为什么会「卡」：一次关注要跑 8~10 趟全树

| 环节 | 遍历 | 旧成本 |
|---|---|---|
| 主循环 `ensureOnAirOrWait` → `detect()` | 全树 | 8~16s |
| 扫描 `collect`（整树找 `：`） | 全树 | 8~16s |
| 扫描 `rowBottomLimit`（找输入栏） | 全树 | 8~16s |
| 点击昵称后 `settle(600)` → `guard()` | 全树 | 8~16s |
| `awaitCard` 找关注按钮 | 全树 | 8~16s |
| 点关注后 `awaitFollowOutcome` | 全树 ×1~2 | 8~32s |
| `closeCard` 的 `settle(500)` → `guard()` | 全树 | 8~16s |
| `waitAfterFollow` 的 `settle(2500)` → `guard()` | 全树 | 8~16s |

实测一轮 25~27 秒（`21:04:32 → 21:04:57`），**几乎全部时间都在遍历**。

### 六处改动（全部是「少跑遍历」，不改业务判据）

1. **扫描改在评论容器子树内采集**（最大单项）。
   `collect(target, max, root = r68 容器)`：节点数 610 → 几十，8~16s → 几百毫秒。
   容器只走**快通道**（缓存 `refresh()` → `findByViewId`），绝不在这里用
   `scrollableIn` 的区域遍历兜底（那本身又是一趟全树）。
   容器内采不到任何行时**退回整树**再采一次（抖音改版换 id 时不至于采不到人），日志会写明 `(整树兜底)`。
2. **删掉 `rowBottomLimit` 的遍历**，改用屏高比例 0.915（输入栏顶 91.4%、最底一行 88.6%，落在中间）。
   于是「一次扫描」从两趟全树变成一趟（且是容器内那趟）。
3. **关注结果改「刷新那颗按钮」**。点关注后抖音是**就地**把主按钮文案换成「取消关注 / 申请关注」，
   所以 `refresh()` + 读 text/desc（1~3 次 IPC，毫秒级）就能定论；只有节点
   **脱离节点树**（`refresh()` 返回 false，资料卡被重建）才退回整树快照。
   `awaitFollowOutcome` 因此从「每 250ms 一趟 10 秒的全树」变成毫秒级轮询。
4. **`guard()` 降频到 5 秒一次**（`FlowContext.GUARD_MIN_INTERVAL_MS`）。
   等待新评论是 800ms 一轮，原来每轮 `settle()` 都跟一次风控检查 = 每两三秒烧掉十几秒。
   风控提示是持续可读的，最坏晚 5 秒发现不会让限流升级成封号；
   **M3 发评论后的那一次必须 `guard(force = true)`**（「评论太快」是闪一下就没的 toast）。
5. **弹层判定的快照加 `lean = true`**（`awaitCard` / `cardStillOpen` / `cardLabelsDump`）：
   跳过 `id` 与 `editable` 两次跨进程调用，每节点 7 → 5 次（省 25%~30%）。
   安全性依据：`douyin_locator.json` 的 `pages`（35 条特征）与 `overlays`（6 条规则）
   **全部是 text/textContains/desc/descContains，没有任何 ID 或 EDITABLE 特征**，
   所以这份缩水快照进缓存后对页面判定、浮层判定、风控判定都无害。
6. **两处 `settle()` 改裸 `delay()`**：
   - `closeCard` 的 `settle(500)` → `delay(500)`（紧接着是滚评论，非点击）
   - `waitAfterFollow` 的 `settle(2500)` → `delay(300)`。
     那个 2500ms 原本是「等抖音攒够新评论浮出浮标」，而现在刷新通道的第一选择是**直接滚容器**
     （缓存 6~12ms），根本不需要等浮标。这 2.5 秒 + 后面那次全树检查，
     是「关注成功 → 评论动」里用户最容易感知的 4 秒。
     顺带：`LiveTargets.input` 字段随之删除（只为 `rowBottomLimit` 存在）。

### 风险与兜底

| 改动 | 万一不成立会怎样 |
|---|---|
| 容器内采集 | 采到 0 行 ⇒ 自动退回整树，行为回到旧版，只是慢 |
| `r68` 混淆 id 变了 | `findByViewId` 返回 null ⇒ 返回 null ⇒ 整树采集，不报错 |
| 快速通道判关注结果 | 按钮节点 refresh 失败 ⇒ 退回整树快照，与旧版一致 |
| `lean` 快照 | 只有 text/desc；页面/浮层/风控都不用 id/editable（已核对配置） |
| `guard` 降频 | 风控提示持续可见，最坏晚 5 秒；M3 toast 场景已 force |

### 验收（真机 vc36）

看日志里这三样：

1. `扫描（冒号切分兜底(容器内)）：原始 N → 评论行 M` —— 应出现 `(容器内)` 字样，且 M 与以前一致；
2. `快照耗时` 告警明显变少（每轮只剩 `detect()` 一次）；
3. `关注「X」成功 → 已下滑评论（命中容器缓存，共 Nms）` 与「已关注「X」」之间的间隔，
   应从 25 秒级降到 **2 秒内**。

## 18. vc36 回归：点击关注后人数不增加（2026-10-30，vc37 / 1.4.8）

### 现象

vc36 上线后用户立刻反馈「点击完关注后 人数不增加」。功能在跑、按钮也点了，就是进度不动。

### 根因：快速通道没有出口

vc36 为了压掉「点关注后每 250ms 跑一趟 10 秒全树」，把结果判定改成
**刷新那颗被点过的按钮、读它的文案**（`quickProbe`）。设计假设是：

> 抖音点关注后，主按钮会**就地**把文案换成「取消关注 / 申请关注」，节点还是同一个。

这个假设在**一半情况下不成立**。抖音常常重建整个资料卡，或者把那个 `AccessibilityNodeInfo`
对应的 View 复用给别的控件——此时 `refresh()` **依旧返回 true**（节点对象没死），
但读到的文案永远不是「取消关注」。

而 vc36 的循环写成了：

```kotlin
if (useButton) { ...; delay(250); continue }   // 只有 refresh 返回 false 才退出
```

`refresh()` 一直是 true ⇒ **6 秒窗口里一次整树判定都没做** ⇒ 直接判 `UNKNOWN` ⇒ 不计入进度。
旧版之所以是好的，恰恰因为它**每轮都跑全树**（虽然慢，但一定读得到真实界面）。

### 修法（三层保险，缺一层都会再次漏计）

1. **快速通道有预算**：`QUICK_PROBE_BUDGET_MS = 2000`。超预算**强制**转整树，
   不再「有按钮就永远不跑整树」。
2. **复用检测**：`quickProbe` 读到的文本既不是「关注」也不是任何已知结果 ⇒ 判定为
   「节点已被复用到别的控件」，**立刻**转整树（不等预算用完）。
3. **整树判定保证至少跑一次**：循环条件从 `while (now < deadline)` 改成
   「跑过整树之后才允许按超时退出」（`snapshotDone` 标志）。
   否则「快速通道没结论 + 到点」还是会直接判失败——这正是 vc36 的形态。

### 顺带加的取证日志

以后日志里能直接看出快速通道到底卡在哪：

```
等关注结果：按钮文案仍为「关注」                      ← 界面还没刷新完（正常）
关注按钮节点已被复用（读到的文案是「XXX」），改走整树判定   ← 节点被复用（vc36 死在这里）
关注按钮节点已脱离节点树（资料卡被重建），改走整树判定
关注结果（按钮直读，180ms）：ALREADY_FOLLOWED          ← 快速通道成功（最优路径）
```

### 性能取舍（如实记）

| 情况 | vc37 耗时 |
|---|---|
| 按钮就地更新（快速通道命中） | 180~2000ms |
| 节点被重建 / 复用 | 2s 预算 + 一趟整树（8~16s）≈ 10~18s |

也就是说 **vc37 只比 vc36「慢」，但和 vc35 及以前持平**；而 vc36 是「快但错」。
速度的进一步优化要等拿到 vc37 的真实日志——先看清按钮文案的实际变化时序
（是「不变」还是「变成别的字」），再决定是缩预算还是干脆去掉快速通道。

⚠️ **教训（写给以后的我）**：把一条「每轮都重读整个界面」的判据换成「只读一个节点」时，
必须回答「这个节点凭什么还能代表界面」。答案不成立时，**回退路径必须是默认路径而不是例外路径**。

## 19. 「已关人数」虚高：两种「已关注」混在一本账上（2026-10-30，vc42~43 / 1.4.12~1.4.13）

### 现象

用户：「我发现显示已关注的数量跟实际的不一样」。日志 `R-20261030-F16CD0`（vc41，23:12 上报）里能直接对出来：

```
23:12:01 扫描：可用新人 3（已排除：本轮已处理 15、历史已关注 13、黑名单 6 …）
23:12:19 已关注「* 玉杰」，进度 7/200（今日 7/200）
```

**面板「已关 13」 vs 实际关注 7 个**，差 6。

### 根因：两条完全不同的路写进了同一个名单

| 情况 | 代码路径 | 该不该算「已关」 |
|---|---|---|
| 点「关注」→ 界面变成「取消关注」 | `markFollowed()` | **算**（这是成绩） |
| 打开资料卡，按钮本来就是「取消关注」 | `markFollowed()` ← 错就错在这 | **不算**（我们什么都没做） |

两条路都进 `followed_names`，而面板「已关 N」= `names.size`，
于是「别人早就关注过的人」全部被算成了我们的成绩。

那一场直播里被跳过的 6 个人（日志逐条可查）：

```
23:05:49 萌兔        已经是关注状态
23:06:14 * 橘漫小剧场2  已经是关注状态
23:08:39 上上谦12     已经是关注状态
23:09:43 * 汐汐叙晚风   已经是关注状态
23:11:26 柠檬爆       已经是关注状态
23:12:00 姗月        已经是关注状态
```

这不是罕见情况：同一场直播里反复出现同一批观众，本来就是直播间评论区的常态。

### 修法：拆成两个名单，去重仍然取并集

| 键 | 含义 | 用途 |
|---|---|---|
| `followed_names` | 本机**真正关注成功** | 面板「已关 N」、名单第一段 |
| `already_followed_names` | 打开时就已关注 | **只参与去重**，名单第二段并注明「未重复关注」 |

`FollowedStore.isFollowed()` = 两边并集，所以**不会重复关注任何人**；
`knownCount()` 只数前者（面板数字因此不再虚高），`alreadyCount()` 数后者。

### 旧数据怎么办：一次性迁移（`split_migrated_v42`）

vc41 及以前的记录分不出谁是谁。留着它就等于留一个永远对不上的数字，所以首次启动时
**整批挪进 `already_followed_names`**，并把 `followed_names` 清空：

- 去重集合（并集）**一个都没丢** —— 不会重复关注任何人；
- 代价只是下次遇到这些人要多开一次资料卡（认出「取消关注」就跳过）；
- 「已关」从 0 重新累计，「本场 / 今日」两个数字**完全不受影响**（它们本来就只数真关注）。

只跑一次（`KEY_MIGRATED` 标记）；当前只有本机这份 vc41（换过包名，等于新装）受影响。

### 面板上的效果

```
本场 6   今日 6   已关 6          ← 三个数字从此一致
──────────
以下 3 人打开时已关注，未重复关注：
· 萌兔
· * 橘漫小剧场2
· 上上谦12
```

### 教训

**「已关注」是一个状态，不是一件成绩。** 凡是把状态当成绩计数的地方，都要问一句
「这个状态是我造成的，还是我发现的」——两者混在一个计数器里，数字必然说不清。

## 20. 「点了关注但界面没变」：先把按钮等到停稳，没生效就重点一次（2026-10-30，vc44 / 1.4.14）

### 现象与样本

日志 `R-20261030-A8EE6C`（vc41）一场 5 次点关注，**3 次失败**；加上 `C478CD` 那场（6 次里 1 次失败），
11 次里 4 次。失败形态完全一致：

```
23:03:50 点击昵称区「* 55💤.」 @ (117,2042)
23:03:51 点击 关注按钮 @ (557,1632)          ← dispatchGesture 返回成功
23:03:51 等关注结果：按钮文案仍为「关注」
23:03:57 「* 55💤.」点关注后 6000ms 内未变成「已关注」，按未成功处理，不计入进度；
         弹层文案：55💤.、关注、Lv.15、荣誉等级、未加入、粉丝团
```

弹层里「关注」还在 ⇒ 这一下确实没生效。**判失败、不计进度是对的**，问题在于为什么会落空。

### 先排除掉的三种可能（都用日志对过）

| 猜测 | 结论 |
|---|---|
| 点到我们自己的悬浮窗上了 | **否**。失败点 y=1632/1650/1830，而面板展开且未展开名单时底边约 1485；窗口 x 起点 36px 也不足以覆盖按钮区（按钮 bounds 宽度 ~200px）。vc44 起日志会直接打「压在悬浮窗上」 |
| 抖音在限流（连续关注被拒） | **否**。同一场里是 失败→成功→失败→失败→成功 交替，限流不会这样 |
| 落点坐标随机偏了 | **否**。失败点 (575,1637)/(566,1650)/(557,1632) 与成功点 (596,1625)/(566,1650)/(599,1628) 完全重叠 |

### 最可能的原因：资料卡滑入动画期间点了「移动中的按钮」

代码里早就记着这个坑（`awaitCard` 的注释 + `CARD_ENTRY_SETTLE_MS = 900`），
但它**只加在「快捷操作栏 → 资料卡」那条路上**；点评论行**直接弹资料卡**的那条路没有等，
`awaitCard` 一找到「关注」就返回 —— 此时卡片可能才滑到一半，取到的 bounds 是半路坐标，
等触摸真正落到屏幕上按钮已经挪走 ⇒ 点在空白处。

> 如实记：11 个样本里「点昵称 → 点关注」的间隔，失败是 {2.73, 1.31, 0.88, 1.06}s，
> 成功是 {2.04, 1.87, 1.53, 2.65, 1.38, 2.52, 1.32}s —— **区间严重重叠，这条证据并不干净**。
> 所以这一版没有只押动画一个原因，而是「等停稳 + 重试 + 取证」三件一起上，
> 让下一轮日志自己把原因指出来。

### 三处改动

1. **点之前等按钮停稳**（`awaitButtonStill`）：每 180ms `refresh()` + 重读 bounds，
   连续两次一致才认为动画停了，最多 4 轮（≈720ms）。位置在动会记一行日志：
   `关注按钮 位置还在动（y 1650 → 1612），等它停稳再点`。
2. **没生效就重点一次**（`tapFollowAndWait`，`FOLLOW_TAP_MAX_ATTEMPTS = 2`）：
   第一次 6 秒没变化 ⇒ **重新走一遍 `awaitCard`**（此时卡片已彻底停稳）再点一次。
   **安全性**：重取按钮这一步会把「取消关注 / 互相关注」认成 `ALREADY_FOLLOWED` 直接返回，
   所以重试**不可能**把已经关注的人取关。
3. **把「点的是哪个关注按钮」写进日志**：`text / desc / id / bounds / 宽高`。
   抖音的**快捷操作栏里也有一个「关注」文本节点**，文案和资料卡的按钮一模一样，只有 id 和位置不同。
   之前 `(554,1830)` 那一次明显比其它次靠下 200px，但旧日志只有落点、没有 id，
   分不清是「资料卡按钮点了没反应」还是「点成了操作栏里的同名项」——下一轮就能分辨。

### 验收看什么

1. `关注按钮候选（第 1 次，X）：text=关注 desc=- id=xxxx bounds=[…]` —— id 是否每次都一样；
2. 出现 `位置还在动（y A → B）` 说明动画确实在跑，这条就是根因；
3. 出现 `第 1 次点「关注」后 6000ms 界面没变（X），重新取按钮再点一次` 之后是否成功；
4. 「未变成「已关注」」的出现率是否从 ~35% 降到接近 0。

### 实测结果（2026-10-30 23:47–00:04，vc44 + vc45 两轮真机）

同一间直播间（SK月湖795），间隔 30 秒，从 App 里点「开始服务」跑了两轮：

| 轮次 | 时长 | 真尝试 | 成功 | 失败 | 失败率 |
|---|---|---|---|---|---|
| vc41（改动前，两次会话合计） | — | 11 | 7 | 4 | **36%** |
| vc44（本轮） | 10 分钟 | 15 | 14 | 1 | **6.7%** |
| vc45（收尾复验） | 100 秒 | 4 | 4 | 0 | 0 |

> vc44 那轮日志里还有 2 条「未变成已关注」，是**我自己用 adb 点屏幕**造成的干扰
> （弹层文案分别是「说点什么...」和「读不到任何短文案」——资料卡已经被我的点击关掉了），
> 不计入失败率。

四个待定问题，逐条给答案：

**① 「点的是哪个关注按钮」——id 每次都一样，此假设被否掉。**

```
15 次全部：text=关注 desc=- id=tfx bounds=[528,1602][618,1655] 高=53 宽=90
```

一个像素都不差。所以**不是点成了快捷操作栏里的同名「关注」**。
（vc44 之前那个 `(554,1830)` 的异常落点，应该是当次卡片位置不同，不是操作栏。）

**② 「位置还在动」——只出现 1 次，而且恰好是唯一真失败的那次。**

```
23:52:18 关注按钮 位置还在动（y 1636 → 1628），等它停稳再点
```

但注意：**停稳之后又点了两次（(574,1612) 与 (546,1635)，都在按钮矩形内），界面依然 12 秒没变。**
所以「动画没停就点」能解释一部分，但**不是唯一原因**。

**③ 重试有没有救回来——3 次触发、0 次转成功。**
其中 2 次是我外部干扰（资料卡已关，重取按钮时 `awaitCard` 找不到卡，直接返回 UNKNOWN），
1 次（`Owen🍟`）停稳后重复点击仍无效。重试目前的价值是「兜住偶发」，不是「治好根因」。

**④ 剩下那 1 例（`Owen🍟`）为什么还是失败？**

| 证据 | 值 |
|---|---|
| 按钮 id / 位置 | `tfx` / `[528,1602][618,1655]`，与 14 次成功完全一致 |
| 两次落点 | (574,1612)、(546,1635)，都在按钮矩形内 |
| 资料卡内容 | `Owen🍟、男·24岁、德国、关注、Lv.21、荣誉等级、未加入、粉丝团`（卡片完整，不是半截） |
| 界面变化 | 12 秒内零变化，按钮文案始终是「关注」 |

**客户端这边没有可改的了**：位置对、节点对、按钮可点、卡片完整、两次点击都没反应。
更像抖音那侧没接受这次关注（服务端拒绝/瞬时风控），而这类拒绝一般以 toast 形式出现，
客户端读不到（toast 一闪就没，且不在本进程的节点树里）。
要真正确证，只能在点击后 1 秒内用 `screencap` 连拍看有没有红色提示——这属于取证手段升级，不在本轮范围。

### 附：vc44 引入的一个真 bug（vc45 修）

vc44 的 `TouchGuard` 直接在协程工作线程上调 `windowManager.updateViewLayout`，抛
`Only the original thread that created a view hierarchy can touch its views`，
被 `runCatching` 吞掉只留一条 warn ⇒ **那道防护从头到尾没生效过**。日志里 93 条：

```
23:52:17.982 W/悬浮窗: 更新窗口属性失败：Only the original thread ... Calling: DefaultDispatcher-worker-2
```

vc45 改为：`setTouchable()` 内部判断线程，非主线程就 `Handler(Looper.getMainLooper())` 投递；
`onSuspend` 还带一个 150ms 的 `CountDownLatch` 等待——**必须等窗口真的变成不可触摸再注入手势**，
否则手势会抢在防护生效之前落地。

验证：vc45 那轮 00:02 之后 `更新窗口属性失败` = **0 条**（vc44 段是 93 条）。

### 教训

> 凡是「改了 `WindowManager.LayoutParams` 却不生效、也不报错」的情况，
> 先看是不是在子线程调用的——`updateViewLayout` 只认创建视图的那个线程，
> 而它在 `runCatching` 里只是一条 warn，最容易被当成「偶发失败」忽略掉。
