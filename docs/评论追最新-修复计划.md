# 评论区「追最新」失效：现象、根因与修复计划

> 2026-10-28 制定。目标：**关注完一个人之后，下一轮挑的一定是「刚说话的人」**，
> 而不是屏幕上几分钟前的旧评论；同时把「列表到底有没有前进」变成可观测、可判定的信号。

---

## 1. 现象

用户口径：**「关注完第一个之后，评论区不会自己滚到最新，挑的人越来越旧」**。

当前实现（`app/src/main/java/com/example/dgg/engine/flow/FollowFromLiveFlow.kt`）的做法是：

1. 每轮开始前取「屏幕上最底那一行评论的文案」当锚点；
2. 调 `awaitNewestChanged()`（L373）：每 300ms 采一次，**等到最底那行换人**才算
   「列表已经推进到最新」，超时 6s 就降级——按「当前屏最新处」取人并写一条 W 日志；
3. 采集时按 `bottomY` 从新到旧排序，只在**最新 3 个可用候选**里加权随机。

这条链路在 2026-10-27 的真机上曾经生效（日志里出现过
`评论区底行已换：「三缺一：饼饼大厨说得好」→「Rattle🌻」`），但现在表现为「永远追不到最新」。
说明**判据本身太脆**：它把「列表有没有前进」押在「一个节点的文案变没变」上。

---

## 2. 已经被真机否掉的方案（不要再试）

| 尝试 | 结果 |
|---|---|
| 评论区 550px 纵向滑动（y1900→1350） | ❌ **直接切到下一个直播间**（主播都变了） |
| 评论区内 120px 短滑 | ❌ 不切房间，但评论行 y 完全没变 → 列表根本不可滚 |
| 反向 120px 下拖 | ❌ 同样无位移，也读不到更早的评论 |

结论不变：**铺满全屏的 ViewPager 会抢手势**，任何 `swipe` 都不能用来滚评论区。
所以「滚到最新」只能实现成「**确认列表自己滚到了最新**」——本计划要修的就是这个「确认」环节。

## 3. 代码层已确认的缺陷（不需要真机即可判定，必须修）

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| D1 | `newestRow()` 取「全屏 `bottom` 最大、文本含全角冒号」的节点，**不做任何过滤** | L349-362 | 只要屏上有一个**非评论**的含冒号节点压在更下面（输入区提示、礼物播报、公告、底部横幅），锚点就被永久钉死 → 每轮都判「没有新评论」→ 永远降级 |
| D2 | 判据是「**底行**换人」单信号 | L373-397 | 底行一旦被上述节点占住，即使中间几十条新评论刷过去也检测不到；反之同一人连发时又会被反复判为"新" |
| D3 | 等待期间 `snapshot(ttlMs = 0)` + 300ms 轮询 | L382、L761-762 | 一次全树遍历实测 1.4s，所以「300ms 轮询」实际是 1.7s/次；6s 窗口只有 3~4 个采样点。每轮还要再跑一趟 `collect()`（L503）→ **单轮 5~6 趟全树 ≈ 8 秒 CPU**，都花在等一个假信号上 |
| D4 | 唯一的"新"约束是 `NEWEST_WINDOW = 3`（L753） | L240-245 | 最新 3 个可用候选被 `handled` 过滤掉后，窗口**静默顺延**到更旧的行，没有任何"这行是多久以前发的"判断；对用户来说就是「又在补关注老观众」 |
| D5 | 降级只写一条 W 日志 | L173-178 | 悬浮窗上仍是「挑中 XXX」，用户看不出「追最新已经失效」，只能凭观感怀疑 |

D1 是最可疑的根因。注意 `newestRow` 的注释写着「刻意不套用任何业务过滤」——
当时是为了保证锚点是"屏幕上真实的最底一行"，但这个"真实"没有排除**根本不是评论**的节点，
而 `collectCandidates()`（L515-545）是有 `rowBottomLimit` + `MIN_ROW_HEIGHT` + `isValidNickname` +
`SYSTEM_MESSAGE_HINTS` 四道过滤的。**两处对"什么是评论行"的定义不一致，这就是 bug 的形状。**

## 4. 真机取证结论（2026-10-28 19:45，OPPO PLB110 / 抖音 40.8.0）

### 4.1 实验与数据

**E1 自然推进（`WATCH 90`，热闹房间，纯读取）**

| 观察 | 结果 |
|---|---|
| 列表是否自己滚 | ✅ 自己在滚，**2 秒内换 3~4 行** |
| 每屏行数 | 8~9 行，y 区间 `1398~2090`，行高 72（长评论 117） |
| 底行是不是真评论 | ✅ 是（`非：笑死了` / `李晨晨。：老了，腿脚不方便了`…） |
| 有没有节点压到输入栏（`limit=2188`） | ❌ 没有，`over=n` 全部正常 |
| 行数抖动 | ⚠️ 采样中 9 行曾掉到 7 行（插入动画/复用），**底行会短暂读不到** |

**真实运行日志统计（上一次会话 76 次挑人）**

| 指标 | 数值 |
|---|---|
| 「6 秒内没有新评论，退化为当前屏取人」 | **43 次 / 76 轮 = 57%** |
| 「最新窗口不足 3 人」（最新的人都处理过 → 窗口下滑） | 22 次 / 76 轮 = 29% |
| 挑中时在窗口内排第几新 | 第 1 新 48 次、第 2 新 19 次、第 3 新 9 次 |
| 总候选人数 | 多为 1~4 人（安静房间，一屏只读得到 4~6 行） |

典型失败序列（23:54:53 → 23:55:10，同一个房间）：

```
23:54:35 底行已换 → 采集 3 人 → 挑中 子栖@y1850
23:54:53 评论区 6000ms 内没有新评论 → 降级 → 挑中 大好小坏🐶@y2010
23:55:09 评论区 6000ms 内没有新评论 → 降级 → 只剩 尘哥@y2170 一人
```

### 4.2 结论：根因不是「锚点被钉死」，是「6 秒等不到就降级随便挑」

先前的头号假设 **H1（底行被非评论节点钉死）不成立**：E1 里底行始终是一行真评论，
且没有任何节点压在输入栏下方。**H2（列表被冻结）也不成立**：列表一直在自己滚。

真正的原因是 **H3 的变体**：安静房间里评论的自然间隔是 **25 秒级**（那份日志 51 秒只换了 2 次），
而等待窗口写死 6 秒 ⇒ **57% 的轮次必然走降级路径**，降级后就按"当前屏"取人；
最新的人都处理过时窗口再**静默下滑**（29% 的轮次）⇒ 挑到 `y=1805` 这种第 4~5 新的老行。

一句话：**判据没错，是"等不到就随便挑"这条退路把"追最新"废掉了。**

### 4.3 因此放弃的方案

- ❌ 「等不到就按当前屏最新取人」——它就是问题的来源，直接删除。
- ❌ 「6 秒硬超时」——保留超时概念，但改成"等到出现为止"，只保留一个 5 分钟的兜底。
- ❌ 自动换房间——用户明确否决，不做。

### 4.4 补充取证：评论区会「脱离底部」（19:57 追加）

E1 是在**刚进直播间、还没点过评论**的前提下做的，那时列表确实自己在滚。
但真正跑流程时每轮都要点评论行，之后列表就**停住了**——2 分钟内 6 行一字未变，
同时底部多出一个浮标：

```
[54,2107][299,2160] Button text="99+条新消息"
```

**这就是"刷新评论/回到最新"的唯一入口**（E1 之所以没看到，是因为当时列表还在底部）。
点它 3 秒内列表就跳到最新，本次实测：

```
20:01:43 评论区未跟进最新，已点「99+条新消息」回到最新
20:01:47 等到新评论：等了 4s，屏上 6 行、首见 6 行、可用 6 人
```

不点它会干等 **123 秒**才自己恢复（19:53 那次的实测值），这就是"关注完一个就追不到最新"的
直接原因。⇒ 修复里加了 `jumpToNewest()`：等待超过 12 秒仍无新评论时，找「N条新消息」浮标并点它
（找不到就继续等，**绝不盲点坐标**）。

## 5. 实施方案（已按此实现）

### P0-1 判据换成「行级首见」

`seenRows: HashMap<行文案, 首次见到时刻>` 跨轮保留。一行评论**第一次出现**就算"列表刚推进到它"：

```kotlin
val fresh = seenRows.put(key, now) == null   // key = 整行文案（昵称 + 正文）
rows++          // 屏上合法评论行数（判断"读不读得到"）
if (fresh) freshRows++
if (!fresh) { skippedSeen++; continue }      // 非首见的行不进候选
```

为什么按**行**而不是按人：已关注过的人又发了新评论，列表一样前进过，
按人判断会把这种轮次误判成"没动"；按行判断两个方向都不出错。

同时删掉 `newestRow()` / `awaitNewestChanged()` / `anchor` 三个东西 ——
"底行换人"这个信号在 E1 里被证明会抖动（9 行采样时掉到 7 行，底行短暂读不到），
既会误报"已推进"也会漏报。

### P0-2 没有新评论就等，**绝不降级下滑**

```kotlin
while (true) {
    val scan = scanOnce(...)          // 唯一一次全树遍历
    if (scan.candidates.isNotEmpty()) return scan
    if (scan.rows == 0 && ++emptyRounds >= MAX_DRY_ROUNDS) throw 定位失效
    if (waited >= STALL_ABORT_MS) throw "5 分钟没有新评论"
    ctx.publish("等新评论 12s（屏上 9 行都已处理）")
    ctx.settle(FRESH_POLL_MS)         // 分片等待，暂停/停止立刻生效
}
```

关键变化：**候选只来自首见的行**，所以窗口不会再因为"最新的人都处理过"而下滑到旧行。
代价是安静房间的吞吐降为「一条新评论 = 关注一个人」，这是"只关注最新"的必然结果，
也是用户明确选择的行为。

### P0-3 等待与采集合并成一趟

旧实现每轮 5~6 趟全树（底行探测 3~4 趟 + 采集 1 趟）；现在等待期间**每次只跑一次采集**
（本来就是需要的），轮询间隔 300ms → 800ms（低于一次遍历耗时 1.4s 的轮询没有意义）。

### P1 可观测性

- 悬浮窗/通知栏：等待时显示「等新评论 12s（屏上 9 行都已处理）」，读不到评论时显示
  「读不到评论行（2/4）」，不再是"看起来卡住"。
- 启动日志改成 `扫描（冒号切分兜底）：原始 5 → 评论行 9（首见 3）→ 可用新人 3`，
  排除项补 `非首见 N`。
- 结束日志补「其中 N 轮为新评论等待过，累计 Xs」。

### 明确不做

- ❌ 自动换房间（用户否决）
- ❌ 超时降级到当前屏取人（正是本次要修的病根）
- ❌ 任何纵向滑动评论区的代码路径（会切直播间）
- ❌ 复活动作（`ACTION_SCROLL_FORWARD` 等）—— E1 证明列表本来就在自己滚，不需要

## 6. 验收标准（真机，必须逐条对上）

| 项 | 期望 |
|---|---|
| 日志判据 | 不再出现「6s 内没有新评论…退化为当前屏取人」；改为 `扫描：评论行 9（首见 3）→ 可用新人 3` |
| 挑人正确性 | 连续 5 轮「挑中」的 `y` 都落在当时**最新 3 行**内，且没有「窗口不足 3 人」还继续挑旧行的情况 |
| 安静房间 | 出现「等新评论 30s（屏上 9 行都已处理）」，而不是挑老观众；5 分钟无新评论才中止 |
| 遍历开销 | 单轮最多 3 趟全树（旧实现 5~6 趟） |
| 不回归 | 关注成功率、取关防护（先判已关注再判可关注）、花钱守卫、弹层关闭全部保持 |
| 不许出现 | 任何纵向滑动评论区的代码路径；任何"等不到就挑当前屏"的分支 |
