# 关注记录与人数口径 — 修改计划

> 目标版本 **vc62 / 1.4.32**。当前基线 vc61 / 1.4.31（已发布）。
> 用户需求原文：「已关注人数，隔天后没有刷新；增加关注记录，时间，主播名字，被关注人的名字」。

---

## 一、现状核查（结论先放前面）

### 1.1 「已关注人数」到底是哪个数

全仓只有一处：**悬浮窗上的「已关 N」**（`view_float_status.xml` 的 `floatKnown`）。

```kotlin
// FloatWindowService.kt:703
b.floatKnown.text = "已关 ${store.knownCount()}"

// FollowedStore.kt:56
fun knownCount(): Int = names().size   // 去重名单 followed_names 的大小
```

`knownCount()` 是**历史累计去重名单的大小**，设计上：
- 永不清零（清掉会导致重复关注同一批人）；
- 上限 `MAX_NAMES = 3_000`，超出后先进先出淘汰。

**所以跨天它本来就不会变。** 这不是 bug，是「累计口径」被放在「今日 N」旁边、没有任何标注，读起来像当日数。

### 1.2 「今日 N」的跨天逻辑是对的

```kotlin
// FollowedStore.kt:126
fun todayCount(): Int {
    if (prefs.getString(KEY_DAY, null) != today()) return 0   // 读时清零
    return prefs.getInt(KEY_DAY_COUNT, 0)
}
```

跨天后读即返回 0，`bumpToday()` 会先 rollover。**这一段不需要改**，只需要在界面上把两个口径分开写清楚。

### 1.3 真正缺的东西

- **主界面里没有任何关注统计**（`MainActivity` 全文没有 `knownCount`/`todayCount`）。用户在 App 内看不到"今天关注了几个"。
- **没有任何明细**：悬浮窗点开「已关」只有一个纯昵称列表（`allNames()`），**没有时间、没有主播、没有日期分组**。所以"昨天是谁、在哪个直播间"永远查不回来。
- **命名会误导**：「已关」三个字对老用户是"已关注人数"，但它其实是"本机累计关注过的人数"。

### 1.4 另一台设备上的现象（已取证）

`R-20261102-D029A4`（今天 20:05，1.4.30，新设备首次安装）27 行日志里全是初始化 + 检查更新，**没有任何关注记录**。

说明：**数据完全在本地**（SharedPreferences + files），换设备/重装不会迁移。新设备上 `knownCount()` 必然是 0，老设备上是 13 —— 如果对照两台手机，会看起来像"数字没刷新"，实际是两份独立的本地数据。

## 二、三项决策（已确认）

| 项 | 决定 |
|---|---|
| 人数口径 | **今日 N · 累计 M** 并排显示 |
| 记录入口 | **主界面入口 + 独立记录页** |
| 保留范围 | **全部保留**（不淘汰） |

---

## 三、方案

### 3.1 存储：追加式文件，不用 SharedPreferences

「全部保留」否掉了 SP 方案：SP 每次写入要全量重写，跑一年 7 万条 = 4 MB，`apply()` 每次序列化 4 MB 不可接受。

```
files/follow_records.tsv        每行一条，tab 分隔
<epochMillis>\t<主播昵称>\t<被关注人昵称>\t<kind>
```

- 写入：`FileOutputStream(file, append = true)`，O(1) 追加。
- `kind` 预留：`F` = 真正关注成功（本版只写这一种）；`A` = 打开时已关注、被跳过；`P` = 私密账号。留着以后扩展不用改格式。
- 昵称里不含 `\t` / `\n`（抖音昵称不允许），写入前仍做一次替换兜底。
- **写入必须 try-catch 包住**：记录失败只写日志，绝不能让关注主流程抛异常。

### 3.2 累计计数：SP 计数器，避免每次读文件

```kotlin
// FollowedStore 新增
private const val KEY_TOTAL = "total_followed"     // 只增不减
fun totalFollowed(): Int                            // 主界面/悬浮窗 O(1) 读
```

- `markFollowed()` 里同步 `+1`。
- **首次升级播种**：`total_followed` 缺失时用 `knownCount()` 初始化，否则老用户会看到累计从 13 突然变 0。用 `KEY_TOTAL_SEEDED` 标记只播一次。
- 记录页里的「共 K 条」以**文件真实行数**为准（打开时统计一次），它与计数器差 1 说明某次写入时崩溃，不影响使用。

### 3.3 写入点

`FollowFromLiveFlow.kt:305`（关注成功后）是**唯一**调用 `markFollowed` 的地方，改造后：

```kotlin
store.markFollowed(nickname)   // 内部：写名单 + 计数器 +1 + 追加一行记录
```

主播昵称在这一刻从 `RoomStore.get(ctx.appContext).lastAnchor` 取——它由每轮 `anchorFromSnapshot()` 刷新（零额外遍历成本），且 M2 不切房，值稳定。取不到（`null`）就写 `-`，不做猜测。

> 为什么不给 `markFollowed` 加参数从流程传：流程拿 anchor 要再走一遍快照，而 `RoomStore.lastAnchor` 已经是同一份数据的缓存值，在 Store 内部读更省、也不会漏传。

### 3.4 界面

#### (a) 自动关注页加一行入口（开始按钮上方）

```
┌─────────────────────────────────────┐
│ 关注记录          今日 12 · 累计 348  › │
└─────────────────────────────────────┘
```

- 整行可点，右侧 `›`。
- 数字在 `onResume` 与每次任务结束后刷新（`render()` 里已有 `invalidate` 时机）。
- **高度预算**：约 **56dp**（一行 + 卡片 padding）。1.3 倍字号下文本「今日 12 · 累计 348」≈ 8 个 CJK + 6 个数字 ≈ 460px，卡片可用 912px，余量充足，**不需要缩短文案**。

#### (b) 新增 `FollowRecordsActivity`

```
┌─────────────────────────────────────┐
│ ‹ 关注记录                           │
├─────────────────────────────────────┤
│  今日 12    累计 348    共 348 条      │   ← 固定统计条
├─────────────────────────────────────┤
│  11月2日 · 12 人                      │   ← 日期分隔行
│  14:23  小明同学                      │
│          主播 小好                    │
│  14:21  阿强                          │
│          主播 小好                    │
│  ...                                 │
│  11月1日 · 2 人                       │
│  12:44  子豪                          │
│          主播 星野                    │
└─────────────────────────────────────┘
```

- **两行一条**：第一行「时间 + 被关注人昵称」，第二行小字「主播 xxx」。三列挤在一行在 1.3 倍字号下必然被压缩（vc60 已知坑：一行两组内容会把 EditText 从 180px 挤到 131px）。
- 用 **`ListView` + `BaseAdapter`**（framework 自带，零新依赖；两种 view type：日期头 / 记录行）。
  - 不引 RecyclerView：项目现在没有这个依赖，material 传递依赖版本不可控，ListView 几万条也撑得住。
- **倒序读取**：从文件尾部按 64 KB 块向前读，凑够 300 条就停 → 首屏只读最后几十 KB，不受总条数影响。
- 滚到底部自动追加下一批（`onScroll` 到 `lastVisible >= total - 5` 时加载）。
- 日期分组与每日小计在**加载那一批时**就地聚合；跨批次的同一天会分成两个头（可接受，因为倒序加载天然按天切）。

### 3.5 文案修正

- 悬浮窗「已关 N」→ **「累计 N」**，与 App 内统一（"已关"三个字是这次误解的源头）。
- 悬浮窗「今日 N」保留不变（口径正确，只是以前没和"累计"并排过）。

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 「全部保留」导致文件无限增长 | 记录是纯文本追加，7 万条约 4 MB；读取走倒序分页，只读尾部。**不做淘汰**是用户明确要求 |
| 记录写入抛异常拖停关注 | 全包 try-catch，失败只 `LogStore.w`，不改变关注结果 |
| 老用户升级后「累计」从 13 变 0 | `total_followed` 首次缺失时用 `knownCount()` 播种 |
| `knownCount()` 上限 3000 导致累计封顶 | 累计改用独立计数器，不再受名单上限影响 |
| 主播昵称取不到 | 写 `-`，界面显示「主播 —」，不猜不补 |
| 1.3 倍字号下入口行被挤 | 文案已按 460px / 912px 预算，无需缩短 |
| 记录页首次打开慢 | 倒序只读尾部 64 KB 块，300 条即停 |

## 六、验收清单（真机）

1. 升级后打开自动关注页：「关注记录 今日 0 · 累计 N」；N 与旧版「已关」一致（播种正确）。
2. 跑 1 个关注（目标 1、间隔 5~10 秒）：记录页出现「今天 · 1 人」，行内**时间 / 被关注人 / 主播**三项齐全。
3. 跨天验证：把设备日期调后一天 → 悬浮窗与入口变「今日 0 · 累计 N+1」，记录页旧记录仍在（**不淘汰**）。
4. 断网/无主播名场景：`anchor` 为 null 时显示「主播 —」，不崩、不空行。
5. **1.3 倍字号**：入口行与记录页两行一条均不挤压、不溢出卡片右边界（996px）。
6. 记录页滚到底：自动追加下一批，不卡顿、不重复。
7. 悬浮窗文案已是「累计 N」而非「已关 N」。
