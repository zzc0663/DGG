# 「开始关注」确认弹窗：只留关键信息 + 加粗强调（修改计划）

> 状态：**待批准，未改代码**
> 目标：`MainActivity.confirmFollow()` / `confirmLiveInteract()` / `confirmNurture()` 三个弹窗
> 涉及文件：`ui/MainActivity.kt`、新增 `ui/PromptText.kt`

---

## 1. 现状与问题

三个确认弹窗都是「5 段长文」，平均 150~200 字：

`confirmFollow()` 现在的正文（vc37）：

```
开始前请确认：你已经在抖音里手动进入目标直播间，并停在直播间画面。

脚本会循环执行：读直播间评论 → 随机挑一个人 → 点开资料卡 → 关注 → 回直播间，
每次关注之间间隔约 18 秒（叠加 ±30% 抖动）。

达到「目标关注数量 200」或「今日上限 200」时停止。

不会私信、不会点赞、不会刷评论，也不会自己去找直播间。

运行期间屏幕会被自动操作，请勿手动干扰；随时可用悬浮窗或通知栏停止。
```

问题有三个：

1. **前提被淹没**。「先手动进直播间」是最容易踩、后果最重的一条（没进 → 流程空转），
   却和「不会私信」这类说明混在同一段里，用户点「开始」时基本不会读第 4 段。
2. **关键参数不显眼**。目标 200 / 上限 200 / 间隔 18 秒散落在两句里，用户想确认
   「我这次设的是不是对」得逐句找。
3. **过程描述是给开发者看的**。「读评论 → 挑人 → 点资料卡 → 关注 → 回直播间」
   对用户决策没有价值——他要决定的是「现在能不能开始」。

---

## 2. 改法：三条式（前提 / 参数 / 边界），只留能影响决策的信息

版式统一为：

```
· **前提**（不符合就会失败的那一条）
· 参数（本次运行的实际数值，数值本身加粗）
· 边界（不会做什么 / 怎么停）
```

规则：

| 规则 | 说明 |
|---|---|
| 最多 4 行 | 超过就再删，弹窗高度要能一眼看完 |
| 每行以 `·` 开头 | 不再用大段自然段 |
| 粗体只给两类 | ① 前提句；② 具体数值。一行最多一处 |
| 删掉过程描述 | 「读评论→挑人→点资料卡」这类不进弹窗 |
| 参数实时取值 | 与 `store.current` 一致，改设置后重开弹窗要跟着变 |

## 3. 三个弹窗的新文案（草案，请审阅措辞）

### 3.1 开始关注（`confirmFollow`）

标题：`开始关注`

```
· 请先手动进入目标直播间，停在直播画面上
· 目标 200 人 · 今日上限 200 · 每次间隔约 18 秒（±30% 抖动）
· 只做关注：不私信、不点赞、不刷评论，也不会自己找直播间
· 随时可用悬浮窗或通知栏停止
```

加粗：第 1 行整句；第 2 行的 `200`、`200`、`18 秒`。

### 3.2 开始直播互动（`confirmLiveInteract`）

标题：`开始直播互动`

```
· 请先手动进入目标直播间，停在直播画面上
· 每 30~60 秒发 1 条（预设评论）
· 每 10 条赞 5~10 次 · 申请连麦
· 无总量目标，手动停止；遇「评论过快」类提示立刻停机
```

- 第 2 行文案按 `commentMode` 二选一：`预设评论` / `复制最新评论`
- 第 3 行「申请连麦」仅当 `micRequest = true` 时显示，否则整段去掉
- 加粗：第 1 行；`30~60 秒`、`10 条`、`5~10 次`

### 3.3 开始养号（`confirmNurture`）

标题：`开始养号`

刷视频模式：

```
· 抖音已打开，停在有右侧点赞按钮的视频画面
· 每条停留 1.5~90 秒（多数 2~12 秒），每 20~40 屏休息一次
· 点赞 20% · 收藏 10% · 3 条文案标签生效
· 运行 60 分钟后自动停；**不关注任何人（不涨粉）**
```

首页连播模式（`NURTURE_HOME`）第 3 行替换为：`· 只刷视频，不做任何互动（不点赞、不收藏）`

加粗：第 1 行；`1.5~90 秒`、`20%`、`10%`、`60 分钟`、末行的「不关注任何人（不涨粉）」。

> 「垂直养号」未开放的分支（`toast`）保持原样，不动。

## 4. 技术实现

### 4.1 加粗：`**…**` 标记 → SpannableString

新增 `ui/PromptText.kt`：

```kotlin
object PromptText {
    /**
     * 把 `**xx**` 解析成粗体。用标记而不是在调用处手拼 SpannableString：
     * 三段文案共 10 余处粗体，手拼 Span 下标极易错位且改文案就要重算。
     * 文案里本来没有星号，不存在歧义。
     */
    fun of(text: String): CharSequence
}
```

实现要点：
- 正则 `\*\*(.+?)\*\*` 逐个匹配，替换成去掉星号的子串 + `StyleSpan(Typeface.BOLD)`
- 用 `SpannableStringBuilder` 逐段 append，**不要**先拼好字符串再按偏移加 Span（偏移会随删星号漂移）
- 落到 `AlertDialog.Builder.setMessage(CharSequence)`（它内部就是 `TextView.setText`，原生支持 Span）

### 4.2 抽公共弹窗

`MainActivity` 里三个 `confirm*` 各写一遍 `AlertDialog.Builder(...)`，改为：

```kotlin
private fun showKeyConfirm(title: String, body: String, onStart: () -> Unit) {
    AlertDialog.Builder(this)
        .setTitle(title)
        .setMessage(PromptText.of(body))
        .setPositiveButton("开始") { _, _ -> onStart() }
        .setNegativeButton("取消", null)
        .show()
}
```

三个 `confirm*` 只负责**拼 body 字符串**（仍留在各自函数里，因为参数来源不同），
`setTitle/setMessage/按钮` 三行不再重复。

### 4.3 不改的部分

| 项 | 决定 |
|---|---|
| 标题文案 | 不动（「开始关注 / 开始直播互动 / 开始养号」） |
| 按钮文案 | 不动（「开始 / 取消」） |
| `showStartFailure` / `showActivationDialog` / `showUnavailable` | **本次不动**（不属于「开始提示」，改动面越小越好） |
| 弹窗样式（系统 AlertDialog） | 不动；项目强制 Light 主题，粗体在浅底上对比度足够 |
| 按钮自绘约定 | 不适用——这里沿用现有 AlertDialog，与全项目一致 |

## 6. 验收

真机（vc38）三个页签各点一次「开始服务」：

1. **弹窗按钮不超出屏幕**，正文 3~5 行、无需滚动即可看全；
2. 每段第一行（前提）**肉眼可辨为粗体**，参数里的数字也是粗体；
3. **参数与设置页一致**：把目标改成 50、间隔改成 6 秒，重开弹窗应显示 `50` / `6 秒`；
4. M3 关掉「申请连麦」后，第 3 行的连麦段消失；
5. M4 切到「首页连播」后，第 3 行变成「只刷视频，不做任何互动」；
6. 点「开始」仍能正常启动（`startFlow` 链路未动），点「取消」不启动。

## 7. 风险

| 风险 | 处理 |
|---|---|
| 文案里的 `·`/`%`/`~` 与全角半角混用 | 统一用半角数字 + 中文单位（`18 秒`），与现有设置页一致 |
| 粗体 Span 下标错位 | 用 `SpannableStringBuilder` 逐段 append，不做偏移计算 |
| 删掉「过程描述」后用户不知道脚本在干什么 | 主界面参数区已有流程说明；而且这些描述对决策无价值（见 §1） |
| 用户其实想要「更详细但排版更好」 | 本计划按「只提示关键信息」执行；如需保留细节，可把长文案挪到「帮助」弹窗，另开一次改动 |

### 踩到的一个 Kotlin 坑

`"$pace节奏"` 编译不过 —— **中文字符也是合法的标识符字符**，编译器把 `pace节奏` 当成一个变量名
（`Unresolved reference: pace节奏`）。必须写 `"${pace}节奏"`。
项目里凡是「变量紧贴中文」的字符串模板都要用花括号，别省。
