# 悬浮窗累计按天 + 按主播分组（悬浮窗 + 关注记录页）— 修改计划

> 目标版本 **vc63 / 1.4.33**。当前基线 vc62 / 1.4.32（已发布）。
> 用户需求原文：「悬浮窗的累计数量也跟天数刷新；然后悬浮窗的关注记录增加 某主播 后面跟关注人数
> 比如 主播 A 已关注 20 1 2 3 . 4 5 6 …20，主播 B 已关注 10 1 2 3 …10 这样」；
> 追加：「后台记录也都需要分组」。

---

## 一、现状

### 1.1 悬浮窗统计行（`view_float_status.xml`）

四格横向排列，每格 `layout_weight=1`，文字 `11sp`：

| id | 当前 | 值来源 |
|---|---|---|
| `float_session` | `本场 0` | `progress.followed`（本轮任务） |
| `float_today` | `今日 0` | `FollowedStore.todayCount()`（跨天归零） |
| `float_known` | `累计 N` | `FollowedStore.totalFollowed()`（**历史总数，只增不减**） |
| `float_reset` | `重置` | 清今日计数 |

用户要改的就是第三格 —— 它现在跨天不归零，与「今日」并排却不解释，容易被误读。

### 1.2 「已关名单」区（点按钮展开）

`float_names_box`（ScrollView，`maxHeight 150dp`）里只有一个 `float_names_list`（**单个 TextView**，`10sp`），内容是：

```
1. 小明同学
2. 阿强
3. 卷卷酱
──────────
以下 6 人打开时已关注，未重复关注：
· 夜色温柔
```

数据来自 `FollowedStore.allNames()` / `alreadyNames()` —— **只有昵称，没有主播、没有时间**。

### 1.3 有主播数据的只有一处

`data/FollowRecordStore`（vc62 建的）写的 `files/follow_records.tsv`：

```
<epochMillis> \t <主播昵称|-> \t <被关注人昵称> \t <kind>
```

⇒ 要按主播分组，**必须改从记录文件读**，不能再用 `allNames()`。

### 1.4 「关注记录」页现状（对应「后台记录」）

`FollowRecordsActivity` + `FollowRecordsAdapter`（ListView，两种 view type）：

```
[日期头] 2026年11月4日 · 今天
[记录] 14:23  小明同学
       主播 雪儿
[记录] 14:21  阿强
       主播 雪儿
[日期头] 2026年11月3日
...
```

分组加进来后要变成三层（日期 → 主播 → 条目），Adapter 需要第三种 view type。

## 二、五项决策（已确认）

| 项 | 决定 |
|---|---|
| 悬浮窗累计口径 | **累计 = 今日累计**（跨天归零）；原「今日」格改为**「剩余 X」** |
| 悬浮窗分组范围 | **只列今天**的记录 |
| 主播名 | 用记录里存的 `anchor`（不额外遍历） |
| 记录页结构 | **日期 → 主播 → 条目**（三层） |
| 记录页条目内容 | **时间 + 被关注人**（主播名只在组标题出现，不再逐条重复） |

### 为什么把「今日」改成「剩余」而不是让它重复

改完三格是：

```
本场 2        剩余 198        累计 2
```

- **本场** = 本轮任务关注了多少（任务重启会归零）
- **剩余** = 每日上限 − 今日已关（还能干多少，这是决定"要不要继续跑"的那个数）
- **累计** = 今日累计（跨天归零，满足"跟天数刷新"）

如果照字面把两格都留成今日数，界面上会出现两个一模一样的数字并排，等于白占一格。

## 三、方案

### 3.1 统计行（`FloatWindowService.render()`）

只改 `else` 分支（关注口径）。养号分支（赞/藏）与 M3 分支（评论数/上限）**一行不动**。

```kotlin
else -> {
    val today = store.todayCount()
    val limit = SettingsStore.get(this).current.dailyLimit
    b.floatToday.text = "剩余 ${(limit - today).coerceAtLeast(0)}"
    b.floatKnown.text = "累计 $today"          // 跨天自动归零（todayCount 读时比对日期）
}
```

### 3.2 名单区按主播分组

新增 `FollowRecordStore.todayGroups()`：

```kotlin
data class AnchorGroup(val anchor: String?, val count: Int)

/** 今天的记录按主播聚合，**保持首次出现顺序**（= 最近在场的在前，因为记录是倒序读的） */
fun todayGroups(): List<AnchorGroup>
```

实现要点：

- 从文件尾部倒读（复用现有 `readTailLines`），**读到日期不再是今天就停**，
  不扫全文件。单日上限 200 条，读 300 条足够。
- `anchor` 为 `null`（当时读不到主播名）归入一组，显示为「未识别主播」。
- 计数口径与统计行一致：只算 `kind == F`（真正关注成功）。

渲染（`onToggleNames()`）：

```
主播 雪儿 · 已关注 3
1 2 3
主播 用户 · 已关注 2
1 2
未识别主播 · 已关注 1
1
──────────
今天打开时已关注、未重复关注：4 人
```

- 每组的数字是**组内序号**（1…N），与用户给的示例一致。
- 「打开时已关注」那批**只给汇总数字，不列明细** —— 它们不计入「已关」，逐条列出会让名单翻几倍。
- 今天一条记录都没有时，退回原提示「今天还没有关注过任何人」。

### 3.3 数据可用性（必须说明）

`follow_records.tsv` 是 **vc62 才开始写的**。因此：

- vc62 之后关注的每一条都有主播名，能正确分组；
- vc62 之前关注的人（本机升级时的那批，用旧名单播种）**没有记录行**，不会出现在分组里。

这是数据断代，不是 bug。统计行的「累计 / 剩余」用 `todayCount()`，不受影响。

### 3.4 关注记录页改成三层结构

目标形态：

```
[日期头]  2026年11月4日 · 今天                      共 12 人
[主播头]  主播 雪儿 · 已关注 8
[记录]    14:23  小明同学
[记录]    14:21  阿强
[记录]    13:52  张三
[主播头]  主播 用户 · 已关注 4
[记录]    13:05  李四
[日期头]  2026年11月3日                             共 2 人
[主播头]  主播 星野 · 已关注 2
[记录]    23:12  子豪
```

#### 关键约束：主播头的「已关注 N」必须是**当天该主播的总数**

不能做成"连续块计数"。原因很实际：一天里用户可能跑多次任务
（房间 A 关注 8 个 → 换到房间 B 关注 4 个 → 又回房间 A 关注 3 个），
流式插入会把 A 拆成「8」和「3」两块，用户看到的就不是「A 已关注 11」。

⇒ **以"天"为聚合单位**，不是以"页"为单位。

#### 加载逻辑（按天对齐）

现有分页是 300 条/页。改成：

```kotlin
val page = store.read(offset, PAGE_SIZE)
val days = page.groupByOrdered { dayKey(it.ts) }        // 保持天的时间顺序
val completeDays = if (page.size < PAGE_SIZE) days      // 读到文件头，全部完整
                   else days.dropLast(1)                // 最后一页可能截断当天，留到下轮
// 只渲染 completeDays；offset 推进到"不完整那天"的第一条
```

- 一天最多 200 条（每日上限默认 200），300 条/页通常能覆盖一整天，绝大多数情况一次就完整。
- 当天跨页时（用户把每日上限调到 300 以上），这一天会**推迟到下一页才渲染**，
  不会出现"同一天同主播被拆成两块、数字偏小"的错误。

#### 排序

- 日期：时间倒序（今天在最上）
- 主播：按**当天最后一次关注的时间倒序**（最近活跃的直播间在前）
- 条目：时间倒序（现有行为）

#### 条目不再重复主播名

`item_follow_record.xml` 删掉 `tv_anchor` 那一行，只保留「时间 + 昵称」。
`ItemRecordHolder` 同步去掉该字段。主播名提升到组标题，同一主播下不再连续重复十几行。

## 五、宽度与字号预算

统计行每格宽度 ≈ `(面板宽 − 内边距) / 3`，面板约 320dp ⇒ **每格约 90dp**。

| 文案 | 字符 | 1.0× 估算 | 1.3× 估算（CJK≈16px/字、数字≈9px） |
|---|---|---|---|
| `本场 2` | 3 CJK + 1 数字 | ~46dp | ~72px |
| `剩余 198` | 2 CJK + 3 数字 | ~44dp | ~68px |
| `累计 12` | 2 CJK + 2 数字 | ~40dp | ~62px |
| 极端 `累计 200` / `剩余 0` | — | ~48dp | ~78px |

1.3× 下最长约 78px，格宽约 247px（90dp×2.75），**余量充足**，无需缩短文案。

⚠️ 仍需真机按 1.3 倍字号截图核对一次（vc60 那次「一行两组内容把输入框从 180px 挤到 131px」就是没算宽度）。

名单区 `maxHeight 150dp` / `10sp`：一行约 16dp ⇒ 约 9 行可见，分组多时滚动（ScrollView 已支持）。

### 记录页

| 元素 | 宽度估算（1.3×，卡片可用 912px） |
|---|---|
| 主播头 `主播 雪儿 · 已关注 8` | 6 CJK + 1 数字 ≈ **160px** |
| 极端 `主播 用户12021052842 · 已关注 12` | ≈ 420px，仍在 912px 内（超出部分 `ellipsize=end`） |
| 条目 `14:23  小明同学` | 时间列 44dp + 昵称自适应，昵称超长走省略号 |

去掉条目里的主播行后，每条高度从约 62dp 降到约 44dp，同样一屏能多显示约 40%。

## 六、风险

| 风险 | 对策 |
|---|---|
| 主播名不完整（`contentDescription` 被抖音截断，如只到「用户」） | 同名会被合并成一组。**如实显示记录里的值**，不猜；已知限制见 §3.3 |
| 分组把「打开时已关注」的人也列出来 | 只统计 `kind == F`，那批只给汇总数字 |
| 一天关注 200 条导致名单很长 | 每组内序号单行折行显示；名单区本身可滚动，不撑破面板 |
| 从文件读记录让展开变慢 | 只读尾部 64KB 且读到非今天即停；实测量级 < 10ms |
| 与主界面入口行的「今日 N · 累计 M」口径不一致 | **主界面不动**（那里是记录页入口，历史累计有意义）。若也要统一，另开一项 |
| **记录页跨页把一天拆成两块**（同主播数字偏小） | 加载改成"按天对齐"：不完整的那天推迟到下一页渲染（§3.4） |
| 记录页首屏变慢（要等一整天才渲染） | 只在"当天跨越 300 条页边界"时才推迟；默认日上限 200，正常一次就完整 |

## 七、验证清单（真机）

### 悬浮窗

1. 跑 2 个关注 → 三格：`本场 2` / `剩余 198` / `累计 2`。
2. 点开名单 → 「主播 xxx · 已关注 2」+ 一行 `1 2`；两个主播各 1 个则分成两组。
3. 改系统日期到明天 → 三格变 `本场 0` / `剩余 200` / `累计 0`，名单区「今天还没有关注过任何人」。
4. 点「重置」→ 剩余回到 200、累计归 0（名单不变，去重照旧）。
5. 1.3 倍字号：三格不换行不截断；名单区不撑破 150dp。
6. 养号与「只跑直播互动」下，那两格仍是「赞/藏」「今日评论数/上限」，未被误改。

### 关注记录页

7. 三层结构正确：日期头 → 主播头 → 条目；条目只有「时间 + 昵称」，不再重复主播名。
8. **同一主播当天两次任务要合并计数**：房间 A 关注 2 → 房间 B 关注 1 → 回 A 关注 1，
   A 应显示「已关注 3」而不是两块（这是 §3.4"按天对齐"的核心验收点）。
9. 日期头右侧「共 N 人」= 当天所有记录数（含未识别主播那组）。
10. 滚到底自动加载下一批，日期头与主播头不重复、不遗漏。
11. 1.3 倍字号：超长主播名走省略号，不撑破卡片右边界（996px）。

## 八、不在本次范围

- 主界面入口行的「今日 N · 累计 M」口径（保持历史累计）。
- 悬浮窗名单里显示被关注人的昵称（宽度放不下；昵称在「关注记录」页看）。
- 记录页的主播头折叠/展开交互（先做纯展示）。
- 跨主播的历史汇总（悬浮窗只做今天）。
