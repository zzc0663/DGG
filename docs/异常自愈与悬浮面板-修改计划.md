# 异常自愈与悬浮面板 —— 修改计划

> 2026-10-29 · 对应需求（用户原话）：
> 1. 「如果有异常 就悬浮窗提供暂停恢复按钮；跟手动暂停一个逻辑」
> 2. 「读不到直播间评论需要优化逻辑，这种异常就直接暂停，但是暂停期间也需要持续的尝试读取，读取成功自动恢复任务 或者人为恢复」
> 3. 「点到礼物界面和右上角的直播人数界面 需要自己尝试恢复」
> 4. 「终态时面板自动展开会盖住主界面参数区……要不要改成只有在抖音界面、而不是抖关关界面时才自动展开」→ **按建议改**
> 5. 「通知栏文字仍用 progress.brief()，终态那行已关注 0/260 也会过期……是否一并处理」→ **一并处理**
>
> 本文只是计划，不改代码。落地顺序见 §8。

## 1. 状态机：新增「等待恢复」

### 1.1 枚举与语义

```kotlin
enum class EngineState {
    IDLE, RUNNING, PAUSED, PAUSED_WAIT, STOPPED, STOPPED_ANOMALY, ERROR;

    // PAUSED_WAIT 必须是 active：任务没结束，前台服务不能退、悬浮窗不能按终态处理
    val isActive get() = this == RUNNING || this == PAUSED || this == PAUSED_WAIT

    val label get() = when (this) {
        ...
        PAUSED_WAIT -> "等待恢复"   // 4 个汉字，胶囊宽度够（现胶囊最长是「异常停止 0/200」）
    }
}
```

语义分工，不重叠：

| 状态 | 谁触发 | 任务协程 | 会不会自己恢复 |
|---|---|---|---|
| `PAUSED` | 用户点暂停 / 展开目标编辑 | 活着，挂起在 `awaitResume()` | 只能人工「继续」 |
| `PAUSED_WAIT` | **流程自愈逻辑**（读不到评论 / 浮层关不掉） | 活着，在 `RecoveryWait` 循环里 | **会**：探测成功自动恢复；也可人工「继续」 |
| `STOPPED_ANOMALY` | 风控命中 | 已结束 | 不可恢复（锁定决策：禁重试） |
| `ERROR` | 真做不到（抖音不在前台、定位配置缺失） | 已结束 | 可「重试」（P2） |

### 1.2 TaskEngine API

```kotlin
// 现有 pause()/resume() 保留（用户手动）
fun pause() = hold(EngineState.PAUSED, "已暂停")
/** 自愈暂停：与手动暂停共用 paused 标志，只是状态标签和 message 不同 */
fun pauseForRecovery(reason: String) = hold(EngineState.PAUSED_WAIT, reason)
private fun hold(state: EngineState, message: String) { ... }

fun resume() { paused = false; state = RUNNING; message = "已恢复" }   // 两种暂停都走它

/** 供 Flow 判断「用户是否已经手动恢复」 */
val isPausedNow: Boolean get() = paused

// P2：只对 ERROR 开放的「重试」
fun rememberFlow(flow: Flow)          // start() 里存 lastFlow（三个 Flow 都无可变字段，实例可复用）
fun restartLast(context: Context): Boolean
```

### 1.3 FlowContext 新增（沿用「注入回调」风格，Flow 仍碰不到引擎内部）

```kotlin
class FlowContext(
    ...,
    private val pauseAuto: (String) -> Unit,
    private val resumeAuto: () -> Unit,
    private val pausedNow: () -> Boolean,
    private val lastAbort: (String) -> String    // 可选：把中止原因写进 message
) {
    fun pauseForRecovery(reason: String) = pauseAuto(reason)
    fun resumeFromRecovery() = resumeAuto()
    fun isPaused(): Boolean = pausedNow()
}
```

### 1.4 按钮 / 颜色矩阵（三处渲染必须一致）

| 状态 | 悬浮窗 `floatToggle` | 悬浮窗 `floatFinish` | 主界面 `btnStartService` | 状态点 | 通知栏 |
|---|---|---|---|---|---|
| `RUNNING` | 暂停 | 结束 | 暂停 | 绿 | 常驻 |
| `PAUSED` | 继续 | 结束 | 继续 | 琥珀 | 常驻 |
| `PAUSED_WAIT` | **继续** | 结束 | 继续 | 琥珀 | 常驻 |
| `STOPPED` / `ERROR` | 结束（P2 时 `ERROR` → 重试） | 关闭 | 开始服务 | 红 | 已撤 |
| `STOPPED_ANOMALY` | **不显示**（绝不给重试入口） | 关闭 | 开始服务 | 红 | 已撤 |

> 改 `render()` 时注意现有写法 `if (progress.state == PAUSED) "继续" else "暂停"`，必须显式列出两种暂停态，否则 `PAUSED_WAIT` 会错显示成「暂停」。

## 2. 读不到评论 → 自愈暂停（核心）

### 2.1 现状为什么不好

```kotlin
// FollowFromLiveFlow.awaitFreshScan
if (scan.rows == 0) {
    emptyRounds++
    if (emptyRounds >= MAX_DRY_ROUNDS) throw FlowAbortException("连续 4 次读不到直播间评论…")
}
```

真机场景里 `rows == 0` 的成因有三类，**只有一类是真故障**：

| 成因 | 现在 | 应该 |
|---|---|---|
| 误触打开了礼物面板 / 观众列表（浮层盖住评论） | 等 4 轮 ≈ 8s 后中止 | 按 back 关掉，恢复正常 |
| 抖音正在加载/转场、评论区被"加载中"占位 | 同上，容易误杀 | 等一下自己就好 |
| `live_comment_line` 真的和当前版本不匹配 | 正确的中止 | **不允许悄悄中止**：暂停 + 持续重试，让人来判断 |

### 2.2 新流程

`awaitFreshScan` 里把「中止」换成「进入自愈等待」：

```kotlin
if (emptyRounds >= MAX_DRY_ROUNDS) {
    emptyRounds = 0
    // 先在暂停前做一次浮层恢复尝试，能自己解决就别惊动用户
    if (!RecoveryWait.tryRecoverOverlay(ctx)) {
        // 关不掉 → 暂停等待（任务不死）
        if (!RecoveryWait.waitForComments(ctx, probe = { scanOnce(...).rows })) return null
    }
    continue
}
```

`RecoveryWait.waitForComments`（新增 `engine/flow/RecoveryWait.kt`）：

```
pauseForRecovery("读不到直播间评论，等待恢复（已暂停，自动重试中）")
loop:
    if stopped → return false
    if !isPaused() → log「用户手动恢复」→ return true          // 人为恢复优先
    rows = probe()                                            // 只读 snapshot，绝不点击
    if rows > 0 → log「已恢复读取（共等待 Ns）」; resumeFromRecovery(); return true
    if 需要 → tryRecoverOverlay(ctx)                           // 识别到浮层才 back()
    guard()                                                    // 风控检查照旧，命中即停
    delay(退避 3s→6s→10s→15s 封顶)
    每 30s publish 一次「等待恢复：已等待 N 分钟（读不到评论行）」
```

要点：

- **暂停期间只读不点**（引擎约定 3 的例外只有「恢复性动作 `back()`」，且必须页面判定明确识别到浮层）。
- **不设放弃上限**（用户明确要求「暂停期间持续尝试」）。用退避控制开销：3s/6s/10s/15s。
- 恢复后**不清空** `seenRows`/`handled`：评论列表可能整屏换过，清空会导致重复关注；首见判定会自然把这些行当新行处理。
- 风控优先：探测循环里仍 `guard()`，命中就 `AnomalyStopException`，穿透到引擎 → `STOPPED_ANOMALY`（绝不因"正在等待"而跳过风控）。
- `STALL_ABORT_MS`（5 分钟无新评论）保持现状：那是「房间安静」，不是「读不到」，如实结束并提示换房。**可选**（P2）同样改成暂停。

### 2.3 M3 直播互动

`buildComment` 连续失败 `MAX_CONTENT_FAILS` 次（"拿不到可发的评论内容"）现在也是直接中止。**同样改为自愈暂停**（复用 `RecoveryWait`，probe = 读取最新评论是否成功）。发送失败（`MAX_SEND_FAILS`）不打这个补丁——那可能是账号被限评，属于该停的真异常。

## 3. 浮层自愈：礼物面板 / 观众列表

### 3.1 现状

`LiveGuard.detectOverlay` 只在**页面判定为 UNKNOWN 时**，用三个精确文案 `赠送 / 资料卡 / 发送` 嗅探。
「在线观众」列表根本不在这三个里，且 `PageState.USER_LIST` **有枚举、无 JSON 规则** ⇒ 判定 UNKNOWN ⇒ 干等。

> ⚠️ 上面的 `value` 是**根据现有日志与文档推的候选值，必须真机 dump 核对**（§6.1 给了取证命令）。
> 文案错了不会误点：识别不出就是「识别不出」，最坏退回自愈暂停。

`LocatorConfig` 新增：

```kotlin
data class OverlayRule(val key: String, val label: String, val threshold: Int, val features: List<Feature>)
data class LocatorConfig(..., val overlays: Map<String, OverlayRule> = emptyMap())
```
解析要点复刻 `pages`：跳过 `_` 前缀键、`optJSONObject()`、`maxScore < threshold` 直接丢弃并告警。缺 `overlays` 段 → 用内置 3 条（即现有 `赠送/资料卡/发送`），保证旧配置文件不炸。

### 3.3 识别与恢复

```kotlin
// LiveGuard
suspend fun ensureOnAir(...) {
    ...
    // ③ 读不出页面时，先试「浮层恢复」，再考虑等
    recoverOverlay(ctx)?.let { ... }
}

/** 返回关掉的浮层名；null = 屏幕上没有可识别的浮层 */
suspend fun recoverOverlay(ctx: FlowContext): String? {
    if (ctx.actions.isDouyinForeground().not()) return null      // 不在抖音绝不按返回
    val facts = ctx.actions.snapshot(ttlMs = 0)
    val hit = config.overlays.values.firstOrNull { rule ->
        rule.features.count { f -> facts.any { actions.matchesFacts(it, f.target) } } >= rule.threshold
    } ?: return null
    // 只在「当前判定不是直播间」时才动手：浮层必须真的盖住了直播间特征
    if (ctx.detector.detect().page == PageState.LIVE_ROOM) return null
    LogStore.w(TAG, "识别到「${hit.label}」浮层（${score}/${hit.threshold}），按一次返回关闭")
    ctx.actions.back()
    return hit.label
}
```

**恢复动作只允许 `back()`**，理由写死在注释里：礼物面板里每一个可点控件都是「选礼物 / 赠送 / 充值」，`tapNode` 的 `PAID_HINTS` 只是最后一道保险，不能当作第一道。

`back()` 之后的处置（`awaitRoom` 再看一次）：

| 落点 | 处置 |
|---|---|
| `LIVE_ROOM` | 恢复成功，继续 |
| 直播频道预览页 | 点「点击进入直播间」（现有能力）——**可能进的是另一个房间**，日志必须如实写 |
| `HOME` / 其它已识别页 | **不抢**：不自动导航，转 `PAUSED_WAIT` 并提示「疑似退出了直播间，请手动回到目标直播间后点继续」 |
| 仍是 `UNKNOWN` | 再给 1 次 `back()`（最多 2 次），仍不行 → `PAUSED_WAIT` |

> 为什么退到「等待恢复」而不是直接中止：用户此时可能只是低头看了眼手机，房间还在，人回来点一下「继续」就能接着跑；直接中止等于让他从「开始服务」重来一遍（还要重新进房）。

## 4. 悬浮窗 / 主界面

### 4.1 终态展开条件（需求 4）

```kotlin
// FloatWindowService.observe()
if (sawActive && !progress.state.isActive) {
    // 抖关关自己在前台时不展开：面板纵向 405~1485，正好盖住参数区，
    // 用户想改参数还得先点 ⌃ 收起（2026-10-29 真机反馈）。
    // 结论在主界面底部状态条里已有，不需要再挡一遍。
    if (!AppVisibility.isUiForeground) setExpanded(true) else setExpanded(false)
}
```

新增 `ui/AppVisibility.kt`（object，`MainActivity.onResume/onPause` 维护计数）：

```kotlin
object AppVisibility {
    @Volatile var isUiForeground = false; private set
    fun onResume() { isUiForeground = true }
    fun onPause() { isUiForeground = false }
}
```
> 不用 `foregroundPackage()` 判断：终态常见于无障碍掉线/抖音被杀，这时节点树读不到，判定会失效。Activity 生命周期是本进程内最可靠的信息。

**双保险**：`MainActivity.onResume()` 里调 `FloatWindowService.collapseIfExpanded()`（同进程，加一个 `@Volatile var instance` 即可），用户从抖音切回抖关关时，任何还展开着的面板自动收起。

### 4.2 通知栏文字实时化（需求 5）

`EngineState.kt` 加一个扩展，三处统一：

```kotlin
/** 分母取「用户当前设置」：progress.target 是启动/上一轮 publish 的冻结快照 */
fun EngineProgress.withLiveTarget(liveTarget: Int): EngineProgress =
    if (target > 0) copy(target = liveTarget) else this   // target==0 = 流程声明「无总量目标」，不凑分母
```

- `ControlService.buildNotification` → `progress.withLiveTarget(SettingsStore.get(this).current.followTarget).brief()`
- `FloatWindowService.render` / `MainActivity.renderEngine` → 换用同一个扩展（现在各自手写了一遍，容易漏改）
- 终态那一行随之变成 `已关注 12/220`（当前设置值），不再是 `12/260`。
- 附加：终态时 `brief()` 前面已经有 `异常停止` / `等待恢复`，不会误导用户以为还在跑。

## 7. 风险与回滚

| 风险 | 影响 | 对策 |
|---|---|---|
| `PAUSED_WAIT` 被当成终态 | 前台服务退出、悬浮窗按终态收尾、任务假活 | `isActive` 必须包含它；`ControlService`/`FloatWindowService` 的判定全部走 `isActive`（现有代码已如此，逐处核对） |
| 自愈等待把「风控」也一起等过去 | 封号风险（最高优先级） | 探测循环里 `guard()` 保留在最前；命中即 `AnomalyStopException` → `STOPPED_ANOMALY`，绝不 resume |
| 无限等待让用户以为卡死 | 观感差 | 每 30s publish 一次等待时长；胶囊常显「等待恢复」；面板按钮是「继续」 |
| `overlays` 文案猜错 | 识别不出 → 退回自愈暂停（不会误点） | 先取证再写值；配置外置，改版只改 JSON |
| `back()` 把直播间退掉 | 用户要重新进房 | 浮层必须先「页面判定 ≠ LIVE_ROOM」才 back；最多 2 次；退出后不自动进陌生房间 |
| 终态不展开 + App 在前台 | 结论只看得到主界面状态条 | 状态条 `needAttention` 已覆盖 ERROR/STOPPED_ANOMALY，文案完整（含 reason） |

回滚：全部改动集中在 3 个提交（§8），任一阶段异常可单独 `git revert`；`overlays` 段缺失时行为等价于今天（内置 3 条）。

## 8. 落地顺序

- **P0（一次提交）状态与显示**
  1. `EngineState.PAUSED_WAIT` + `withLiveTarget` + 三处渲染/按钮矩阵 + `AppVisibility` + 终态展开条件 + 回 App 收起。
  - 这一阶段不动流程，先把「暂停/恢复/不挡参数区/通知栏」四条盘干净，可独立验收。

- **P1（两次提交）自愈**
  2. `RecoveryWait` + `TaskEngine.pauseForRecovery` + `FollowFromLiveFlow` 改判（读不到评论 → 暂停等待）。
  3. `overlays` 配置化 + `LiveGuard.recoverOverlay` + `LiveInteractFlow` 的 `MAX_CONTENT_FAILS` 分支。

- **P2（可选，看你要不要）**
  4. `ERROR` 终态的「重试」按钮（`STOPPED_ANOMALY` 永不提供，风控禁重试）。
  5. 「5 分钟没有新评论」也改成暂停等待（现在如实结束并提示换房，我认为现状更好，倾向不改）。

每个阶段做完都按 §6.2 跑对应项，并把真机日志片段补进 `docs/运行期容错与悬浮面板.md`。
