# 日志上报接口契约（给云端）

面向实现服务端的人。客户端代码是唯一权威：本文每条约束都能在
`app/src/main/java/com/example/dgg/data/log/` 下找到对应实现，标注在 §8 的对照表里。

> 版本：对应客户端 `versionCode=2 / versionName=1.1`。
> 产品决策（2026-10-28 用户明确要求）：**用户界面上不再有「查看日志」入口**，
> 点「日志」按钮 = 直接上传到云端。客户端没有本地日志浏览页，服务端必须承担
> 「存档 + 检索」的职责 —— 这是本契约存在的前提。

---

## 1. 一条接口

| # | 接口 | 谁调用 | 关键要求 |
|---|---|---|---|
| 1 | `POST /v1/log/upload` | 客户端点「日志」按钮 | HTTPS、UTF-8 JSON、快（客户端 10s 连接 / 20s 读超时）、**必须回 `reportId`** |

`reportId` 是这条链路唯一不可省的字段：用户报障时只会念这个编号，
客服靠它在云端定位日志。服务端**生成失败就不要返 200**（见 §5.2）。

---

## 2. 传输约定

| 项 | 约定 |
|---|---|
| 协议 | **HTTPS**。客户端 `network_security_config` 禁明文，仅放行 `127.0.0.1` / `localhost`（供 `adb reverse` 联调） |
| 方法 | 只 `POST`。没有 GET 查询接口（客户端不读历史日志） |
| 请求头 | `Content-Type: application/json; charset=utf-8`、`Accept: application/json`。**不发** `Authorization` / cookie / `Content-Encoding` |
| 请求体 | UTF-8 JSON，**不压缩**。客户端用 `setFixedLengthStreamingMode` 发送，`Content-Length` 准确 |
| 字符集 | UTF-8（无 BOM） |
| 时间戳 | 毫秒（`createdAt` / `uploadedAt` / `expiresAt`），与时区无关的 epoch |
| 大小 | 字节（`size`） |
| 重试 | **客户端不重试**。失败立刻告诉用户「再点一次」，不后台静默重推 |
| 幂等 | **没有幂等键**。用户连点两次 = 两份日志、两个 `reportId`，服务端按两次独立上报处理（要合并只能按 `deviceId + createdAt` 近似去重） |

> 为什么不用 multipart：正文上限 512 KB，JSON 完全塞得下；multipart 要在服务端多一条
> 解析分支、客户端多一套边界处理，换来的只是几十 KB 的编码开销。真要传原始文件
> （以后加截图/录屏）再单开一条接口，不要改这条。

## 3. 请求体

```
POST https://<host>/v1/log/upload
Content-Type: application/json; charset=utf-8
```

```json
{
  "app": "dgg",
  "deviceId": "9b68224bf2b9d6ba0d318c70c4739a85b92439abb4a091bf41429c729793001f",
  "versionCode": 2,
  "versionName": "1.1",
  "channel": "stable",
  "source": "file",
  "size": 183402,
  "truncated": false,
  "createdAt": 1761741234567,
  "content": "10-29 22:15:41.203 I/引擎 开始任务：自动关注\n10-29 22:15:42.887 I/页面 判定 LIVE_ROOM(权重 7)\n..."
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `app` | string | 是 | 固定 `dgg`。多产品线共用采集服务时用来分流 |
| `deviceId` | string | 是 | 64 位小写十六进制，`sha256("<ANDROID_ID>:<installUuid>:<packageName>")`。**不是明文 ANDROID_ID**，客户端不上传任何原始硬件标识（不采集 IMEI / MAC / 序列号）。同一设备多次上报可关联；清除数据或卸载重装会生成新的 `installUuid`，因此 `deviceId` 会变，服务端视为新设备 |
| `versionCode` | int | 是 | 客户端版本号。**排查时先看这个**：老版本报的故障可能早已修掉 |
| `versionName` | string | 是 | 形如 `1.1`，可能为空串 |
| `channel` | string | 是 | 当前固定 `stable` |
| `source` | string | 是 | `file` = 取自落盘 `runtime.log` 尾部；`memory` = 落盘不可用，退回内存环形缓冲（最多 2000 条）。**`memory` 说明现场可能有缺失** |
| `size` | int | 是 | `content` 的 UTF-8 字节数（由客户端计算，服务端应复核实际收到的长度） |
| `truncated` | bool | 是 | `true` = 正文只是最近一段（文件比 512 KB 长，或内存缓冲溢出）。**`true` 时日志开头可能缺前置上下文** |
| `createdAt` | long | 是 | 客户端采集时刻（毫秒） |
| `content` | string | 是 | 日志正文，UTF-8，**按时间正序**（早 → 晚）。可能为空串 |

### 3.1 `content` 的形态

- 每行一条，行内以 `\n` 分隔（不保证有 `\r`）。
- 行格式：`MM-dd HH:mm:ss.SSS <级别>/<标签> <消息>`，例如
  `10-29 22:15:41.203 I/引擎 开始任务：自动关注`。
  级别只有 `V` / `D` / `I` / `W` / `E` 五种。
- 内容含中文，可能含无障碍节点文案（直播间昵称、评论原文）。**这些是用户可见的公开内容**，
  但服务端仍应按隐私数据处理（见 §6）。
- 单次正文上限 **512 KB**。文件更大时只取尾部，并保证第一行是完整行
  （客户端会丢掉可能被截断的半截首行，所以首行不会出现残缺时间戳）。
- `content` 里**没有**设备唯一标识之外的个人信息，也没有 token / 密码
  （客户端不打日志里写凭据，见 §9）。

### 3.2 服务端应做的校验

| 检查 | 不满足时 |
|---|---|
| `Content-Length` ≤ 1 MB（客户端上限 512 KB，留一倍余量） | 413，`code` 非 0 |
| `content` 的 UTF-8 字节数与 `size` 差距 ≤ 1%（正常应完全相等） | 记录告警，仍可入库 |
| `app == "dgg"` | 400，`code` 非 0 |
| `deviceId` 非空，长度 64 | 400，`code` 非 0 |
| `versionCode` > 0 | 接受但打标（可能是自编译包） |

## 4. 响应体

### 4.1 成功

HTTP 200，`application/json`：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "reportId": "R-20261029-8F3A21",
    "uploadedAt": 1761741235120,
    "expiresAt": 1764333235120,
    "size": 183402,
    "status": "accepted",
    "ticketUrl": "https://console.example.com/tickets/R-20261029-8F3A21"
  }
}
```

### 4.2 响应字段（**只有这份白名单里的键会被读取**）

`data` 下：

| 字段 | 类型 | 必填 | 客户端行为 |
|---|---|---|---|
| `reportId` | string | **是** | 弹窗里显示给用户。**缺失即视为失败**（抛「响应缺少 reportId」，用户看到红字提示） |
| `uploadedAt` | long | 否 | 当前不展示，仅保留解析 |
| `expiresAt` | long | 否 | > 0 时弹窗显示「云端保留至：YYYY-MM-DD HH:mm」 |
| `size` | long | 否 | > 0 时弹窗显示大小（< 1 KB 显示「332 B」，否则「8 KB」/「5.7 MB」）。建议如实回传实际入库字节数；**回 0 或省略就不显示这一行** |
| `status` | string | 否 | `accepted` / `queued` / `filtered` 三值，见 §4.3。缺省或空串按 `accepted` |
| `ticketUrl` | string | 否 | **必须 `https://` 开头**，否则客户端直接丢弃。存在时弹窗多一个「查看工单」按钮 |

顶层还兼容 `result` 作为 `data` 的别名（服务端框架习惯不同），两者都存在时优先 `data`。

**白名单之外的键不会报错，但也不会生效。** 想加字段必须同步改客户端。

### 4.3 `status` 三值语义

| 值 | 客户端文案 | 什么时候用 |
|---|---|---|
| `accepted`（默认） | 已入库 | 日志已落存储，客服能立刻查到 |
| `queued` | 已受理（排队入库） | 走了异步队列 / 对象存储直传还没完成。**此时 `reportId` 必须已可查**，否则客服拿到编号查不到会当成客户端 bug |
| `filtered` | 已收到（被过滤，请联系客服） | 内容命中风控/敏感词规则被丢弃。**必须在 `message` 里写明原因**（如「正文含疑似凭据，已脱敏后隔离」），否则用户只有一句"被过滤"无从下手 |

`filtered` 是**成功响应**（HTTP 200 + `code: 0` + 有 `reportId`），不是错误。
区别在于客户端把它当作"收到了但内容没入库"，需要用户联系客服。

### 4.4 业务拒绝

HTTP 200（或 4xx，两者客户端都处理），`code` 非 0：

```json
{ "code": 1003, "message": "该设备本小时上报次数已达上限（5 次）" }
```

客户端把 `message` **原样弹给用户**。所以：

- `message` 必须是**能给人看的中文**，不要写 `ERR_RATE_LIMIT`；
- `message` 留空时客户端会显示「服务端拒绝：code=1003」，用户看不懂 —— 请务必填；
- 客户端**不做任何自动补救**（不重试、不换设备标识）。

建议的错误码（不强制，仅为了客服口径统一）：

| code | 场景 | 建议 message |
|---|---|---|
| 0 | 成功 | `ok` |
| 1001 | 参数缺失/非法 | `缺少 deviceId，请重装客户端后重试` |
| 1002 | 体量超限 | `日志超过 1 MB，请联系客服人工获取` |
| 1003 | 频控 | `上报过于频繁，请 10 分钟后再试` |
| 1004 | 设备被封禁 | `该设备已被暂停上报，请联系客服` |
| 2001 | 服务端内部错误 | `服务端暂时不可用，请稍后重试` |

### 4.5 非 2xx

客户端一律视为失败，弹「日志上传失败：HTTP 500 <前 120 字符响应体>」。
所以 5xx 时**也不要返大段 HTML 错误页** —— 前 120 字符会直接出现在用户手机上。

## 5. 边界情况

### 5.1 客户端会先本地采集，采集失败就不会发请求

`runtime.log` 不存在且内存缓冲为空时，`content` 为空串，请求**照样发出**（
服务端收到一条只有元数据的上报）。这种情况通常意味着 App 刚启动就点了日志。
服务端可以选择接受（记录 `size=0`）或回 `code=1001`，两端都不会崩。

### 5.2 `reportId` 生成失败时不要返 200

不要返回 `{"code":0,"data":{}}` —— 客户端会报「响应缺少 reportId」，
用户体验上等同于失败，但服务端监控里会显示"全部成功"。请直接返 `code` 非 0。

### 5.3 超时

客户端 10s 连接 / 20s 读超时。**入库慢于 15 秒时请改走 `status="queued"` 立即返回**，
不要让连接挂着 —— 用户手机可能在弱网下，等 20 秒才失败会被当成 App 卡死。

### 5.4 重复上报

用户可能会连点（虽然上传中按钮是禁用的，但失败后可以立刻再点）。
同一份日志可能被上传多次，`reportId` 不同。服务端按 `deviceId + createdAt`
（误差 5 分钟内）可以识别为疑似重复，但**不要静默丢弃** —— 用户每次点击都期待一个编号。

## 6. 隐私与留存（服务端责任）

客户端**不做脱敏**：日志里的昵称、评论原文都是原样上传（它们本来就是无障碍读到的公开内容）。
明文脱敏的责任在服务端：

| 要求 | 说明 |
|---|---|
| 留存期 | 建议 30 天。若设了期限，**必须在 `expiresAt` 里回传**，客户端会展示给用户 |
| 访问控制 | 日志只对客服/开发按工单开放，不做全量导出 |
| 昵称/评论 | 属于用户可见公开内容，可按业务需要保留；导出给第三方前应打码 |
| `deviceId` | 是（已 SHA-256，**不可反推**）。仅用于关联同一设备的多份日志与灰度统计，不做画像 |
| 凭据 | 客户端保证不写 token / 密码 / 短信验证码进日志（见 §9）。若服务端仍匹配到疑似凭据，走 `status="filtered"` |

## 7. 客户端侧行为（服务端了解即可）

1. 用户点「日志」按钮 → 收集最近 512 KB → **立即 POST**，无二次确认、无本地预览。
2. 上传中按钮文案变「上传中…」且禁用；完成后恢复「日志」。
3. 成功 → AlertDialog「日志已上传」，显示编号 / 状态 / 大小 / 保留期限，有 `ticketUrl` 时多一个「查看工单」。
4. 失败 → Toast「日志上传失败：<原因>」，**保留本地日志文件**（用户可以再点一次）。
5. 全程不写任何"已上传"的持久标记 —— 服务端不要依赖客户端去重。

## 9. 客户端承诺（服务端可依赖）

- 不上传 APK、截图、录音、通讯录、短信；只有一份文本日志。
- 日志里不含 OTA 安装包 URL 之外的任何服务端地址，也不含凭据。
- 正文恒定 UTF-8，不会被 gzip 或二次编码。
- `size` 是**实际发送的正文字节数**，不是字符数（中文一字 3 字节）。
- 请求只发一次，不会因为超时在后台补发。

## 10. 本地联调（不需要公网）

debug 包的 `API_BASE_URL` 是 `http://127.0.0.1:3000/`：

```bash
# 1. 起一个本地 mock（任意语言），只要实现 POST /v1/log/upload 返回 §4.1 的 JSON
#    推荐至少准备三个分支：正常 accepted / queued + ticketUrl / HTTP 500
node .tmp/log-mock.js        # 或 python -m http.server 之类

# 2. 端口转发到手机（forward 挂在 adb 守护进程上，本机每条命令都会重启守护）
#    所以 reverse、触发、读日志必须写在同一次 shell 调用里
adb reverse tcp:3000 tcp:3000 && \
  adb shell am force-stop com.example.dgg && \
  adb shell monkey -p com.example.dgg 1 >/dev/null && \
  sleep 3

# 3. 在手机上点「日志」，然后看服务端有没有收到（mock 自己打请求体）
```

验证要点：

- 弹窗里的「编号」= mock 返回的 `reportId`；
- `status=queued` 时标题下方应显示「已受理（排队入库）」，且出现「查看工单」按钮；
- `ticketUrl` 给 `http://` 开头时应**没有**按钮（客户端只认 https）；
- mock 返回 HTTP 500 → Toast「日志上传失败：HTTP 500 …」，App 不崩；
- 本地日志文件（`files/runtime.log`）在失败后仍然存在。

联调完记得 `adb reverse --remove tcp:3000`，并把 `files/last_log_upload.json`
从设备上删掉（`LocalLogUploadProvider` 的残留）。

### 10.1 如果本机 3000 已被别的服务占用

`adb reverse` 转发到本机端口时，若该端口已有**别的进程绑在 `0.0.0.0:3000`**，
请求会落到别人的服务上，表现成客户端收到一份格式完全陌生的 JSON
（实测见过 `{"error":{"code":"NOT_FOUND","request_id":"req_…"}}`）——
排查时很容易误判成"客户端发错了地址"。先确认端口归属：

```bash
netstat -ano | grep ":3000" | grep LISTEN     # 看是不是有两个 PID
```

换端口联调（不必改代码）：

```bash
./gradlew :app:assembleDebug -Pdgg.debugApiBaseUrl=http://127.0.0.1:3100/
adb reverse tcp:3100 tcp:3100
```

debug 的 `API_BASE_URL` 默认仍是 `http://127.0.0.1:3000/`，不带参数编译就回到默认值。

## 11. 与 OTA / 授权接口的关系

三条链路共用同一个 `API_BASE_URL` 与同一套 Provider 范式：

| 链路 | 接口 | 失败是否打扰用户 |
|---|---|---|
| 授权 | `/license/activate`、`/heartbeat`、`/unbind` | 是（弹窗） |
| OTA | `/v1/ota/latest` | 否（静默，下次启动再查） |
| 日志 | `/v1/log/upload` | **是（红字/Toast 必须让用户知道）** |

日志上报是**唯一**由用户在当下主动触发、且结果必须立刻可见的接口。
不要把它做成"异步排队、后台慢慢传" —— 用户点完看不到编号会以为没生效，
而这正是当初取消「本地查看日志」后唯一的安全感来源。
