## 2. 需求 2：授权密钥改成 11 位纯数字

### 2.1 服务端现状（精确到函数）

| 位置 | 现状 |
|---|---|
| `security.js: generateKey()` | `DGG-XXXXX-XXXXX-XXXXX-XXXXX`，20 位 `KEY_ALPHABET` 随机 |
| `security.js: normalizeKey()` | `toUpperCase().replace(/[^A-Z0-9]/g, '')` ⇒ 去横杠/空格，转大写 |
| `security.js: keyHash()` | `hmacHex(normalizeKey(key))`，**入库只存 hash，不存明文** |
| `security.js: keyMeta()` | `prefix = slice(3,8)`（跳过 `DGG`）、`last4 = slice(-4)` |
| `security.js: maskKey()` | `DGG-${prefix}-••••-••••-${last4}` |
| 表 `licenses` | `key_prefix` / `key_last4` / `key_hash UNIQUE` |

### 2.2 目标格式（建议）

```
11 位纯数字，首位取 2–9（避开 1xx 手机号段，也避免 Excel/表格把前导 0 吃掉）
示例：73849201566
展示分组（仅显示，输入仍是纯数字）：7384 920 1566
```

> ⚠️ **11 位数字与手机号同形**，这是本方案唯一的真实 UX 风险。必须在输入框提示里写明「不是手机号」，见 §2.4。

### 2.3 服务端改动清单（由你执行）

按重要性排序，**第 2 条是唯一会伤到存量密钥的地方**：

1. **`generateKey()`** 改成 11 位数字：`首位 2-9 + 10 位 0-9`。
   唯一性靠 `licenses.key_hash` 的 UNIQUE + `licenses.js:134` 已有的冲突重试循环；建议把重试上限从 5 提到 20（11 位空间 9×10¹⁰，碰撞概率极低，但多一层保险）。

2. 🔴 **`normalizeKey()` 必须双轨，不能直接改成 `[^0-9]`**
   现在的旧密钥 `DGG-ABCDE-…` 经 `normalizeKey` 得到 20 位字母数字串再 HMAC。如果把规则改成「只保留数字」，**存量密钥的 hash 全变 ⇒ 已发出去的密钥一夜之间全部失效**，而且症状与「更新软件后失效」完全一样，极难排查。

   推荐实现：按规范化后长度分流

   ```js
   export function normalizeKey(value) {
     const raw = String(value || '').trim().toUpperCase();
     const digits = raw.replace(/[^0-9]/g, '');
     // 11 位纯数字（允许用户输入时带空格/横杠）
     if (digits.length === 11 && !/[A-Z]/.test(raw)) return digits;
     // 其余一律按旧规则：去非 A-Z0-9
     return raw.replace(/[^A-Z0-9]/g, '');
   }
   ```

   并给新版密钥加**格式前置校验**（`/^[2-9]\d{10}$/`），格式不符直接返回 `LICENSE_FORMAT_INVALID`，
   而不是走到 `LICENSE_INVALID`——用户能立刻知道是「输错了位数」还是「密钥不存在」。

3. **`keyMeta()`**：11 位数字没有 `DGG` 前缀，`slice(3,8)` 语义失效。改成按长度分支：
   数字 11 位 → `prefix = slice(0,4)`、`last4 = slice(-4)`；旧格式保持 `slice(3,8)`。

4. **`maskKey()`**：同样分支。数字 11 位 → `7384 •••• 1566`（不要出现 `DGG-`）。
   客户端 `maskCode()` 也会二次打码，两边要一致，否则面板显示会出现两次掩码。

5. **迁移与共存**：新增密钥与存量密钥**并行有效**（靠 `key_hash` 天然区分，无需数据迁移）。
   若要强制存量作废，那是产品决策，不是技术必然——**建议不要**，代价是每台已激活设备都要重新发密钥。

### 2.4 客户端改动清单

| 文件 | 现状 | 改成 |
|---|---|---|
| `MainActivity.kt:778` | `hint = "DGG-XXXXX-XXXXX-XXXXX-XXXXX"`<br>`inputType = TEXT or CAP_CHARACTERS`<br>`filters = LengthFilter(64)` | `hint = "11 位数字授权码（不是手机号）"`<br>`inputType = TYPE_CLASS_NUMBER`<br>`filters = LengthFilter(11)` |
| `MainActivity.kt:797` | 只判 `isBlank()` | 加 `Regex("^\\d{11}$")` 前置校验，不通过直接 `input.error = "请输入 11 位数字授权码"`，**不发请求** |
| `MainActivity.kt:825 maskCode()` | `take(4) + "••••" + takeLast(4)` | 对 11 位数字显示 `前4 •••• 后4`；长度不符回落原逻辑 |
| `content_auto_follow.xml:439` | 标签「激活卡密」 | 「授权密钥」（与新文案统一；`tv_license_code` 的 `contentDescription` 同步） |
| `RemoteLicenseProvider.activate()` | `code.trim()` | 增加「去空格/横杠」的规范化（用户从微信复制常带空格） |

粘贴场景要专门处理：从微信/短信复制的码常带空格或不可见字符，客户端做一次 `replace(Regex("[^0-9]"), "")` 再校验长度，比让用户自己删更省事。

### 2.5 兼容矩阵

| 场景 | 结果 | 备注 |
|---|---|---|
| 新密钥 + 新 App | ✅ | 主路径 |
| 旧密钥 + 新 App | ⚠️ 取决于客户端是否还允许输入字母 | 若 `inputType=NUMBER` 就**输不进旧密钥**。要么保留「切换旧格式」入口，要么接受旧密钥改为手动在服务端换发 |
| 新密钥 + 旧 App（未升级的客户） | ⚠️ 能输入（旧 App 限制 64 位文本），但旧 App 的 `normalizeKey` 在服务端 | 服务端双轨后可用 |
| 旧密钥 + 旧 App | ✅ 不受影响 | 前提是服务端做了双轨 |

🔴 **这里有个必须你拍板的取舍**：客户端把输入框锁成纯数字后，**旧格式密钥在这台设备上就输不进去了**。三种处理：

- **A（推荐）**：输入框纯数字，但对「长度 ≠ 11 且含字母」的输入给专门提示「这是旧格式密钥，请升级到 vX 或联系管理员换发」——不静默失败。
- **B**：保留一个隐藏入口（长按标题 5 次）切到旧格式输入。适合过渡期，但多一条代码路径。
- **C**：直接作废旧格式。客户全部重新发密钥，最干净但要一次性通知到位。

### 2.6 验收

1. 服务端生成 10 个密钥 → 全部 `^[2-9]\d{10}$`、无重复、`maskKey` 显示为 `xxxx •••• xxxx`。
2. 客户端输入 10 位 → 本地即报错，不发请求；输入 11 位错误码 → 服务端 `LICENSE_INVALID`。
3. 输入带空格的 `7384 920 1566` → 能激活成功。
4. 存量 `DGG-…` 密钥仍能激活（若采纳 A/B 方案）。
5. 面板「授权信息」里显示 `7384••••1566`，不出现 `DGG-`。

## 3. 需求 3：更新软件后授权失效（真 bug，需要先取证再改）

### 3.1 现状链路（已核实）

```
App 侧  deviceId = sha256( "${ANDROID_ID}:${installUuid}:${packageName}" )
        installUuid 存 SharedPreferences("dgg_device")，首次启动随机生成
        令牌 TokenStore 用 Android Keystore 加密后存 SharedPreferences("dgg_license_secure")
服务端  activate: key_hash 查 licenses → 名额检查 device_count >= max_devices → 拒
        handshake: 只校验 JWT(token) 与 device / license 状态，**不校验当前设备身份**
```

### 3.2 为什么「更新」会导致失效（三个候选，含证据强度）

| # | 机制 | 触发条件 | 证据强度 |
|---|---|---|---|
| **A** | **卸载重装** ⇒ `installUuid` 重新生成 ⇒ `deviceId` 变 ⇒ 服务端视为新设备 ⇒ `max_devices=1` 时满额 | 系统拒绝覆盖安装（签名/降级）、用户手动卸载、"清理大师"类工具、部分 ROM 安装器默认卸载旧的 | 🔴 **强**：日志 `R-20261030-E82372` 22:39 连续 4 次 `激活失败：设备数已满` |
| B | Keystore 解密失败 ⇒ 令牌被 `TokenStore.load()` 的 `onFailure` 清掉 ⇒ 走激活 | 换签名、清数据、部分 ROM 的 Keystore 异常、`am clear` | 🟡 中：日志会出现 `LicenseStore: 读取设备令牌失败：X`，**需去日志里确认有没有这行** |
| C | 服务端版本绑定 | — | 🟢 排除：`handshake` 只把 `app_version_code` 当记录字段更新，不参与校验 |

> 注：覆盖安装（同签名、`adb install -r`）**不会**丢 `installUuid`，实测三项权限与令牌都会保留（见 `MEMORY.md` 权限保留表）。所以纯 OTA 升级不该掉授权 —— 掉了就一定是 A 或 B。

### 3.3 诊断（改代码前先做，避免治错病）

1. **客户端加两条日志**（低风险，可先进一个诊断包）
   - `DeviceIdentity`：首次生成 `installUuid` 时记 `device_id 前 8 位`；每次启动比对一次并记「deviceId 未变 / 已变化（新生成 UUID）」。
   - `TokenStore.load()`：把 `onFailure` 的异常类型与消息一起记（现在只记 `javaClass.simpleName`，Keystore 的 `KeyPermanentlyInvalidatedException` 与 `AEADBadTagException` 含义完全不同）。
2. **服务端**：`DEVICE_LIMIT_REACHED` 抛出前，把该 license 下已有设备的 `device_name / model / last_seen_at` 记进 `license_events`，便于一眼看出「同名同型号、两台」= 重装。
3. **一次对照实验**：同一台机，(a) 覆盖安装 `adb install -r` → 看授权是否保留；(b) 卸载后重装 → 看是否卡在设备数满。
   两条都记录 `device_id` 前 8 位，根因立刻分晓。

### 3.4 治本方案：硬件指纹 + 名额自动回收

**思路**：`installUuid` 是随机的，重装必然变；但 `ANDROID_ID` 从 Android 8 起是「按签名 + 用户 + 设备」派生的，**同签名的卸载重装不会变**。用它派生一个稳定标识。

**客户端**

```kotlin
// DeviceIdentity.payload() 新增字段，不动现有 device_id
val fingerprint = sha256("$androidId:${context.packageName}")   // 不含 installUuid
put("device_fingerprint", fingerprint)
```

**服务端**

```sql
ALTER TABLE devices ADD COLUMN IF NOT EXISTS device_fingerprint TEXT;
CREATE INDEX IF NOT EXISTS idx_devices_fp ON devices(license_id, device_fingerprint);
```

`activate` 的名额检查改成三级：

```
1. 同 device_hash 且 active        → 幂等更新，直接返回（现状已有）
2. device_count >= max_devices 时：
   2a. 按 device_fingerprint 找同 license 下的 active 旧记录
       命中 → 旧记录置 unbound(reason='reinstall_replaced')、device_count -1、
              记 license_event('device_replaced')，然后正常激活新记录
   2b. 未命中 → 抛 DEVICE_LIMIT_REACHED（真·第二台设备，仍然拦住）
3. 其余情况 → 正常插入
```

**为什么这既是修复也是「加强」**：它不放宽总设备数，只是把「同一台机器的旧身份」回收掉；真正换第二台手机仍然会被拦。而且回收动作**留审计**（`device_replaced` 事件），事后能查是不是有人拿指纹刷名额。

**兼容**：旧版 App 不带 `device_fingerprint` ⇒ `2a` 跳过，行为与现在完全一致（不会因为字段缺失而放宽）。

### 3.5 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 指纹可伪造（root/Xposed） | 理论上能刷出「无数台同指纹设备」 | 只在**名额已满**时用，且每次回收写审计；管理员可封禁 license |
| ANDROID_ID 被系统重置 | 恢复出厂 / 部分 ROM 的「重置广告 ID」不影响 ANDROID_ID，但恢复出厂会变 | 变了就退回现状（报设备数满），由管理员解绑——与今天一致，不更糟 |
| 应用分身 / 双开 | 分身通常有独立 ANDROID_ID | 视为另一台设备，符合预期 |

## 4. 需求 4：加强判定

### 4.1 现状漏洞（按严重度）

| # | 位置 | 问题 |
|---|---|---|
| 🔴 1 | `EngineController.start()` | **完全不校验授权**。拦在 `MainActivity.btnStartService.isEnabled` 与 `toast("请先激活授权")` 这两处 UI 上。悬浮窗的「重试」（`restartLast()`）与通知栏入口也都不校验 ⇒ 授权被撤销后仍能继续跑 |
| 🟠 2 | 授权新鲜度 | 只在 `MainActivity.onCreate` 调一次 `initialize()`。**App 常驻前台跑几小时，期间 license 被停用/到期都不会被发现**（离线宽限 72h） |
| 🟠 3 | 离线宽限可被时钟回拨延长 | `offlineUntil` 是绝对时间戳，存本地；把系统时间往前调就能一直「宽限」 |
| 🟡 4 | 令牌不绑设备 | `handshake` 只认 JWT。Keystore 挡住了一部分，但 root 环境可导出 |
| 🟡 5 | 本地占位实现 | `LocalLicenseProvider` 存在但未被注入（已确认 `MainActivity:156` 用的是 `RemoteLicenseProvider`），**保留一个 authorized=true 的实现本身就是隐患** |

### 4.2 改法

**P0-1 授权门禁下沉到服务层**

```kotlin
// EngineController.start() 最前面
if (!LicenseGate.isAuthorized(context)) {
    LogStore.e(TAG, "拒绝启动：授权无效（$reason）")
    return Result.failure(IllegalStateException("授权无效，请重新激活"))
}
```

`restartLast()` 走同一个 gate。这样 UI 层只是「提前告知」，真正的门禁在唯一入口，任何路径（悬浮窗重试、通知栏、未来新增入口）都绕不过。

**P0-2 运行期握手新鲜度**

- 触发点：回前台（`onResume`）+ 每隔 6 小时（与现有 OTA 6 小时检查共用一个计时器，不额外起协程）。
- 判定：`now - lastSuccessHandshakeAt > 24h` 且处于离线宽限 ⇒ 拒绝启动任务并提示「授权需要联网确认」。
- 注意：**不能因为网络抖动就停任务**。只有「授权明确失效」才停；「连不上」只在超过阈值时降级为「禁止开始新任务」，不打断正在跑的任务。

**P0-3 防时钟回拨**

`TokenStore` 里多存一个 `lastSeenWallClock`（每次握手成功或 App 启动时写）。启动时若 `System.currentTimeMillis()` 明显小于该值（比如 5 分钟以上），判定为本地时间异常：

- 记日志 + 面板提示；
- **禁用离线宽限**（强制要求联网握手成功才放行）；
- 不回拨不误伤 —— 正常时区切换/夏令时差值在分钟级，5 分钟阈值足够。

**P1-1 握手带指纹**

`handshake` 请求体加 `device_fingerprint`；服务端比对 `devices.device_fingerprint`，不一致返回 `DEVICE_MISMATCH`（客户端清 token 并要求重新激活）。这条在 §3.4 的字段落地后几乎零成本。

**P1-2 清理本地占位**

`LocalLicenseProvider` 的 `authorized = true` 是硬编码常量。建议：整个类移到 `debug` 源集，或加 `@VisibleForTesting` + release 构建断言，避免哪天有人图省事把它接进去。

### 4.3 明确不做的

- ❌ **不做本地「密钥算法校验」**（把 11 位数字按某种规则算校验位在本地判真假）——密钥真伪只有服务端知道，本地算等于把规则交给破解者。
- ❌ **不做「每 N 分钟强制联网」**——直播间场景网络本来就不稳，会把正常用户误停。
- ❌ **不把 token 换成设备特征绑定**（如 IMEI/MAC）——与既定的隐私取舍冲突。

| **P1** | 服务端 11 位 `generateKey` + `normalizeKey` 双轨 + `keyMeta/maskKey` 适配 | **你** | 客户端 P0 完成后一起发版 |
| **P1** | 客户端上报 `device_fingerprint`；服务端加列 + 名额自动回收 | 我 + 你 | 服务端先加列（向后兼容） |
| **P2** | 握手新鲜度、防时钟回拨、handshake 指纹校验、占位类清理 | 我 | P1 稳定后 |

服务端可以先行的顺序（不影响现有客户端）：**加 `device_fingerprint` 列 → 双轨 `normalizeKey` → 新的 `generateKey`**。三步都是向后兼容的，旧 App 照常工作。

## 7. 需要你拍板的 4 件事

1. **旧密钥（`DGG-…`）要不要继续可用？**
   要 → 服务端必须双轨 `normalizeKey`，客户端给「旧格式」专门提示。
   不要 → 一次性换发，但每台在用设备都要重新激活一次。
2. **11 位数字是否允许首位为 0？**
   建议不允许（首位 2–9）：既避开 1xx 手机号段，也避免表格/Excel 把它当数字吃掉前导零。
3. **「更新软件后失效」你的实际场景是哪种？**
   覆盖安装（手机上点新 APK 直接装）还是先卸载再装？这决定 §3 的重心是修 A 还是修 B。
   如果方便，把那台设备的最新日志再传一份，我直接看 `TokenStore` 有没有报解密失败。
4. **接受「同指纹自动回收旧设备」这个策略吗？**
   它能让重装/换机不占名额，代价是 root 环境理论上能刷指纹。我的判断：值得做，但要留审计（已写进方案）。

## 9. 执行记录（2026-10-30，vc35 / 1.4.6）

### 9.1 服务端已就位（用户执行）

`security.js` 现状与计划一致，且**比计划更简洁**——`normalizeKey` 直接改成
`trim().replace(/[\s-]/g, '')`（只去空格与横杠，不再转大写、不再过滤字母）：

```js
const KEY_LENGTH = 11;
generateKey()  → 11 位纯数字（crypto.randomInt(10)，**首位可能是 0 或 1**）
normalizeKey() → String(v).trim().replace(/[\s-]/g, '')
keyMeta()      → prefix = slice(0,7)、last4 = slice(-4)
maskKey()      → `•••••••${last4}`（7 个掩码位 + 后 4 位）
```

⚠️ **对计划的两处修正**：

1. **不能要求首位非 0**。生成的第一个测试密钥就是 `17084534704`（1 开头），
   服务端没有任何首位置约束——客户端若加这条校验，约 20% 的密钥会输不进去。
   实际校验只判 `^\d{11}$`。
2. **不需要双轨兼容**（用户已明确旧密钥作废）。`normalizeKey` 对旧 `DGG-…` 串仍能算出原 hash，
   但产品上不再支持：客户端输入框锁成纯数字后旧密钥根本输不进去，所以文案里明说
   「旧格式密钥已停用，请联系管理员换发」，而不是让它静默失败。

### 9.4 关于「更新后失效」的实测结论（重要）

**覆盖安装本身不会掉授权。** 上面 20:58 那次覆盖安装，令牌、到期时间、设备绑定全部保留。

本轮实测到的唯一一次失效，是我在 vc34 上直接覆盖装 vc35 时出现的
「授权凭证已失效，请重新输入密钥」——那是**更早版本留下的旧 token** 在握手时被服务端
判为 `TOKEN_INVALID`（`CLEAR_TOKEN_CODES` 命中后客户端主动清空，于是要求重新激活）。
它属于历史包袱，不是「每次升级都会复现」的缺陷。

**但根因还没锁死**，因为那次 401 发生时服务端 `setErrorHandler` **根本没打日志**
（记录里写着"已加 warn"，实际代码里没有），只能看到 `statusCode:401`，看不到 code。
已补上：

```js
request.log.warn({ code, status, url, msg }, "app error")
```

（`src/app.js`，备份 `app.js.bak-4xxlog`）。以后再有 4xx，journalctl 一眼看到是
`TOKEN_INVALID` / `TOKEN_EXPIRED` / `DEVICE_UNBOUND` 中的哪一个，不用猜。

同时客户端补齐了两侧证据：

- `DeviceIdentity` 会打印 `deviceId 已变化 xxxxxxxx… → yyyyyyyy…`（重装/清数据的铁证）；
- `TokenStore` 会打印解密失败的异常类型，并区分「密文真的坏了」与「Keystore 临时故障」。

**下一步（P1，尚未做）**：`device_fingerprint` + 服务端名额自动回收（计划 §3.4）。
在拿到一次真实的 4xx code 之前不动它——否则可能是在修一个不存在的病。
