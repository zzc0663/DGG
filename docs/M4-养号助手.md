# M4 · 养号助手（主动刷视频 + 随机停留 + 标签加权互动）

> 状态：**计划待确认**（2026-10-28）。真机取证已完成，代码未开工。
> 目标机：OPPO PLB110 / Android 17 / 抖音 40.8.0 / 1080×2400。

---

## 1. 范围

> **决策已确认（2026-10-28）**：① 不做关注作者 ② 点赞概率上限放宽到 60% ③ 本期 P1~P3，垂直养号留 P4。

### 做

1. **主动刷视频**：脚本自己上下滑推荐流，不再要求用户手动停在某个页面。
2. **每个视频停留时间随机**：按真人的长尾分布，不是均匀随机。
3. **点赞倾向可设置**：界面滑块（已有，上限 40→60），叠加标签加权。
4. **视频文案标签识别**：读当前视频的文案/话题，命中标签则提高点赞概率。

### 不做

- **不关注作者**（本次决策）：⇒ **本功能不产生粉丝**，模式 0 的名字与文案必须从
  「挂机涨粉」改成「刷视频养号」，不能对外承诺涨粉（§8 说明原因与后续）
- 不评论（养号场景评论走内容审核，风险收益比最差；评论能力已在 M3，需要时再开）
- 不转发（转发会污染主页/朋友动态，暴露面最大）
- 不自动进直播间（推荐流会插直播卡，**必须滑走**，绝不点）
- 不搜索、不换频道（模式 1「垂直养号」的搜索链路放到 P4）
- 不做强制时长（`runMinutes` 到点就停）

## 2. 三种模式的重新定义（界面文案要跟着改）

现在界面上的三档语义含糊（「挂机涨粉」「垂直养号」「首页连播」都能理解成刷首页），需要明确成：

| 值 | 名称（新） | 行为 | 风险 |
|---|---|---|---|
| 0 | 刷视频养号 | 刷推荐流 + 概率点赞/收藏，**关注零动作** | 低 |
| 1 | 垂直养号 | 先按关键词搜索，只刷该垂类，强化兴趣画像 | 中（P4 才做） |
| 2 | 首页连播 | **只刷视频，零互动**，纯挂时长 | 最低（最保守） |

⚠️ 模式 0 原名「挂机涨粉」必须改名：不关注 = 不会有粉丝进来，继续叫"涨粉"是误导用户。
`tv_mode_desc` 三行描述同步改：

- 刷视频养号：刷推荐流视频，按停留节奏随机观看，命中标签时概率点赞
- 垂直养号：按关键词搜索后只刷该垂类，强化账号兴趣标签（暂未开放）
- 首页连播：只刷视频不互动，最保守的挂时长方式

模式 2 的实现成本几乎为零（同一套循环，互动概率全填 0），可作为 P1 阶段的天然形态。

### 3.2 四个决定设计的关键发现

**① 点赞/收藏状态可从 desc 判定 —— 养号的点赞可以闭环校验**

实测：点一下点赞按钮，`content-desc="未点赞，喜欢13.3万，按钮"` 立刻变成
`content-desc="已点赞，喜欢13.3万，按钮"`；收藏同理 `未选中，收藏9847` → `已选中，收藏…`。

这比 M3 强得多：M3 在直播间只能双击空白画面，**无法证明点赞生效**（记忆里写着"只写发出 N 次手势"）。
养号场景必须用这个 desc 判定作为唯一成功判据，点完状态没变就记失败并进入冷却。

**② 文案的位置：视频页在 `text`，图文页在 `content-desc`**

- 视频作品：`text="@sweet"` + `text="让你爱上我 要多久 >"`，desc 为空
- 图文作品：`text="第 25 集"`，而 `content-desc` 里是**完整长文案**（含换行、话题、@ 提及）

⇒ 文案提取必须**同时扫 text 和 content-desc**，只扫一个会漏掉一半作品。

**③ 推荐流是混合信息流，不是纯视频流**

连续滑动 4 次的实际内容：图文作品（"第 25 集"+「图片1，按钮」「动图」）→ **直播推荐卡**
（`点击进入直播间按钮`、`@呢呢直播中`）→ 视频 → 视频。

⇒ 每一屏必须先分类再决定动作。直播卡上有大面积可点区域，**误点就直接进了直播间**，
后续整套流程（页面判定、风控、返回）全乱。这一条是 M4 最大的单点风险。

**④ 视频播放中 `uiautomator dump` 会失败（`ERROR: could not get idle state`）**

实测：视频播放时 dump 必失败，暂停后立刻成功。原因是 uiautomator 等 idle、而视频永不 idle。

> 这条**不影响脚本**（本项目的 `Actions.snapshot()` 走 AccessibilityNodeInfo 自己遍历，不等 idle），
> 但**影响调试**：以后"dump 不出东西"先怀疑视频在播，别怀疑无障碍服务挂了。
> 调试时可先 `input tap <空白区>` 暂停再 dump（实测点击中央空白区 = 暂停/继续）。

### 3.3 还没取到的（P0 补齐）

|---|---|
| `content-desc="进度条"` 的 `rangeInfo` 是否可读 | 能读到进度就能判"这条看完了"，停留时间可做成真实行为而非猜时长 |

## 4. 一轮的时序

```
┌─ 前置（一次）─────────────────────────────────────────────┐
│ 确认前台是抖音（不等直播间）→ 确认当前是 FEED（推荐流）      │
│ 不是 FEED 就先导航：点底栏「首页」→ 点顶部「推荐」页签       │
│ 导航失败 → 中止，绝不猜                                    │
└──────────────────────────────────────────────────────────┘
        ↓
┌─ 每屏循环 ────────────────────────────────────────────────┐
│ 1. snapshot(ttl=0) 一次抓全树                             │
│ 2. 分类：VIDEO / IMAGE_SET / LIVE_CARD / AD / UNKNOWN      │
│ 3. LIVE_CARD、AD、UNKNOWN → 记日志 → 直接滑走（零点击）      │
│ 4. VIDEO / IMAGE_SET →                                      │
│    a. 提取文案（§6）→ 匹配标签 → 算出本次点赞概率            │
│    b. 掷骰：点赞？（受"不连续互动"约束）                    │
│    c. 掷骰：收藏？（独立概率，与点赞互斥）                  │
│    d. 随机停留（§5，分片可中断）                            │
│    e. 互动动作（若有）→ 立刻校验 desc 状态变化              │
│    f. 每步之后 guard() 查风控                              │
│ 5. 滑动到下一屏（§9 轨迹随机化）+ invalidateSnapshot        │
│ 6. 周期性休息判定（§9）                                    │
└──────────────────────────────────────────────────────────┘
        ↓
退出条件：runMinutes 到点 / 风控命中 / UNKNOWN 连续 N 次 / 用户停止
```

注意顺序：**先停留再互动**。真人是看了几秒才点赞，点完再看一会儿或直接滑走。
反过来（进屏先点赞）是最容易被识别成脚本的特征。

## 5. 停留时间模型

### 5.1 为什么不能用均匀随机

「在 2~20 秒之间均匀随机」听起来随机，但和真人的分布完全不同。真人看视频是**长尾**：
大量 1~4 秒划走（划走成本极低），少数看十几秒，极少数看完或看两遍。
均匀随机会让"每次都看 8~14 秒"这件事变成稳定特征 —— 反而更假。

### 5.2 分段加权（默认参数）

| 档 | 权重 | 停留区间 | 行为含义 |
|---|---|---|---|
| 划过 | 40% | 1.5~4 s | 不感兴趣，扫一眼 |
| 正常看 | 35% | 4~12 s | 看一半 |
| 看完 | 20% | 12~35 s | 对内容有兴趣 |
| 深度 | 5% | 35~90 s | 看评论/走神/后台切走 |

均摊约 13.6 s / 屏。按 60 分钟算约 260 屏 —— 这是**故意**的量级：真人一小时也刷不到 500 条。

界面提供「停留节奏」三档（慢 / 标准 / 快），分别把上表整体乘 1.6 / 1.0 / 0.6。
不暴露四个权重给用户 —— 参数越多越容易调出机器特征。

### 5.3 实现约束（踩过的坑）

- **不要用 `settle(baseMs)` 传一个已经随机好的值**：`settle` 内部还会叠 `humanizer.delayMs`
  的 ±jitter%，两层随机叠加会让实际区间漂出设定范围（35s 能漂到 45s+）。
  正确做法：自己 `humanizer.longIn(min, max)` 掷出目标值，再 `settleLong(target, capMs = max)`，
  由 `capMs` 夹住上限。
- 停留必须**分片**（`settleLong`，chunk 500 ms），否则用户点「暂停」要等这条视频看完才生效。
- 停留期间不能只 `delay`：`settleLong` 顺便每 10s 上报剩余，悬浮窗不会一动不动。

## 6. 文案标签识别

### 6.1 文案提取算法

输入：一次 `snapshot()` 的 `NodeFacts` 列表。输出：`copyText`（去噪后的文案）+ `hitTags`。

```
candidates = []
for f in facts:
    text = f.text（若空则 f.desc）
    if text.isEmpty(): skip
    if text 含任一 EXCLUDE_HINTS: skip           // 「，按钮」「已选中，收藏」「分享1.2万」…
    if f.top < 屏高 * copyAreaTopRatio: skip     // 默认 0.78，只扫下半屏
    if text 以 "@" 开头且长度 < 12 且无空格: skip // 纯作者名
    if text.length < 2: skip
    candidates += text

copyText = candidates 按长度降序 取前 3 条拼接   // 覆盖"文案 + 话题 + 音乐名"被拆成多节点的情况
```

`EXCLUDE_HINTS` 必须包含（来自实测）：
`，按钮`、`已选中`、`未选中`、`喜欢`、`评论`、`分享`、`收藏`、`音乐`、`人推荐`、
`搜同款`、`玩同款`、`拍同款`、`发弹幕`、`进度条`、`关注`、`播放视频`、`暂停视频`、`图片`

### 6.2 截断容忍

文案节点尾部带 ` >` 是"展开"标记，说明**长文案会被截断**（阈值待测，§3.3）。

⇒ 匹配规则：标签词只要出现在 `copyText` 里就算命中（`contains`），不做整词相等；
并且**绝不为了读全文去点文案** —— 点文案区会打开评论面板，把整个流程打断。

### 6.3 标签规则格式

界面里一个多行输入框，一行一条，两种写法都接受：

```
健身
蛋白粉 80
减脂 50%
```

- 只写词 = 加成 100%
- `词 数字` = 加成 N%（`%` 可写可不写）
- 单行非法 → 只跳过这一行 + 标红提示，**不让整份配置失败**
  （`LocatorConfig.parse` 就吃过这个亏：一行字符串注释让整份配置降级成 fallback）
- 上限：最多 20 条、单条加成 0~200%

内置一份默认标签（见 `assets/nurture_tags.json`），用户第一次进入时预填，可全删。

## 7. 点赞倾向与概率模型

> 上限已确认放宽到 **60%**（2026-10-28 决策）。界面滑块的 `valueTo` 要从 40 改成 60，
> 底部提示文案也要同步改：原「每项概率最多设置 40%」→「点赞最多 60%，其余每项最多 40%」。

### 7.1 公式

```
base   = settings.probLike                          // 界面滑块 0~60%
bonus  = Σ(tag.weight for tag in hitTags)           // 100% + 80% = 180%
final  = clamp(base * (1 + bonus), 0, MAX_LIKE_PERCENT)   // MAX_LIKE_PERCENT = 60
```

**乘法而不是加法**，因为：

- `base = 0` 时 `final` 恒为 0 —— 用户把滑块拉到 0 就是"不要点赞"，这个意图不能被标签推翻
- 加法会让 base=0、命中 3 个标签变成 30%，用户会认为"我明明关了点赞它还在点"

**常量要拆成两个**，不要用一个 `MAX_PERCENT` 糊住全部四项：

| 常量 | 值 | 作用范围 |
|---|---|---|
| `MAX_LIKE_PERCENT` | 60 | 点赞（本次放宽） |
| `MAX_INTERACT_PERCENT` | 40 | 收藏 / 评论 / 转发（**维持原承诺不变**） |

收藏概率也走同一条 `NurtureTags` 计算路径时，上限必须用 40，别跟着点赞一起放到 60。

### 7.2 界面（在现有「操作概率」卡片内扩展）

```
点赞倾向                           40%
[━━━━━━━━━━━━━━━━━━━━━━━━]         ← slider_like: valueTo 40 → 60
标签加权  已启用 3 条 · 最高 +180%   ‹编辑›
  └ 命中标签时点赞概率最高可到 60%

收藏概率                           15%
[━━━━━━━━━━━━━━━━━━━━━━━━]         ← 保持 valueTo 40

⚠ 点赞最多 60%，其余每项最多 40%    ← 原文案是"每项最多 40%"，必须改
```

- 「点赞倾向」= 原来的 `probLike`，文案改叫"倾向"，因为现在它是**基线**而非最终概率
- 「标签加权」右侧点开弹窗编辑（多行输入 + 保存）
- 收藏/评论/转发三项的 `valueTo` **不动**

### 7.3 日志可核对

每屏都要能复现"为什么点了/没点"：

```
[养号] 文案「减脂期别只吃水煮菜 #减脂」命中 [减脂+50%, 健身+100%]
       基础 10% → 25%，掷骰 0.173 → 点赞
[养号] 文案「我家猫又长胖了」无命中 → 10%，掷骰 0.62 → 跳过
```

没有这行日志，用户反馈"点赞太多/太少"时无法定位是概率配置问题还是识别问题。

## 8. 关注作者：本期不做（2026-10-28 决策）

### 8.1 必须如实告知：本功能不涨粉

**刷视频、点赞不会带来粉丝。** 刷和赞影响的是账号活跃度权重与推荐画像，
粉丝增长只能来自"关注别人 → 对方回关"或"自己发内容被推荐"。

⇒ 模式 0 的产品定位是**养号**（把账号养得像个正常活跃用户、把推荐画风纠正到目标垂类），
**不是涨粉**。界面文案、启动确认弹窗、日志、以及任何对外话术都不能写"涨粉"。
说"涨粉"是骗用户，用户跑一周没涨一个粉就会来找你。

### 8.2 调研结论（留给以后，不必重查）

视频页右侧就有一颗 `content-desc="关注"` [893,1112][1076,1199]，
**点一下直接关注当前作者，不用进资料页** —— 比 M2 那条"进资料页→找按钮→返回"的链路便宜一个数量级。

如果以后要开，必须同时满足这五条，缺一条就不要开：

| 约束 | 值 | 理由 |
|---|---|---|
| 单次关注概率 | ≤8% | 关注是"重动作"，抖音判定比点赞严格得多 |
| 关注之间最小间隔 | ≥90 s | 真人不会一分钟关注三个人 |
| 每日关注上限 | 复用 `dailyLimit` | 与 M2 共享额度，避免两处加起来超标 |
| 关注后必校验 | desc 变「已关注」才算成功 | 状态没变 = 没生效，不记数、不重试 |
| 连续失败 3 次 | 关闭关注动作继续刷 | 可能被限流，此时继续点只会加重 |

⚠️ **必须先实测确认**：关注后 `content-desc="关注"` 变成什么。**确认不了就不做** ——
"点了就当成功"是 M2 明确禁止的做法（见 `docs/M2-直播间评论关注.md`）。

### 8.3 将来做时的位置过滤

顶部页签里也有一个 `content-desc="关注，按钮关注的作者正在直播"`（y 128~252）。
取目标时必须 `x > 屏宽 * 0.8` 且 `y 在屏幕中段`，否则会点到顶部页签跳走。

本期不需要这个目标，但 `douyin_locator.json` 里仍预留 `feed_follow`，
避免以后开功能又要改一次配置格式。

## 9. 刷视频特有的风控约束（硬性）

| 项 | 做法 | 不做会怎样 |
|---|---|---|

## 14. 已知限制（不掩盖）

- **本功能不涨粉**：只提升账号活跃度权重、纠正推荐画像。想涨粉需要关注别人（P4）。
- **文案可能被截断**：标签按 `contains` 匹配，截断位置正好切断关键词时会漏命中。
- **拿不到视频时长**：除非进度条 `rangeInfo` 可读（P0 待测），否则"看完/看一半"只能是时间近似。
- **图文作品与视频同等对待**：图文实际浏览行为更短，暂不区分。
- **看不懂内容**：标签是纯字符串匹配，不理解语义；"减脂"和"减肥"算两个标签，需要用户自己都写上。
- **无法判断"广告"**：靠 `adHints` 关键词，垂类广告会漏。
- **点赞 60% 已接近"每两条赞一条"**：这比真人的点赞率高得多，风控风险由用户通过滑块自行承担；
  默认值仍为 40%（`Settings.probLike` 不变），放宽的只是上限。
- 抖音改版会让 `feed` 段全失效；但因是配置外置，改配置即可，不必发版。
- **一屏的真实耗时不可控**：抖音视频页一趟无障碍遍历实测 **0.2 秒 ~ 20 秒**（同一台机器、
  同样约 1200 个节点），抖动来自系统对无障碍 IPC 的节流，与节点数无关。
  停留时长会把这段识别时间扣掉（`alreadySpentMs`），所以「每条看多久」在小值档位下会被
  识别耗时淹没 —— 想让它像真人，只能靠别把 `MAX_NODES` 调大、也别在播放最卡的时候跑。
- 详见 §15 的实测记录。

### 15.2 Bug 1：直播悬浮小窗被当成直播卡（空刷 39 屏）

- **现象**：连续 39 屏日志都是 `直播卡「撩开你的长发 怎么有香水味 #女大学生 #随拍 」`，
  每屏都 `跳过直播卡` 然后 `滑动 成功`，画面其实一动没动；**任何熔断都没触发**。
- **根因**：`liveCardHints` 只判「文本里有没有 `点击进入直播间`」。抖音看完直播退回来会留一个
  左下角**悬浮小窗**（PiP），它带同样的文案且一直浮在最上层 → 每屏都是直播卡。
  而直播卡分支不算「认不出」，`stallAbortRounds` 永远数不到。
- **修法**：`feed.liveCardMinAreaRatio = 0.12` —— 命中节点必须占屏 ≥12% 面积才算直播卡
  （真直播卡的按钮几乎盖满屏，PiP 只有百分之几）。
- **验证**：同一故障现场重跑，第 1 屏就变 `认不出`，第 7 屏中止：
  `连续 7 屏画面完全相同（…），滑动没有生效。可能是抖音停在活动页/直播卡里，或无障碍手势被系统拦了`。

### 15.3 Bug 2：把「下一条视频」的文案算进这一屏

- **现象**：换了视频但文案不变；用 App 内 `DUMP` 抓到实证 —— 当前条 `@好运全来` 的文案
  `[36,2004][801,2140]`，**下一条** `@zmo` 的文案 `[36,4244][801,2179]`、点赞按钮
  `未点赞，喜欢68.4万，按钮` 的 `top=3376`（屏高 2374）。
- **根因**：`classify` 只判断「在文案区以下」（`f.top < copyTop → skip`），**没有上界**。
  RecyclerView 预加载的下一条/下 N 条仍在树里，于是被拼进 `copyText`（按长度取前 3 条），
  指纹因此永远对不上这一屏；极端情况下右侧按钮也会取到屏幕外那一个（点下去打空）。
- **修法**：`classify` 与 `likeStateOf` / `collectStateOf` 一律先排除
  `f.top >= height || f.bottom <= 0`。
- **验证**：修后每屏文案互不相同（`嗷！#宿舍搞笑日常…` → `查看图文版太帅了…` → `小白饭撒中…`），
  点赞/收藏校验也稳定通过。

### 15.4 Bug 3：休息越过运行时长

- **现象**：设了 2 分钟，实际 23:27:15 开始、23:28:38 就 `休息 111s`，把时长顶穿。
- **修法**：`rest(ctx, maxMs = deadline - now)`，休息按剩余时间裁剪；剩不到 5 秒就不休息。

### 15.5 性能：为什么「剪枝」救不了一屏十几秒

- 实测 `快照耗时 17959ms / 19953ms / 18139ms / 17336ms / 19070ms`，同时也有
  `1597ms / 1683ms / 196ms / 719ms`。日志里 `遍历 1200 节点`（撞 `MAX_NODES` 上限）、
  `保留 ~280 条`。
- 试过两件事，**都没解决**：
  1. `pruneOffscreen`（整棵屏外子树不展开）：只命中 `剪枝 0~2` 棵，耗时不变。
  2. `!node.isVisibleToUser` 也当剪枝条件：35 趟里只有 2 趟剪掉 89 个节点，
     但每节点要多一次跨进程调用 —— **已撤掉**，只留 bounds 判定版。
- 结论：开销在「1200 个节点 × 每节点数次跨进程调用」，且 IPC 延迟本身被系统节流。
  缓解手段只有「把识别耗时扣进停留时长」（已实现）。
