# 抖音定位配置说明

> 适用版本：M1 起
> 对应文件：`app/src/main/assets/douyin_locator.json`
> 加载代码：`engine/LocatorConfig.kt`（`LocatorConfigLoader`）

这份配置决定「脚本怎么在抖音界面上找到东西」。抖音版本不受限制，任何写死在代码里的
控件 id 都可能在下个版本失效，所以定位规则**全部外置到 JSON**，改版时改文件、重新打包即可，
不用碰引擎代码。

当前 `version: 12`，`pages` / `targets` 已在抖音 40.8.0 上真机全量校准（见 §9）。
剩余未在校准范围内的项记在 `_unverified_targets` 里（例如 `live_comment_send` 需要点开评论面板
才会出现「发送」；部分直播间底栏没有独立连线按钮，流程记警告后跳过）。新增或改版后仍必须按
第 4 节重新校准，否则大概率每步都超时。

---

## 1. 文件结构

```jsonc
{
  "_note": "...",              // 说明性文字，代码不读
  "_unverified": true,         // 仅人工标记，代码不读
  "version": 12,               // 配置版本号，只用于日志排查（v11 = 加 overlays，v12 = 加私密账号判据）
  "excludeNicknames": ["我", "作者", "主播"],   // M2：采集评论时直接丢弃的昵称
  "privateAccountHints": ["私密账号", "已申请"], // 私密账号判据（全等匹配），见 §3.6

  "pages": {                   // 页面识别规则（加权投票）
    "HOME": {
      "threshold": 5,          // 得分 ≥ 该值才认定处于此页面
      "features": [            // 一条 = 一个证据 + 权重
        { "w": 3, "type": "text", "value": "首页" }
      ]
    }
  },

  "targets": {                 // 命名目标（被步骤/流程按名字引用）
    "search_entry": { "type": "descContains", "value": "搜索" }
  },

  "overlays": {                // 浮层识别（v11 起），命中后只允许按返回，见 §3.5
    "GIFT_PANEL": { "threshold": 5, "features": [ /* ... */ ] }
  }
}
```

## 2. `type` 的六种取值

| type | 含义 | 匹配方式 | 备注 |
|---|---|---|---|
| `text` | 节点 `text` 属性 | **全等** | 最严格，适合按钮文案 |
| `textContains` | 节点 `text` 属性 | 包含 | 适合「搜索 xxx」这类带变量的文本 |
| `desc` | 节点 `contentDescription` | **全等** | 图标按钮通常只在此属性上有文字 |
| `descContains` | 节点 `contentDescription` | 包含 | 同上，文案带变量的场景 |
| `id` | `resourceId` | 全等，需带完整前缀 | 形如 `com.ss.android.ugc.aweme:id/xxx`；抖音大量节点无 id，**不要当主力** |
| `image` | 图像模板匹配 | 相似度 ≥ `threshold`（默认 0.82） | **未接入**，配置里写了也不会命中，见第 6 节 |
| `editable` | 节点的 `isEditable` | — | **不需要 `value`**。输入框的文案不可靠时的唯一可靠判据，见 §9.3 |

匹配前会 `trim()`，空白字符串视为不存在。只在**当前活动窗口**的节点树里找，
遍历上限 1200 个节点（抖音的树很深，全量遍历会拖到每步几百毫秒；
1200 这个数是实测出来的，见下表最后一行）。

## 3. 加权投票是怎么判的

引擎对每个页面把所有 `features` 逐个查一遍，命中就累加 `w`，最后取**得分最高且过阈值**的那个：

```
score(HOME)  = 3(首页) + 3(朋友) + 2(消息) = 8  ≥ 5   ✅ 命中
score(SEARCH) = 3(搜索… ) + 0 + 0          = 3  < 4   ✗
→ 判定 HOME，得分 8
```

这样设计的理由是**容忍局部失效**：抖音某次改版把「朋友」tab 改名了，HOME 仍然拿 5 分
（= 阈值）继续命中，只是日志里少一条证据；如果写成「必须命中所有特征」，改一个字就全线崩。

配置里的几条硬性校验（在加载期完成，坏规则会被**跳过并告警**，不会让应用崩）：

| 校验 | 不通过时的行为 |
|---|---|
| `features` 为空或全部非法 | 跳过该页面规则 |
| `threshold` ≤ 0 | 跳过该页面规则 |
| `threshold` > 所有 `w` 之和 | 跳过并明确告警「永远无法命中」——这条最容易写错 |
| 有效页面规则为 0 | 整体降级到 `LocatorConfig.fallback()` |

`targets` 里没有被任何步骤引用的条目是允许的（先备着，M2/M3 用），缺失才会在运行时
报「配置中不存在目标 xxx」并让那一步失败。

## 3.5 `overlays`：浮层识别（v11 起，2026-10-29）

`pages` 判「现在在哪一页」，`overlays` 判「有没有东西盖在上面」。两者独立：观众列表是
**半屏浮层**，盖住下半屏但直播间特征还在，`detect()` 依然返回 `LIVE_ROOM`——所以
**不能拿页面判定当浮层的前置门禁**（第一版就这么写的，观众列表 14 秒没被关掉）。

```jsonc
"overlays": {
  "GIFT_PANEL": {
    "label": "礼物面板",        // 只用于日志
    "threshold": 5,
    "features": [               // 权重字段同样是 w —— 写成 weight 会被 optInt("w",1) 当成 1 分，规则静默失效
      { "type": "text", "value": "赠送",     "w": 3 },
      { "type": "text", "value": "双击赠送", "w": 3 },
      { "type": "text", "value": "钻",       "w": 2 },
      { "type": "desc", "value": "关闭",     "w": 1 }
    ]
  }
}
```

- 判定算法与 `pages` 相同（累加命中权重，过阈值即命中）；命中多个时取**得分最高**的。
- `threshold > 权重总和` 的规则在加载期直接丢弃——配错了等于永不命中，留着只会误导。
- 键名以 `_` 开头视为注释跳过（`parseOverlays` 与 `parse` 同一规则）。
- **命中后唯一允许的动作是 `back()`**，绝不点浮层内控件：礼物面板里全是「赠送/送出/充值」，
  误点直接产生费用。关不掉就交回调用方，不连按返回（会退出真实直播间）。

已校准的六条与阈值依据见 `运行期容错与悬浮面板.md` §9（v13 起新增 `LIVE_PROFILE_FULL`，
主播头像弹出的**全屏**主页；它与半屏的 `PROFILE_CARD` 是两套形态，别合并）。

### 遇到「没收录的浮层」怎么办

不要凭截图猜文案——先看日志。`RecoveryWait` 在页面读不出来时会 dump 一次现场：

```
W/自愈等待: 仍读不出来，屏上文案（补 overlays 规则用）：
  text=[…] desc=[…]
```

照着那份真实 `text/desc` 加一条多特征规则即可（单特征很容易误杀：`人气开场` 是直播间
常驻徽标，`在线观众` 在右上角也有）。**改完必须真机验证「正常直播间不误触发」**，
因为误命中的代价是 `back()` 直接退房。

## 3.6 `privateAccountHints`：私密账号判据（v12 起，2026-10-29）

```jsonc
"privateAccountHints": ["私密账号", "私密帐户", "申请关注", "已申请", "已提交请求",
                        "等待通过", "请求关注", "已发送关注请求", "关注请求已发送"]
```

一组**文案**（不是 Target），命中即判定「对方是私密账号」。

- **必须全等匹配**：包含匹配会让「关注」命中「申请关注」，把所有人都判成私密账号。
  这也是它不能写成 `Target` 的原因——`Target` 的 `textContains` 是包含语义。
- 同时比对 `text` 与 `contentDescription`（申请态多数在按钮 text 上，有的版本挂 desc）。
- 只看屏幕 **30% 以下**：顶部是直播间头部，主播自己的「关注」按钮在那儿。
- 判据**优先级低于「已关注」**：先看有没有「取消关注/互相关注」，有就是真关注成功，
  绝不会因为文本里有「私密账号」字样把成功案例算成失败。
- 缺这一段时用 `LocatorConfig.DEFAULT_PRIVATE_HINTS`，旧配置文件不会丢这个能力。

遇到没收录的新文案：超时日志会打出「弹层文案：…」，照抄进来即可，不用改代码。
细节见 `M2-直播间评论关注.md` §13。

## 4. 上真机后怎么校准（必做）

### 4.1 抓一份真实界面结构

```bash
# 手机开着抖音，停在要校准的页面，然后
adb shell uiautomator dump /sdcard/ui.xml
adb pull /sdcard/ui.xml
```

> Windows / Git Bash 下 `adb shell` 后面的 `/sdcard/...` 会被 MSYS 当成**本地路径**改写，
> 必须加 `MSYS_NO_PATHCONV=1`，否则命令看似成功、远端其实没有文件。

### 4.2 从 dump 里挑特征

```bash
# 挑 text（注意：text 属性出现在 resource-id 之前，先抓整个 <node ...> 再取字段）
grep -o '<node [^>]*text="[^"]*"[^>]*>' ui.xml | head -40

# 挑 contentDescription（图标按钮一般只在这里有值）
grep -o 'contentDescription="[^"]*"' ui.xml | sort -u | head -40

# 挑 resourceId
grep -o 'resource-id="com.ss.android.ugc.aweme:id/[^"]*"' ui.xml | sort -u | head -40
```

### 4.3 挑特征的三条原则

1. **优先选「这个页面独有」的文案**。比如「猜你想搜」只在搜索页出现，权重给 3；
   「搜索」两个字首页也有，给了会误判。
2. **每个页面至少留 3 条特征、总权重至少是阈值的 1.5 倍**，留出容错余量。
3. **不要用「点赞数」「粉丝数」这类会变的文本做全等匹配**，要用 `textContains`（如 `粉丝`）。

### 4.4 判定阈值定多少

经验值：`threshold ≈ 总权重 × 0.6`。

- 太低 → 首页和搜索结果页会互相误判（两者都有「用户」这类词）；
- 太高 → 抖音小改版就判不出来。

### 4.5 改完怎么验证不用连设备

应用内 **悬浮按钮 → 自检 → 「识别当前页面（只读）」**，会弹出：

```
判定：USER_PROFILE
得分：7（阈值 5）
最接近：USER_PROFILE
前台包名：com.ss.android.ugc.aweme
页面规则数：5

命中证据：
text:"关注"(3) + textContains:"粉丝"(2) + textContains:"获赞"(2)
```

它**只读不发任何操作**，可以反复试。判定不对就看「最接近」和「命中证据」两行，
基本能直接看出是缺特征还是阈值写歪了。

## 5. 改配置后必须做的事

**校准阶段（热加载，不必打包）**：

1. 改本文件 → 覆盖到设备 `<app>/files/douyin_locator.json`：
   ```bash
   adb push douyin_locator.json /data/local/tmp/locator.json
   adb shell run-as com.example.dgg cp /data/local/tmp/locator.json files/douyin_locator.json
   ```
2. 重启应用（`am force-stop` + `am start`，引擎缓存在内存里，必须重启进程）；
3. 日志里会打印 `已加载 vN（来源：外部文件）` —— 看到「来源：外部文件」才算生效。

> 路径刻意是**内部** `files/`：`/sdcard/Android/data/<pkg>/files` 在 Android 11+ 连
> `run-as` 都进不去（FUSE + SELinux），adb 无法投递文件。

**发布阶段**：

1. 把改好的配置同步回 `app/src/main/assets/douyin_locator.json`；
2. `version` 加 1；
3. 重新打包（assets 是编译进 APK 的）。

外部文件解析失败会自动回退 assets，不会因为一份写坏的配置让任务彻底跑不起来。

## 6. M2 直播间关注用到的定位项

直播间评论关注（`engine/flow/FollowFromLiveFlow.kt`）用这几个目标，缺任何一个都会在启动时直接中止并说明原因：

| 目标名 | 用途 | 缺了会怎样 |
|---|---|---|
| `live_comment_line` | 主路径：收整行文本，按 `：`/`:` 切出昵称 | 与下一项都缺 → 拒绝启动 |
| `live_comment_nickname` | 可选主路径：直接收集评论昵称节点 | 当前抖音版本**没有**这个节点，配置里已注释掉 |
| `follow_button` | 弹层里的「关注」 | **拒绝启动**（没有它就不知道该点哪） |
| `followed_button` | **已关注态**的文案。抖音 40.8.0 实测是「取消关注」（对方也关注你时是「互相关注」，代码里有兜底） | **拒绝启动**（没有它就无法校验，会变成假成功） |

`close_card` 已从配置与代码中移除，原因见 §6.4 —— 那是个会把用户踢出直播间的陷阱。

### 6.1 为什么弹层按钮要按位置过滤

抖音的半屏资料卡多数是 **Activity 内的浮层**而不是独立窗口，所以 `rootInActiveWindow`
会把直播间背景一起返回——**主播自己也有一个「关注」按钮**（在右上角头部）。

如果不区分，会出两个问题：

1. 可能点到主播的关注按钮，关注了错的人；
2. 更糟：主播若已关注，头部按钮显示「取消关注」，会被误判成「这个候选人已关注」，
   于是**每一轮都跳过**，表现成「任务在跑但一个人也没关注」。

所以代码里对「关注/已关注」候选节点做了两个约束（`FollowFromLiveFlow.findCardButton`）：

- **排除屏幕顶部 30%**（`TOP_EXCLUDE_RATIO = 0.30`）——头部那颗按钮在那个区域；
- 在剩余候选里**取面积最大的那个**——弹层的主按钮是整行大按钮，头部的是小按钮。

> 这是全配置里唯一写死的**位置假设**。如果真机上弹层按钮恰好落在顶部 30% 内（例如小屏机型的
> 居中弹窗），需要把 `TOP_EXCLUDE_RATIO` 调小。校准时先看日志里「没等到弹层里的关注按钮」
> 是不是稳定复现——是的话优先怀疑这个阈值，而不是怀疑定位。

**2026-10-27 实测（OPPO Android 17 / 抖音 40.8.0）**：这个假设成立。
资料卡是**底部半屏浮层**，「关注」按钮在 `[318,1632][780,1740]`（屏高 2412 的 68%），
主播那颗在 `[360,156][483,240]`（8%），`TOP_EXCLUDE_RATIO = 0.30` 把两者干净分开。

两个容易踩的细节：

- 截图上的按钮文案是「**+关注**」，但无障碍读到的 `text` 只有「**关注**」——「+」是装饰图标，
  不进文本。所以配置用 `text` 精确匹配「关注」是对的，不要被截图误导去改成 `textContains`。
- 已关注后按钮变「**取消关注**」，但节点树里**仍残留**一个 `text="关注"` 的 TextView。
  这意味着 `follow_button` 在已关注状态下也会命中，因此**必须先判「已关注」再判「可关注」**，
  否则会点在那颗已经变成「取消关注」的按钮上，把已关注的人取关。

### 6.2 评论昵称采集的两级策略（实测后已简化）

1. `live_comment_line` 收整行 → 按 `：`/`:` 切分取前段（**40.8.0 实测的唯一可行路径**）；
2. 可选：若 `live_comment_nickname` 存在且命中，优先用独立昵称节点；
3. 过滤：长度 2–24、非纯数字、不含冒号、不含系统提示词（`来了`/`送出`/`关注了主播`/`加入粉丝团`…）、
   不以 `[` 开头（文本化表情）、不在 `excludeNicknames`、不在本轮已处理集合、不在持久化「已关注」名单。

日志会分开报「原始 N 条 → 可用 M 人」，以及各条排除原因的数量——**「没采到」和
「采到但全是已关注的」是两种完全不同的故障**，不能混在一起。

### 6.3 抖音 40.8.0 实测结构（2026-10-26，Android 16 / 1200×2608）

这一节的每条都是真机 `dump` 出来的，不是推测。改配置前先读这一节。

**1. `resource-id` 全部是混淆短码。** 实测出现 `j_x` / `gxu` / `5ym` / `0py` / `h7l` / `oiq`，
随版本变化且毫无语义。**任何依赖 `id` 的定位都注定在下个版本失效**，所以本配置只用
`text` 与 `content-desc`。

**2. 评论是「一整行一个节点」，昵称不是独立节点。**

```
text = "‎紫丽丽：喜欢灰灰主播[调皮][调皮][调皮][凋谢][…]"   bounds=[36,1915][846,1933]
```

- 格式是 `昵称：正文`，分隔符是**全角冒号**；
- 表情被**文本化渲染**成 `[调皮]` 这种方括号词；
- 行高只有 18px，且 `clickable=true`。

**3. 文本开头有 U+200E 零宽字符。** 上面 `‎紫丽丽` 的首字符是 `LEFT-TO-RIGHT MARK`。
不清理会导致：同一人换条评论就被当成新面孔（去重失效）、用昵称回查节点匹配不上。
代码里 `sanitize()` 统一剔除 `U+200B..200F`、`202A..202E`、`2060..2069`、`FEFF` 与控制字符。

**4. 点击必须落在**行首昵称区**。** 整行宽度可达 800px，正文区点击不会打开资料卡。
`Actions.tapNickname()` 把落点限制在左侧 2%~28%（且不超过 150px）内。

**5. 直播间右上角的「关闭 按钮」是退出直播间**，`desc="关闭 按钮"` / `desc="关闭"`。
拿「关闭」当弹层关闭键，弹层一消失就会点它 → **每轮都被踢出直播间**。见 §6.4。

**6. 「在线」「送礼」的真实文案是 `779在线观众`（desc）与 `礼物`（desc）**，
所以 LIVE_ROOM 的判定特征按实测改为：`说点什么`(3) + `在线观众`(2) + `礼物数`(2)
+ `本场点赞`(2) + `关闭 按钮`(1)，阈值 5。实测该页面得分 7~9，可稳定命中。

### 6.4 为什么不能点「关闭」按钮关弹层

抖音直播间的「关闭」有两层含义：右上角的**退出直播间**，以及弹层自己的关闭键，
两者 `desc` 都含「关闭」。一旦配置写了 `descContains: "关闭"`，代码就会在
「弹层已经不在」的情况下点到退出键，把人踢出房间，之后每一轮都在错误的页面上空跑。

现在的做法（`FollowFromLiveFlow.closeCard`）：

1. 先确认弹层还在（还能找到「关注/已关注」按钮）；
2. 还在 → 用**系统返回**关闭（`performGlobalAction(BACK)`），不点任何「关闭」；
3. 已经不在 → 什么都不做，避免多余的返回退掉直播间。

## 7. 真机调试通道（这台机器上没有别的路）

本机是 Xiaomi / Android 16（HyperOS），三个限制叠加，常规调试手段全部失效：

| 手段 | 结果 | 原因 |
|---|---|---|
| `adb shell input tap` | 被拒 | 缺 `INJECT_EVENTS` |
| `adb shell settings put secure …` | 被拒 | 缺 `WRITE_SECURE_SETTINGS`（小米移除） |
| `adb shell pm grant …` | 被拒 | 缺 `GRANT_RUNTIME_PERMISSIONS` |
| `uiautomator dump`（直播间内） | 报 `could not get idle state` | 画面持续动画，UI 永不 idle |
| `am broadcast` 到静态 receiver | **静默丢弃** | Greezer：`need cached broadcast` |
| `adb logcat` 看本应用日志 | 看不到 | HyperOS 过滤第三方应用日志 |

所以代码里内置了一条**文件命令通道**（`service/DebugChannel.kt`，仅 debuggable 构建启动）：

```bash
# 触发：写入命令文件
adb shell "run-as com.example.dgg sh -c 'echo DUMP > files/debug_cmd'"

# 支持的指令
DUMP                 # 把活动窗口节点树按 uiautomator 同格式写入 files/dump/window.xml
PAGE                 # 页面判定结果写入 files/dump/page.txt
TAP x y              # 用无障碍 dispatchGesture 点击（绕过 adb 限制）
SWIPE x1 y1 x2 y2    # 滑动
BACK                 # 系统返回

# 取结果
adb shell "run-as com.example.dgg cat files/dump/window.xml" > window.xml
# 用项目自带脚本解析（与 uiautomator dump 同格式，可直接复用）
python tools/parse_dump.py window.xml
```

运行日志同步写到 `files/runtime.log`（因为 logcat 拿不到）：

```bash
adb shell run-as com.example.dgg tail -30 files/runtime.log
```

> 通道启动点同时挂在**无障碍服务 `onCreate`/`onServiceConnected`** 与 **`MainActivity.onCreate`**。
> 只挂服务是不够的：HyperOS 在覆盖安装/强杀后不一定会重新回调 `onServiceConnected`，
> 表现为命令文件写进去却没人消费。发现不消费就 `am start` 一次主界面。

## 8. 已知限制（M1/M2）

| 限制 | 影响 | 计划 |
|---|---|---|
| `image` 类型恒不命中 | 纯图标、无任何文字与描述的按钮定位不到 | M2 真机校准后按需引入（`MediaProjection` + 模板匹配） |
| 只遍历当前活动窗口 | 弹窗覆盖时可能判成弹窗背后的页面 | 直播间场景已用**位置过滤**规避，不做多窗口合并 |
| 遍历上限 1200 节点 | 极端页面（节点数 >1200）深处仍可能漏 | 按需分层遍历 |
| **直播频道预览页有 973 个节点** | 800 的上限会在到达「点击进入直播间」之前截断，`find` 返回 null，表现为「屏幕上明明有这个按钮」 | 已把上限提到 1200（实测覆盖该页） |
| 去重靠昵称 | **同名不同人会被误杀** | 可访问性拿不到 uid，这是已知代价，不假装准确 |
| 弹层按钮的 30% 顶部排除 | 小屏机型上可能误杀真实按钮 | 真机校准 `TOP_EXCLUDE_RATIO` |
| 昵称区点击位置 | 昵称很长（>8 字）时落点可能落到正文，导致不弹资料卡 | 实测长昵称场景后再调 28%/150px 上限 |
| 资料卡关闭只走返回键 | 个别版本弹层不响应 BACK | 待实测；届时改用「点卡片外空白」而非「点关闭」 |
| 无坐标兜底 | 定位不到就失败，不「凭比例猜一下点哪」 | **不打算做**——盲点是最容易被判机器行为、也最容易误触（比如点到「取消关注」）的路径 |

### 9.1 搜索页的真实文案与旧版不一样

40.8.0 的搜索入口页**没有**「猜你想搜」也**没有**「取消」，实际是：

```
TextView  text='猜你想看'                      ← 区块标题（旧版是「猜你想搜」且写在 desc 上）
ViewGroup desc='古的咪路人视角视频搜索，按钮'    ← 一排推荐搜索卡，文案以「搜索，按钮」结尾
TextView  text='语音搜索'                      ← 底部语音入口
TextView  text='搜索' desc='搜索'              ← 右上搜索按钮（**搜索结果页也有这颗**）
```

所以「搜索」这一颗单独只有 3 分，**必须再凑 2 分才算搜索页**，否则搜索结果页会被判成搜索页。

### 9.2 搜索输入框不能用文本定位（新增 `editable` 类型）

搜索框里默认填的是**推荐搜索词**（实测是某个视频标题 `古的咪路人视角视频`），
既不是「搜索」也不是空串——按文本永远命不中。同理直播间的「说点什么」命中的可能只是提示节点。

因此 `Target.Kind` 增加 `editable`：不比对任何文本，直接找 `isEditable` 的节点，配置写法：

```json
"search_input": { "type": "editable" }
```

不需要 `value` 字段（解析器对 `editable` 跳过 value 校验）。

### 9.3 ⚠️ 直播间「小心心」= 1 钻付费礼物

直播间底栏四颗：`表情入口` / **`小心心`** / `礼物` / `更多面板 按钮`。
`desc='小心心'` 点下去弹「送出小心心礼物需支付1钻，确定支付？」——**它不是点赞按钮**。

- 配置里不要出现指向它的目标（`live_like_button` 已删除）；
- `Actions.tapNode` 有**花钱守卫**：text/desc 命中「小心心/支付/充值/购买/打赏/送礼」直接拒点并记 error。
- 点赞只能双击空白画面（`Actions.doubleTap`），落点用 `freePointIn()` 校验底下没有可点控件。

### 9.4 性能：一次遍历 + 快照

实测单品：这台真机上**一趟全树遍历（647 节点）约 1.4 秒**（每次 `getChild`/`text` 都是跨进程调用）。

旧实现给每条特征各遍历一遍，21 条特征 ⇒ 每次页面判定 30 秒，
表现是「点了开始之后半分钟界面毫无动静」，一次 11 秒的等待要跑 32 秒。

现在：
- `Actions.snapshot()` 一次遍历抓成 `NodeFacts` 列表，页面判定与风控检查都在内存里比对；
- 快照有 700ms 缓存，**任何手势（点击/滑动/返回/输入）之后立刻失效**；
- 实测启动到判定从 28 秒降到 **2.3 秒**。

### 9.5 判「不在直播间」要连续确认两次

收键盘、窗口切换的中间态会让某一刻读到空窗口（`UNKNOWN 0/6`）。
单次误判就按返回，会把好好的直播间退掉（实测踩过：日志里「已发评论 1」紧跟「已经不在直播间」）。

现在 `ensureLiveRoom()` 要求**连续 2 次**判定非 `LIVE_ROOM` 才按返回，
并且**先确认前台是抖音**——返回键作用于当前前台应用，按错了退的是别的应用。
