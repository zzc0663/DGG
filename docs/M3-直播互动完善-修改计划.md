# M3 直播互动完善 · 修改计划

> 基线：vc59 / 1.4.29（设备 API 37 / 1080×2374 / 抖音 40.8.0）
> 目标：vc60 起，分两阶段交付

## 一、先看事实：M3 现在是什么状态

### 1.1 它已经很久没被跑过了

拉服务端最近 15 条日志上报（2026-10-30 ~ 10-31），**没有一次 M3 运行**，全部是 M2「直播间关注」。

```
R-20261031-81F05E vc58  ← 全是「直播间关注: 已关注「…」进度 3/200」
R-20261030-774556 vc53  ← 同上
R-20261030-A839D7 vc45  ← 同上
```

最后一次 M3 真机跑通是 **2026-10-27**（`docs/M3-直播互动.md` §5，抖音 40.8.0）。
此后经历了 vc41 改名、vc54~vc59 四次界面重排、`bindRangedIntField` 重写 —— **M3 一次都没跑过**。
所以「完善」的第一件事不是加功能，是**先确认它现在还能不能发出一条评论**。

### 1.2 功能矩阵

| 能力 | 状态 | 代码位置 |
|---|---|---|
| 发评论（预设 / 复制） | 有 | `LiveInteractFlow.sendComment` |
| 每 N 条评论触发一次点赞 | 有 | `likeBurst`（双击空白画面） |
| 申请连麦（只一次、不确认） | 有，多数房间没入口 | `tryApplyMic` |
| **本轮目标 / 每日上限** | **完全没有** | `while (true)` 只响应 `stop` |
| **定时休息** | **完全没有** | 同上 |
| **话术编辑** | **只能替换 `<app>/files/live_comments.json`** | `PresetComments` |
| 系统推荐进入 | **假选项**（warn 一句后按手动跑） | `LiveInteractFlow:58-63` |
| 状态条分母 | 无（`publish(target = 0)`） | `LiveInteractFlow:80` |
| 发送成功判据 | 弱：只看「说点什么」占位符是否回来 | `awaitSubmitted` |

### 1.3 三个必须承认的问题

**① 无限评论 —— 唯一的「没有闸」的流程。**
M2 有目标数 / 每日上限 / 定时休息三道闸（`FollowFromLiveFlow:62,116-133`），M3 一道都没有。
评论是抖音审核最严的动作，一条不设闸的 `while (true)` 是把「临时限流」升级成「封号」最快的路径。

**② 默认模式是「复制别人评论」**（`Settings.commentMode = 0`）。这是内容风险最高的一档，却是默认值。

**③ 复制模式拿不到正文会静默改发预设话术**（`buildComment` 的 `?: run { … fallback }`）。
用户选的是「复制」，实际发出去的是话术库里的句子，界面上只有一行 `LogStore.w`，悬浮窗看不到。

### 1.4 热路径很可能已经跑不动（待基线日志确认）

`find()` 是**无缓存的全树 BFS**（`Actions.findBy`，上限 1200 节点），而直播间播放时的全树遍历实测
**5~16 秒**（`R-20261030-A88080`：610 节点 / 16099ms；健康值 ≈2ms/节点）。一条评论要跑 4 趟：

```
find(comment_input)        → 全树        约 5~16s
findEditable()             → 全树        约 5~16s
waitFor(send, 3000)        → 全树×1      超时后基本只来得及扫 1 趟
awaitSubmitted()           → 全树×1      3s 窗口内最多 1 趟，多半判「未提交」
```

⇒ 单条评论 30~60 秒，而且 `awaitSubmitted` 的 3 秒预算**装不下一趟遍历**，
大概率恒定判失败 ⇒ 3 次后 `FlowAbortException("连续 3 次发送评论失败")`。
这条只有真跑一轮才能确认，不能靠猜。

## 二、阶段 A（vc60）：让它可用 + 加闸

### A1 安全阀（Settings 新增 4 项）

| 字段 | 默认 | 范围 | 语义 |
|---|---|---|---|
| `commentTarget` | **20** | 1 ~ 2000 | 本轮发满即正常结束（→ 状态条有分母） |
| `commentDailyLimit` | **200** | 1 ~ 2000 | 当日累计上限，到点不再起流程 |
| `restComment` | **true** | — | 定时休息开关 |
| `commentRestAfterN` | **10** | 1 ~ 500 | 每发 N 条 |
| `commentRestSeconds` | **60** | 1 ~ 600 | 休息 M 秒 |

- 当日计数落 `InteractStore`（新建，照 `FollowedStore` 的 `today()/rolloverIfNeeded()` 写法，
  key = `comment_day` / `comment_day_count`），**跨进程、跨场次累计**。
- 达到每日上限 → `ctx.publish()` + 正常 `return`（引擎置 `STOPPED`「流程执行完毕」），**不抛异常**
  （抛 `FlowAbortException` 会变成红色 ERROR + 「重试」，语义不对）。
- 发满 `commentRestAfterN` 条 → 休息 `commentRestSeconds` 秒，走 `ctx.settleLong()` 分片，
  每片查暂停/停止。
- `publish(target = commentTarget, followed = sent)` ⇒ 状态条显示 `已发评论 7/20`。

### A2 默认模式改「预设」+ 复制降级要可见

- `Settings.commentMode` 默认 `0 → 1`（预设）。**不做存量迁移**：老用户存过的 0 就还是 0，
  这是他自己选的；只改新装默认值。
- `buildComment` 的 fallback 保留（否则复制模式在没人说话的房间里会空转），但必须可见：
  `ctx.publish(message = "本轮没有可复制的正文，改发预设话术")` + `LogStore.w`。同一场次只提示一次。

### A3 话术编辑（App 内）

- 直播卡「评论模式」行右侧加 `tv_edit_presets`「编辑话术 ›」（12sp 品牌红）。
- 点开对话框：一个多行 `EditText`（每行一条）+「恢复默认」+「保存」。
  - 载入：`PresetComments.load(externalOnly = …)` 读**当前生效**的列表（外部文件优先，否则 assets）
  - 保存：写 `<files>/live_comments.json`（格式与 assets 一致），然后 `PresetComments.load(forceReload = true)`
  - 校验：逐行 trim → 去空行 → 去重 → 单条 ≤ 30 字 → 总数 1~100 条。
    不合法就 toast 具体哪一行，**不写盘**（宁可拒绝，也不要写进去一个半残列表）
  - 「恢复默认」= 删除外部文件 + reload
- 复制模式选中时该入口置灰（复制模式不用话术库）。但**编辑入口始终可见**，避免用户找不到。

### A4「系统推荐」怎么处理（三选一，见待定事项）

推荐做法：**删掉这一行**。产品原则是「用户自己进直播间」（`docs/M3-直播互动.md` §1 的「不做」），
而这个选项从上线起就没实现过，选中只会在日志里写一行 warn。删掉后 `enterMode` 字段与
`LiveInteractFlow:58-63` 的 warn 分支一并删，和 vc49 删 `calMode` 同一套处理。

### A5 发送判据加强（低成本版）

`awaitSubmitted` 现在只判「占位符回来了」。加一条**正向证据**：同一趟扫描里同时确认
「屏上已没有 `isEditable` 的节点」或「可编辑节点文本为空」。两者都不满足才算未提交。

⚠️ 不加额外遍历次数 —— 直播间一趟就是几秒，多加一趟等于把 3 秒预算彻底撑爆。
所以这一条**等 A6 的局部化落地后再上**，否则改了也不会变准。

### A6 热路径局部化（阶段 A 的最后一项，依赖基线日志）

思路与 vc36 对 M2 做的一样：**不再信任全树，改从已知节点向上/向下限定子树。**

1. `find(comment_input)` 拿到的就是输入条里的节点 —— 取它的 `parent` 走 2~3 层作为**底栏容器**，
   日志打出容器节点数（验证这个假设只需一次真机日志）。
2. 后续 `findEditable(container)`、`find(send, container)` 全部限制在容器内。
3. 发送面板若不在底栏容器内（要点开评论面板才知道），退化为「容器 → 容器 parent → 全树」三级，
   每级耗时写日志，取第一个命中的。
4. `awaitSubmitted` 同理，且**只判一次**（点完发送等 800ms 再扫），把 3 秒轮询删掉。

验收标准：单条评论从 30~60 秒降到 **≤8 秒**（不含评论间隔），日志里能看到 `容器内 N 节点 / Xms`。

## 三、阶段 B（vc61）：按基线再决定

候选（都不进 vc60，避免一次改动太大无法归因）：

| 项 | 说明 |
|---|---|
| 点赞独立节奏 | 现在只有「每 N 条评论赞一次」；补「每 M 分钟赞一次」，支持只点赞不评论 |
| 连麦后暂停评论 | 上麦期间发评论等于开着麦克风自言自语；需要「检测到连线成功 → 暂停 → 断开后恢复」 |
| `idleLive` / `continueAfterMic` | 两个死开关（现在置灰）；真正的语义属于这一阶段 |
| 点赞有效性校验 | 目前无法验证（万人房自然增长淹没）；可试「点赞计数节点」定位，成功率未知 |

## 四、布局与高度

直播卡现在 8 行（每行 40dp + 8dp 间距），加 3 项、删 1 行：

```
进入方式  [手动][系统推荐]        ← A4 删掉（-40dp，仅当删该选项时）
评论间隔  [5] ~ [15] 秒
评论模式  [复制][预设]   编辑话术 ›
启动后自动复制…（说明单行）
评论目标  [20] 条 · 上限 [200] 条     ← 新增 1 行（+40dp）
休息      (●) 每 [10] 条 [60] 秒      ← 新增 1 行（+40dp）
自动申请连麦                      (○)
评论时自动点赞                    (●)
点赞触发  [3] 条
每次点赞  [5] ~ [10] 次
```

净增 **+40dp**（删 1 行、加 2 行），整页从 ~830dp 到 ~870dp ≈ 1.45 屏。
若 A4 选择保留「系统推荐」，则 +80dp ≈ 1.55 屏。
