## 1. 悬浮窗：胶囊 ⇄ 展开面板

### 为什么改

旧版悬浮窗只有一条胶囊 + 一个「停止」键。点「停止」的后果是：

1. `ControlService.stop()` → 引擎停 → 前台服务 `shutdown()` 里顺手 `stopService(FloatWindowService)`
   → **悬浮窗当场消失**；
2. 用户既看不到「为什么停了」（风控？异常？到目标了？），观感上也像是被踢回了应用。

### 现在的结构

```
收起态：[●] 运行中 3/180 [⌄]          ← 点 ⌄ 展开
展开态：┌────────────────────┐
        │ ● 运行中          [⌃] │
        │ 3/180                 │   ← 大红字，一眼看清进度
        │ 已关注                 │
        │ 挑中「xxx」            │   ← message，含"为什么停"
        │ [ 暂停 ]  [ 结束 ]     │
        │ ─────────────────     │
        │ 今日累计 25      重置  │
        │ [   关闭悬浮窗   ]     │
        └────────────────────┘
```

| 按钮 | 行为 |
|---|---|
| 暂停 / 继续 | `TaskEngine.pause()` / `resume()`。暂停期间不产生任何界面动作，只保留风控检查。**唯一例外**是 `PAUSED_WAIT` 自愈态：为了探测「评论是否恢复」需要把抖音拉回前台并关掉遮挡浮层，但**永不点赞、不关注、不点评论行**（见 §8） |
| 结束 | **只调 `TaskEngine.stop()`**：不撤悬浮窗、不启动任何 Activity，抖音保持在前台 |
| 关闭悬浮窗 | 唯一会撤掉悬浮窗的操作 |
| 重置 | 清「今日累计」，**不动已关注名单**（名单是去重用的，清了会重复关注同一批人） |

终态（已停止 / 风控停机 / 异常停止）时：面板**自动展开**显示结论，按钮从「结束」变成「关闭」，
悬浮窗**不会自己消失**——必须用户点关闭。

### 唯一的例外

从抖关关界面点停止（`EngineController.stop(this, ...)`）会顺手撤掉悬浮窗：此时它的终态面板
是重复信息，还挡着用户自己的界面。悬浮窗上点「结束」不走这条路径。

### 实测

```
22:39:45 I/悬浮窗: 悬浮窗「结束」被点击（当前 运行中）
22:39:45 I/悬浮窗: 任务已到终态（已停止），面板保留待用户关闭
22:39:45 I/任务结束：悬浮窗结束
22:39:45 I/前台服务: 前台服务已退出：任务进入终态：已停止（悬浮窗保留终态面板）

mCurrentFocus = com.ss.android.ugc.aweme/.live.LivePlayActivity   ← 仍是抖音，没退回应用
```

## 2. 人为切换直播间 → 继续执行

### 旧行为（错的）

`ensureLiveRoom` 连续 2 次判非直播间就按一次返回。用户手动滑到下一个直播间时，
转场动画期间页面判定是 UNKNOWN（命不中直播间特征），于是：

```
用户切到新直播间 → 判定 UNKNOWN → 按返回 → 退出新直播间 → 回到直播频道页 → 空转到中止
```

### 现在（`engine/flow/LiveGuard.kt`）

| 判定 | 处置 |
|---|---|
| `LIVE_ROOM` | 继续，不管主播换没换人（用户切到哪个房间就跟哪个） |
| `UNKNOWN` | **不按返回**，最多等 3 轮 × 10 秒。覆盖转场、加载、抖音冷启动 |
| `USER_PROFILE`（资料卡浮层） | 按一次返回关掉，再判 |
| 直播频道预览页 | 点「点击进入直播间」自己进房 |
| `HOME`（且是我们刚拉回来的） | 点顶部「直播」页签 → 再点进房 |
| 其它已识别页面 | 中止并说明。**不猜房间**——拿不到「该进哪一个」，乱点可能进到付费直播 |

关键点：**页面读不出来时绝不按返回**。UNKNOWN 可能是转场、加载、收键盘，
按下去退的是真实页面；只有「明确识别出是浮层」才允许按返回。

## 3. 退出抖音 → 自动拉回

`LiveGuard.relaunchDouyin()`：`DouyinLauncher.launch()` 最多 3 次，每次等 8 秒回到前台。

能成功的前提是**有悬浮窗权限**：Android 10+ 限制后台启动 Activity，但持有
`SYSTEM_ALERT_WINDOW` 的应用不受该限制。本应用本来就要求悬浮窗权限，所以这条路可用。

实测（按 HOME 键）：

```
22:38:55 W/直播守卫: 抖音已不在前台（用户切走了，或被系统回收）
22:38:55 W/直播守卫: 自动拉回抖音（第 1/3 次）
22:38:56 I/直播守卫: 抖音已回到前台            ← 0.4 秒
22:39:11 I/直播间关注: 已关注「* 尤尤-」，进度 2/175   ← 继续跑
```

拉回后如果抖音落在**直播频道预览页**（退出期间被系统回收后重启时常见），
会点「点击进入直播间」自动进房：

```
22:38:18 W/直播守卫: 停在直播频道预览页，点「点击进入直播间」自动进房
22:38:19 I/页面识别: 页面 → LIVE_ROOM（8/5）
22:38:19 I/直播守卫: 已自动进入直播间，继续执行
```

## 4. 一个顺带修掉的启动 Bug

`EngineController.start()` 原来无条件 `DouyinLauncher.launch()`。如果抖音**已经在前台**
（用户停在自己选好的直播间里），这个 launch 会让抖音重走启动流程 → splash → 首页/预览页，
用户精心选好的直播间当场没了，脚本随后只能报「不在直播间」。

现在先取当前前台包名，是抖音就不 launch：

```kotlin
val front = ActiveWindow.root(DggAccessibilityService.current)?.packageName?.toString()
if (front == DouyinLauncher.PACKAGE) {
    LogStore.i(TAG, "抖音已在前台，不再重复拉起（重复拉起会打断当前直播间）")
}
```

## 5. 追最新：从「整屏随机」到「加权最新」

### 不滑动的理由（四组真机实验，详见 `M2-直播间评论关注.md` §12.2）

| 操作 | 结果 |
|---|---|
| 评论区内 550px 上滑 | 切到下一个直播间 |
| 评论区内 120px 上滑 | 不切房间，但评论行 y 完全不变（列表不可滚） |
| 评论区内 120px 下滑 | 同上，没有出现更早的评论 |

所以「下滑到最新」在抖音直播里做不到（滑大了换房间、滑小了没反应）。
等价实现是**等列表自己滚到最新**，并只在最新那几个人里挑。

### 本轮新增

1. **加权随机**：最新一行的权重 3、第二 2、第三 1。
   三选一等概率会有 2/3 概率挑到不是最新的那个（观感就是"又在挑老观众"），
   而永远挑最底那一行又是明显的机器特征。权重随机两头都照顾。
2. **「人都处理过」不再当成故障**：
   - 屏幕上**读得到评论行**但行里的人都在本轮已处理名单里 → 最多少等 12 轮（约 1 分钟），
     日志写「这一屏 N 人都已处理过，等新评论进来」；
   - 屏幕上**一行评论都读不到** → 4 轮就中止（定位失效或被浮层盖住，等下去没意义）。
   旧实现混用同一个上限 4 轮，冷清房间会被误判成「脚本自己停了」。
3. **过滤未成型的行**：评论插入时有高度展开动画，实测读到过 **6px 高**的行
   （`行=[36,2164][780,2170]`），点上去落在空白，白等 6 秒超时。现在低于 20px 直接跳过。

## 6. 已知限制

- **UNKNOWN 与「真不在直播间」无法完全区分**。极端情况下（抖音卡在启动画面）会等满
  30 秒才报错，而不是立刻停。这是刻意选的：宁可慢，也不要误退用户的直播间。
- **预览页进的是第一个直播间**，不保证是原来那个。用户自己切了直播间时同样如此。
- 悬浮窗终态面板**不会自动消失**，会一直等到用户点「关闭悬浮窗」。这是「不退回应用」的
  代价；胶囊态很小，展开态由用户主动点开。
- **浮层识别靠文案**：现在改为 `assets/douyin_locator.json` 的 `overlays` 段驱动（加权多特征投票，
  见 §9），不再是硬编码三个词。抖音改版换了按钮文案仍会失效——失效表现是「探测不到浮层 →
  继续等」，**绝不会误点**，属于可接受的降级。
- 点评论行仍有概率点到礼物飘屏（打开礼物面板）。现在靠 §9 的浮层恢复自动按一次返回即可关闭，
  实测 30 秒内自愈、进度继续走。根治要判「落点最上层是哪个控件」，无障碍拿不到 z 序，暂未做。

## 7. 自动进房链路（选择直播间）的校验修复（2026-10-28）

### 现象

「选择直播间」后的自动进房日志：

```
00:01:09 W/进房导航: 点直播卡片后没有进房（第 1/3 张）
00:01:13 D/收藏房间: 窗口 com.ss.android.ugc.aweme 里没有「本场点赞」desc
00:01:17 W/进房导航: 进的是「null」不是「小好」，退出重找
00:01:22 ...×3 → 试了 3 张直播卡片都不是「小好」
```

当时 `mCurrentFocus=SearchResultActivity`（不在直播间），转储 317 节点 0 命中「本场点赞」。

### 根因（两个）

1. **点卡片失败后没有清理现场**：`waitForPage(LIVE_ROOM)` 失败直接 `return@repeat`
   进下一轮，可能停在半开预览上继续找卡片，越找越乱。
2. **进房校验依赖页面判定 + 短窗读昵称**：`waitForPage(LIVE_ROOM)` 在进房加载期
   可能误判通过，而主播昵称只给 2 次 × 1.5s——节点还没挂上就读完了，误判成「进错房间」。

### 修复

第④步改为**锚点轮询**，不再用页面判定做进房信号：

- 点卡片后每 800ms 读一次「本场点赞」锚点（`CurrentRoomAnchor.currentAnchorName`），
  总窗口 10s。**锚点出现 = 进房成功 + 拿到主播名**（该 desc 只存在于真正的直播间）。
- 锚点超时 → 如实记录当前页判定，`returnToSearchResult()` 清理现场（先确认是不是
  已经在结果页——「点了没反应」的常见态，避免多按返回退出搜索；不在则按返回最多 2 次）。
- 锚点昵称不匹配 → 按返回退出错房，`returnToSearchResult()` 回到结果页再试下一张。

### 纪律不变

锚点读不到时**绝不猜**：宁可报「试了 3 张卡片都不是」让用户手动进，也不乱进一个直播间
（付费礼物误触的最大来源就是乱进房）。

## 8. 自愈暂停 `PAUSED_WAIT`（2026-10-29，vc14 / 1.2.8 真机验证）

### 旧行为（错的）

「连续 4 轮读不到直播间评论」原本直接 `FlowAbortException` → `ERROR` 终态。
后果是**一次误判就把整场任务判死**：评论区滚动一卡、浮层盖住评论、抖音短暂掉帧，
用户回来看到的是「已结束」，得手动重开、重新进房、而且去重名单还在（等于白干）。

而抖音这类异常几乎都是**秒级可恢复**的，问题只在「有没有人去重试」。

### 三态分工

| 状态 | 谁进入 | 协程 | 前台服务 | 悬浮窗按钮 | 自动恢复 |
|---|---|---|---|---|---|
| `PAUSED` | 用户点「暂停」 | 挂起 | 保持 | 继续 / 结束 | **否**（等用户） |
| `PAUSED_WAIT` | 引擎检测到可恢复异常 | **挂起但不退出** | 保持 | 继续 / 结束 | **是**（探测成功即 resume） |
| `ERROR` | 不可恢复（浮层关不掉、被踢出登录、安全验证） | 结束 | 退出 | 重试 / 结束 | 否，需人点「重试」 |

`PAUSED_WAIT` 和手动暂停**共用同一个 `paused` 标志**——所以「继续」按钮不需要第二套逻辑：
用户随时点「继续」就等于接管，`RecoveryWait` 循环下一轮看到 `!isPaused()` 就退出并放行。

```kotlin
// TaskEngine.kt
fun pause()              = hold(EngineState.PAUSED,      "已暂停",   "任务暂停")
fun pauseForRecovery(r)  = hold(EngineState.PAUSED_WAIT, r,          "任务进入等待恢复：$r")
val isPausedNow get() = paused
```

`EngineState.isActive` 含 `PAUSED_WAIT` ⇒ 前台服务不会因「非 RUNNING」而退出，
悬浮窗也照常用 `isActive` 决定是否显示。三个渲染点（主界面状态条 / 胶囊 / 通知栏 / 面板）
统一加 `PAUSED_WAIT -> "等待恢复"`，面板状态点用**琥珀色**与手动暂停的灰区分。

### `RecoveryWait` 退避探测

```kotlin
suspend fun waitForComments(
    ctx: FlowContext, reason: String,
    probe: suspend () -> Int,     // 返回读到的评论行数，>0 视为已恢复
): Boolean
```

单轮动作顺序（**顺序不能换**）：

1. `stopped?` → 立即返回 false（用户按了「结束」，不要再多动一下界面）；
2. `guard()` → 风控检查优先级最高，命中就抛（异常即停，不重试）；
3. `!isPaused()` → 用户点了「继续」，视为接管，返回 true；
4. 抖音不在前台 → `relaunchDouyin()` 拉回（探测必须看得见评论）；
5. `liveGuard.recoverOverlay()` → 关掉挡评论的浮层（**只 `back()`**）；
6. `probe()` → 读到评论即 `resumeFromRecovery()` 返回 true；
7. 每 30 秒往面板上报一次「已等待 N 秒」，退避 `3s → 6s → 10s → 15s` 封顶。

不设总超时：**这是刻意的**。直播间的评论可能真的断流几分钟（主播休息、连麦静音），
判死没有意义，而「无限等 + 用户随时可接管」比「等 5 分钟就 ERROR」更符合现场。

探针用的是 `HashMap(seenRows)` **副本**——等待期间新进来的评论不能被记成「已见」，
否则恢复后第一轮会把新观众全跳过，白等一轮。

### 真机实测

```
面板（4/300，琥珀点）：● 等待恢复
                      连续 4 次读不到直播间评论，等待恢复（自动重试中）
                      [ 继续 ]  [ 结束 ]
        ↓ 15 秒内（评论重新出现，探测第一次就命中）
胶囊：● 运行中 5/300        ← 自动 resume，用户没碰手机
```

### 谁调用它

| 位置 | 触发条件 | 说明 |
|---|---|---|
| `FollowFromLiveFlow` | `emptyRounds >= MAX_DRY_ROUNDS`（原本抛异常） | 主战场：评论区读不到行 |
| `LiveInteractFlow` | `MAX_CONTENT_FAILS`（原本抛 `FlowAbortException`） | 发评论连续失败（多为键盘/发送键被挡） |
| `LiveGuard.ensureOnAirOrWait` | 维持直播间失败且最终判定 `UNKNOWN`（原本抛异常） | 见 §11：未识别的**全屏**浮层（如「人气开场」助力页） |
| `LiveGuard.recoverOverlay` 关不掉浮层 | **不**走 RecoveryWait | 直接 `ERROR`，给「重试」，避免无限按返回 |

## 9. 浮层恢复矩阵（配置化，`assets/douyin_locator.json` v11）

### 为什么不能只看页面判定

**观众列表是半屏浮层**：它盖住下半屏，但直播间的其余特征还在，页面判定依然是 `LIVE_ROOM`。
所以「判定不是直播间 ⇒ 一定有浮层」这种前置门禁是错的（第一版就栽在这，观众列表 14 秒没被关掉）。
现在改成**直接对整棵树做加权投票**，与页面判定解耦。

### 规则格式

```json
"overlays": {
  "GIFT_PANEL": {
    "label": "礼物面板",
    "threshold": 5,
    "features": [
      { "type": "text", "value": "赠送",     "weight": 3 },
      { "type": "text", "value": "双击赠送", "weight": 3 },
      { "type": "text", "value": "钻",       "weight": 2 },
      { "type": "desc", "value": "关闭",     "weight": 1 }
    ]
  }
}
```

`LocatorConfig.parseOverlays()` 会丢弃**阈值 > 特征总权重**的规则（配错了等于永不命中，
留着只会让人误以为在工作）。遍历时跳过 `_` 前缀键，避免一条注释把整段配置搞成 fallback。

### 已校准的五条（全部真机 dump 取证）

| key | 阈值 | 关键特征（权重） | 实测 |
|---|---|---|---|
| `GIFT_PANEL` | 5 | 赠送(3) 双击赠送(3) 钻(2) `desc==关闭`(1) | vc13：约 30 秒自动 `back()` 关掉，进度 2/220 → 5/220 |
| `VIEWER_LIST` | 3 | `desc==在线观众`(3) 玩家榜(2) 贡献榜(1) | vc14：**14 秒**内关掉，任务不中断（3/300 继续） |
| `PROFILE_CARD` | 2 | 资料卡(2) | 点错昵称会弹 |
| `LONG_PRESS_MENU` | 5 | 不感兴趣(3) 小窗播放(2) 投屏(2) 稍后再说(2) 转发到日常(2) | 长按评论会弹 |
| `COMMENT_KEYBOARD` | 2 | 发送(2) | 挡住底部工具栏 |

阈值卡在**「正常直播间拿不到，浮层必拿到」**之间。以 `GIFT_PANEL` 为例：正常直播间最多
从评论里偶然出现一个「钻」字拿 2 分，离 5 分很远；而礼物面板同时有「赠送」「双击赠送」「钻」，
稳定 ≥8 分。`VIEWER_LIST` 之所以只给 3 分阈值，是因为该面板第二次打开时**整块只剩一个节点**
`desc="在线观众"`（「玩家榜」消失），权重必须让单个特征就够过线。

### 安全性：只许 `back()`

`OverlayRule` 命中后**唯一动作是 `ctx.back()`**，绝不点浮层内的任何控件。
理由：浮层里全是「赠送 / 送出 / 立即充值」这类**会花钱**的按钮，误点等于直接造成经济损失。
关一次没关掉就 `delay(1s)` 再试，仍关不掉则返回 null 交回落点处置（`LiveGuard.ensureOnAir`
**不会连按返回**——连按会退出真实直播间）。

### 调用点

| 时机 | 目的 |
|---|---|
| `FollowFromLiveFlow` `emptyRounds == 1` | 刚读不到一行就先查浮层，礼物面板实测能省 20~30 秒空等 |
| 12 秒「定期体检」分支 | 先查浮层，再点「99+条新消息」刷评论 |
| `RecoveryWait` 每轮 | 关掉挡评论的浮层再探测 |
| `LiveGuard.ensureOnAir` 第③步 | 拉回抖音后清理现场 |

## 10. 终态不再挡参数区 + 通知栏文案（2026-10-29）

### 问题

1. 任务到终态时面板**自动展开**（纵向 405~1485），正好盖住主界面的参数区。
   用户想改参数得先点面板右上角 `⌃` 收起——而这时候任务已经结束了，展开的信息价值近乎为零。
2. 通知栏正文用 `progress.brief()`，标题已经有「抖关关 · 运行中」，正文又来一遍「运行中 · 」；
   且 `target` 在 `start()` 时被冻结进快照，用户中途改「设置关注」人数，通知栏仍是旧分母。

### 修法

**自动展开加前置条件**（`AppVisibility`：进程内 Activity 生命周期标志，比读节点树可靠——
终态常伴随无障碍掉线，读树会得到 null）：

```kotlin
// FloatWindowService.observe()
if (AppVisibility.isUiForeground) setExpanded(false) else setExpanded(true)
```

抖关关在前台 ⇒ 用户正看着自己的参数区，不展开；抖音在前台 ⇒ 展开给结论。
双保险：`MainActivity.onResume()` 里主动 `FloatWindowService.collapseIfExpanded()`，
覆盖「面板先展开、用户随后才切回来」的时序。

**分母实时**（`EngineProgress.withLiveTarget`）：

```kotlin
fun EngineProgress.withLiveTarget(liveTarget: Int) =
    if (target > 0) copy(target = liveTarget) else this
```

`target == 0` 表示流程声明「无总量目标」（如养号助手），此时不能被替换成设置值。
四处渲染点（主界面状态条 / 胶囊 / 面板 / 通知栏）全部改用当前设置值，参数改动即时生效。

**通知正文去掉状态**：`brief(includeState = false)`，标题已有状态。

### 真机实测

| 场景 | 结果 |
|---|---|
| 面板「设置关注」220 → 300 | 大号计数 `4/220 → 4/300`、按钮「设置 220 → 设置 300」即时刷新 |
| 通知栏 | `已关注 4/300`，与面板/胶囊/主界面四处一致 |
| `ERROR` 态点「重试」 | `1/220` → 重新运行，`EngineController.restartLast()` 用 `TaskEngine.lastFlow` 复跑 |

### 终态遮挡的实测（2026-10-29，vc14）

先在抖音界面点面板「结束」→ 终态「已停止」面板**照常展开**（此时抖音在前台，结论需要给人看）。
再把抖关关拉回前台：

```
mCurrentFocus = com.example.dgg/.ui.MainActivity
胶囊：● 已停止 15/300        ← 只剩一枚胶囊，不是 405~1359 的展开面板
参数区全部可见：目标关注数量 300 / 扫描间隔 10 秒 / 每日关注上限 200 / 延迟抖动 30
底部状态条：「任务已停止 · 已关注 15/300」   ← 结论在主界面本来就有
```

⚠️ **一个实测出来的事实**：任务运行中把抖关关拉到前台，`LiveGuard` 会在 **4 秒内**
把抖音拽回前台（它认为「抖音不在前台」）。所以「任务运行 + 用户在主界面改参数」这个组合
实际上**只存在于暂停态**；大多数情况下用户看到的是终态，走的正是 `onResume → collapseIfExpanded`。
`observe()` 里那个 `AppVisibility.isUiForeground` 判断是**兜底**（终态恰好在抖关关前台时到达），
两条路径最终效果相同，都已具备，主路径已真机取证。

## 11. 页面整块读不出来时不再终止（2026-10-29，vc22 / 1.3.4）

### 现场

2026-10-29 22:57 真机日志（vc18）：

```
22:57:01.568 已关注「* 白色小狗.」，进度 2/157
22:57:08.847 W/页面识别: 页面 UNKNOWN：最高分 0/6（最接近 HOME），证据：无
22:57:19.034 W/直播守卫: 页面读不出来（可能在转场/加载/抖音刚启动），等第 1/3 轮，不按返回
22:57:29.252            …第 2/3
22:57:39.476            …第 3/3
22:57:49.680 W/直播守卫: 已不在直播间（当前判定 UNKNOWN），脚本不会盲目找房间，交由调用方中止
22:57:49.684 E/任务引擎: 任务异常终止 … 当前页面判定 UNKNOWN（0/6）
```

屏幕当时被抖音「**人气开场**」助力页（`助力 | 冲榜` 页签、`送鲜花 10 钻` / `送跑车 1200 钻`）
整屏占满。**用户什么都没做，进度却断了**，还得重新进直播间从头开始。

### 为什么没走「识别浮层 → 按返回」这条路

`overlays` 里已有的 `GIFT_PANEL` 要 5 分（赠送 3 + 双击赠送 3 + 钻 2 + 关闭 1），
而这页最多只能靠「钻」拿到 2 分，认不出。

**而且这个页面不能只凭「人气开场」去认**：直播间右上角常年挂着一颗
`人气开场 / 2人助力` 徽标（真机截图可证）。把它写成单特征，正常直播间就会被判成浮层，
`back()` 下去**直接退出房间**——比原来的中止更糟。要给这页写规则必须走多特征组合
（助力日历 / 累计助力值 / 挑战成功 / 加热完成），而这几条文案目前只有截图 OCR，
没有节点树取证，**未经校准的规则一律不写**。

### 改法：把「读不出来」和「离开了直播间」分开处置

`ensureOnAir` 失败时的落点决定语义，两者不能一视同仁：

| 最终判定 | 含义 | 处置 |
|---|---|---|
| `UNKNOWN` | 大概率叠了一个没见过的**全屏**浮层，或卡在转场 | **等**（自愈暂停 + 持续探测） |
| `HOME` / `FEED` / `SEARCH_RESULT` | 用户自己切走了，脚本不该抢界面 | 返回 false，交调用方中止 |

新增 `LiveGuard.ensureOnAirOrWait()`：先走原 `ensureOnAir`，失败后再判一次页码——
是 `UNKNOWN` 就进 `RecoveryWait.waitForPage()`（暂停 + 3s→6s→10s→15s 退避探测），
探测条件 = 页面回到 `LIVE_ROOM`。M2 与 M3 都改成调它。

`RecoveryWait` 同时抽出了通用核心 `waitFor()`，`waitForComments`（探评论行数）
与 `waitForPage`（探页面）共用同一套循环：风控优先、用户「继续」接管、
每 30 秒上报、等待期间只调 `recoverOverlay`（识别到浮层才按返回，绝不猜位置）。

### 取证入口：把「没见过的浮层」变成日志

认不出就意味着补不了规则，所以等待期间**第一次**探测失败时会 dump 一次屏幕文案：

```
W/自愈等待: 仍读不出来，屏上文案（补 overlays 规则用）：
  text=[1 钻、赠送、万圣兔兔、299 钻、鲜花、10 钻、人气票…]
  desc=[人气票 1 钻 双击赠送、关闭…]
```

`text` 与 `desc` **分开列**：抖音的按钮语义一半挂 text（「赠送」），一半挂 desc
（「人气票 1 钻 双击赠送」）。只抓 text 会逼着补规则的人去猜 desc。

### 真机验证（vc21 测试包，把 `GIFT_PANEL` 阈值临时设成 99 让它认不出）

测试方法值得复用：**要复现「UNKNOWN + 认不出的浮层」，不需要等抖音改版**——
把某条规则的阈值调到超过满分，`parseOverlays` 就会丢弃它（日志会明确写
`阈值 99 超过满分 9，永远无法命中，已跳过`），那个浮层立刻变成「未收录」。

```

23:34:41 I/任务引擎: 任务进入等待恢复：页面读不出来（可能有未识别的浮层盖住直播间…）
23:34:41 W/自愈等待: 仍读不出来，屏上文案（补 overlays 规则用）：text=[1 钻、赠送…] desc=[…]
23:36:03 I/自愈等待: 已恢复读取（共等待 81s），自动恢复任务     ← 手动按一次返回
```

**回归**（vc22 正式配置）：运行中手动点开礼物面板 → 20 秒内被 `GIFT_PANEL` 规则
自动 `back()` 关掉，进度 `1/300 → 4/300`，全程 `运行中`，没有走暂停。

### 仍未做

等哪天真机再撞上，照着日志里的 `text/desc` 补一条多特征规则即可，不必改代码。
