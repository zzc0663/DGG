# 运行期容错与悬浮面板

> 2026-10-27 真机实现并验证（OPPO PLB110 / Android 17 / 抖音 40.8.0）
> 对应需求：「按停止不退回应用，展开界面」「人为切换直播间要继续跑」「退出抖音要自恢复拉回」
> 「关注完追到最新再关注」

---

## 1. 悬浮窗：胶囊 ⇄ 展开面板

### 为什么改

旧版悬浮窗只有一条胶囊 + 一个「停止」键。点「停止」的后果是：

1. `ControlService.stop()` → 引擎停 → 前台服务 `shutdown()` 里顺手 `stopService(FloatWindowService)`
   → **悬浮窗当场消失**；
2. 用户既看不到「为什么停了」（风控？异常？到目标了？），观感上也像是被踢回了应用。

### 现在的结构

```
收起态：[●] 运行中 3/180 [⌄]          ← 点 ⌄ 展开
展开态：┌────────────────────┐
        │ ● 运行中          [⌃] │
        │ 3/180                 │   ← 大红字，一眼看清进度
        │ 已关注                 │
        │ 挑中「xxx」            │   ← message，含"为什么停"
        │ [ 暂停 ]  [ 结束 ]     │
        │ ─────────────────     │
        │ 今日累计 25      重置  │
        │ [   关闭悬浮窗   ]     │
        └────────────────────┘
```

| 按钮 | 行为 |
|---|---|
| 暂停 / 继续 | `TaskEngine.pause()` / `resume()`。暂停期间不产生任何界面动作，只保留风控检查 |
| 结束 | **只调 `TaskEngine.stop()`**：不撤悬浮窗、不启动任何 Activity，抖音保持在前台 |
| 关闭悬浮窗 | 唯一会撤掉悬浮窗的操作 |
| 重置 | 清「今日累计」，**不动已关注名单**（名单是去重用的，清了会重复关注同一批人） |

终态（已停止 / 风控停机 / 异常停止）时：面板**自动展开**显示结论，按钮从「结束」变成「关闭」，
悬浮窗**不会自己消失**——必须用户点关闭。

### 唯一的例外

从抖关关界面点停止（`EngineController.stop(this, ...)`）会顺手撤掉悬浮窗：此时它的终态面板
是重复信息，还挡着用户自己的界面。悬浮窗上点「结束」不走这条路径。

### 实测

```
22:39:45 I/悬浮窗: 悬浮窗「结束」被点击（当前 运行中）
22:39:45 I/悬浮窗: 任务已到终态（已停止），面板保留待用户关闭
22:39:45 I/任务结束：悬浮窗结束
22:39:45 I/前台服务: 前台服务已退出：任务进入终态：已停止（悬浮窗保留终态面板）

mCurrentFocus = com.ss.android.ugc.aweme/.live.LivePlayActivity   ← 仍是抖音，没退回应用
```

## 2. 人为切换直播间 → 继续执行

### 旧行为（错的）

`ensureLiveRoom` 连续 2 次判非直播间就按一次返回。用户手动滑到下一个直播间时，
转场动画期间页面判定是 UNKNOWN（命不中直播间特征），于是：

```
用户切到新直播间 → 判定 UNKNOWN → 按返回 → 退出新直播间 → 回到直播频道页 → 空转到中止
```

### 现在（`engine/flow/LiveGuard.kt`）

| 判定 | 处置 |
|---|---|
| `LIVE_ROOM` | 继续，不管主播换没换人（用户切到哪个房间就跟哪个） |
| `UNKNOWN` | **不按返回**，最多等 3 轮 × 10 秒。覆盖转场、加载、抖音冷启动 |
| `USER_PROFILE`（资料卡浮层） | 按一次返回关掉，再判 |
| 直播频道预览页 | 点「点击进入直播间」自己进房 |
| `HOME`（且是我们刚拉回来的） | 点顶部「直播」页签 → 再点进房 |
| 其它已识别页面 | 中止并说明。**不猜房间**——拿不到「该进哪一个」，乱点可能进到付费直播 |

关键点：**页面读不出来时绝不按返回**。UNKNOWN 可能是转场、加载、收键盘，
按下去退的是真实页面；只有「明确识别出是浮层」才允许按返回。

## 3. 退出抖音 → 自动拉回

`LiveGuard.relaunchDouyin()`：`DouyinLauncher.launch()` 最多 3 次，每次等 8 秒回到前台。

能成功的前提是**有悬浮窗权限**：Android 10+ 限制后台启动 Activity，但持有
`SYSTEM_ALERT_WINDOW` 的应用不受该限制。本应用本来就要求悬浮窗权限，所以这条路可用。

实测（按 HOME 键）：

```
22:38:55 W/直播守卫: 抖音已不在前台（用户切走了，或被系统回收）
22:38:55 W/直播守卫: 自动拉回抖音（第 1/3 次）
22:38:56 I/直播守卫: 抖音已回到前台            ← 0.4 秒
22:39:11 I/直播间关注: 已关注「* 尤尤-」，进度 2/175   ← 继续跑
```

拉回后如果抖音落在**直播频道预览页**（退出期间被系统回收后重启时常见），
会点「点击进入直播间」自动进房：

```
22:38:18 W/直播守卫: 停在直播频道预览页，点「点击进入直播间」自动进房
22:38:19 I/页面识别: 页面 → LIVE_ROOM（8/5）
22:38:19 I/直播守卫: 已自动进入直播间，继续执行
```

## 4. 一个顺带修掉的启动 Bug

`EngineController.start()` 原来无条件 `DouyinLauncher.launch()`。如果抖音**已经在前台**
（用户停在自己选好的直播间里），这个 launch 会让抖音重走启动流程 → splash → 首页/预览页，
用户精心选好的直播间当场没了，脚本随后只能报「不在直播间」。

现在先取当前前台包名，是抖音就不 launch：

```kotlin
val front = ActiveWindow.root(DggAccessibilityService.current)?.packageName?.toString()
if (front == DouyinLauncher.PACKAGE) {
    LogStore.i(TAG, "抖音已在前台，不再重复拉起（重复拉起会打断当前直播间）")
}
```

## 5. 追最新：从「整屏随机」到「加权最新」

### 不滑动的理由（四组真机实验，详见 `M2-直播间评论关注.md` §12.2）

| 操作 | 结果 |
|---|---|
| 评论区内 550px 上滑 | 切到下一个直播间 |
| 评论区内 120px 上滑 | 不切房间，但评论行 y 完全不变（列表不可滚） |
| 评论区内 120px 下滑 | 同上，没有出现更早的评论 |

所以「下滑到最新」在抖音直播里做不到（滑大了换房间、滑小了没反应）。
等价实现是**等列表自己滚到最新**，并只在最新那几个人里挑。

### 本轮新增

1. **加权随机**：最新一行的权重 3、第二 2、第三 1。
   三选一等概率会有 2/3 概率挑到不是最新的那个（观感就是"又在挑老观众"），
   而永远挑最底那一行又是明显的机器特征。权重随机两头都照顾。
2. **「人都处理过」不再当成故障**：
   - 屏幕上**读得到评论行**但行里的人都在本轮已处理名单里 → 最多少等 12 轮（约 1 分钟），
     日志写「这一屏 N 人都已处理过，等新评论进来」；
   - 屏幕上**一行评论都读不到** → 4 轮就中止（定位失效或被浮层盖住，等下去没意义）。
   旧实现混用同一个上限 4 轮，冷清房间会被误判成「脚本自己停了」。
3. **过滤未成型的行**：评论插入时有高度展开动画，实测读到过 **6px 高**的行
   （`行=[36,2164][780,2170]`），点上去落在空白，白等 6 秒超时。现在低于 20px 直接跳过。

## 6. 已知限制

- **UNKNOWN 与「真不在直播间」无法完全区分**。极端情况下（抖音卡在启动画面）会等满
  30 秒才报错，而不是立刻停。这是刻意选的：宁可慢，也不要误退用户的直播间。
- **预览页进的是第一个直播间**，不保证是原来那个。用户自己切了直播间时同样如此。
- 悬浮窗终态面板**不会自动消失**，会一直等到用户点「关闭悬浮窗」。这是「不退回应用」的
  代价；胶囊态很小，展开态由用户主动点开。
- **浮层识别靠文案**：页面判定掉成 UNKNOWN 时，用「赠送 / 资料卡 / 发送」三个精确文案判断
  「是不是有浮层盖住了直播间」。抖音改版换了按钮文案就会失效——失效的表现是「等 30 秒后
  中止」，不会误点，属于可接受的降级。
- 点评论行仍有概率点到礼物飘屏（打开礼物面板）。现在靠上面的浮层识别按一次返回即可恢复，
  实测每次约多花 5 秒。根治要判「落点最上层是哪个控件」，无障碍拿不到 z 序，暂未做。
