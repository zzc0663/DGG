## 一、先看事实

### 1.1 三个开关早就存在，但零消费方

`Settings.kt` 里这三个字段连注释都写好了：

```kotlin
val idleLive: Boolean = false,
val applyMic: Boolean = false,
val continueAfterMic: Boolean = false,
```

注释原文：「以下三个开关**尚未接入任何流程**（引擎里零引用，界面上已置灰并标「暂未生效」）」。

布局里对应 `sw_idle_live` / `sw_apply_mic` / `sw_continue_after_mic`，统一的
`android:enabled="false"` + `android:alpha="0.5"` + 副标题「暂未生效」。
`MainActivity.bindLive` 里刻意没绑监听，理由也写在注释里：「绑了反而是『能改设置但没人消费』的假象」。

**所以本轮不是"新增功能"，是"给已有壳子填内核"。** 好处：存储层零迁移、界面零新增控件（只多一行）。

### 1.2 但存在一个重复开关（必须先解决）

| 开关 id | 字段 | 位置 | 现状 |
|---|---|---|---|
| `sw_mic_request` | `micRequest` | **直播互动卡**内 | ✅ 已接线，M3 消费（只点一次申请、不认弹窗） |
| `sw_apply_mic` | `applyMic` | **定时休息卡**末尾 | ❌ 置灰，无消费方 |

同一个语义两个开关两个字段，用户看到会直接困惑。本轮必须合并成一个。

**合并方案（零迁移风险）**：
- 保留 `micRequest` 作为唯一字段；
- `SettingsStore.readFromSp()` 读成 `sp.getBoolean(KEY_MIC_REQUEST) || sp.getBoolean(KEY_APPLY_MIC)`；
- `writeAll()` 两个 key **同写**。

这样：老用户开过任一开关都不丢；万一回滚到 vc60 也读得到。

### 1.3 M3 的发送逻辑是 `private`，M2 用不了

`LiveInteractFlow.sendComment()` / `awaitSubmitted()` / `buildComment()` / 去重窗口全是 private，
而 M2 要发的评论和 M3 是**同一件事**：同一套 viewId 快路径、同一套三判据校验、同一套话术库。

**不抽取的结果**：M2 里再抄一份 → 抖音改版后两份都要改，且必然改漏一份。

### 1.4 连麦的定位配置几乎是空的

现在只有 `live_mic_button = descContains("连线")`，且 M3 只点不认。要做"申请→确认→上麦→下麦"
四态，需要四个新定位项，**全部得真机取证**：

| 需要的配置项 | 用途 | 现状 |
|---|---|---|
| `live_mic_button` | 打开连麦入口 | 有（`descContains 连线`），未验证当前版本 |
| `mic_apply_confirm` | 点「申请连线 / 确认申请」弹窗 | ❌ 无 |
| `mic_on_seat` | 判「已经上麦」 | ❌ 无 |
| `mic_hang_up` | 下麦按钮 | ❌ 无 |
| `mic_waiting` | 判「已申请、等主播接受」 | ❌ 无 |

### 1.5 真机取证受限（实测确认）

本轮尝试 dump 当前直播间：`uiautomator dump` 连续 7 次失败（`could not get idle state`），
关闭动画/暂停播放均无效。截图只拿到 481×1057 缩略图，能看底栏有「输入框 / 表情 / 礼物 / 发送」，
**看不到独立的连线入口**（该入口通常在「更多」面板里，或主播未开放连麦时压根不存在）。

⇒ 连麦四态特征必须**在实施时第一件事做取证**，取不到就按 §5.3 降级，**不许猜**。

## 二、设计决策（本轮已确认）

| 项 | 决策 | 说明 |
|---|---|---|
| 休息时发评论 | **开关控制自动发** | 不做悬浮窗按钮。休息开始后发，受统一安全阀约束 |
| 空闲互动的「空闲」 | **等新评论的空窗期** | 即 `awaitFreshScan` 里没候选、原地等待的那些轮次 |
| 自动连麦边界 | **自动点确认 + 到点自己下麦** | 上麦停留 60±20 秒随机，然后主动下麦并恢复原任务 |

## 三、架构：先抽出 `CommentSender`

**这是阶段 A 的第一步，也是唯一一次真正的重构。**

新建 `engine/LiveCommentSender.kt`（不做成对象，做成有状态类，因为要持有去重窗口）：

```
class LiveCommentSender(config: LocatorConfig) {
    fun send(ctx: FlowContext, text: String): Boolean        // 原 sendComment
    fun buildDraft(ctx, settings): Draft?                    // 原 buildComment
    fun remainingToday(dailyLimit: Int): Int                 // InteractStore 代理
    val recentBodies: List<String>                           // 自己最近发的正文（给 M2 过滤用）
    fun markSent(text: String)                               // 记入窗口 + InteractStore.bumpToday
}
```

搬迁清单（**逐字搬，先不改行为**）：

| 从 `LiveInteractFlow` | 到 `LiveCommentSender` |
|---|---|
| `sendComment()` | `send()` |
| `awaitSubmitted()` | 私有 `awaitSubmitted()` |
| `buildComment()` / `copyLatestComment()` / `isSystemish()` / `pickPreset()` | 同名 |
| `rememberSent()` + `recent` 窗口 | `markSent()` + `recentBodies` |
| `LiveTargets` | `CommentTargets`（名字改掉，避免与 M2 的 `LiveTargets` 撞名） |
| `SYSTEM_HINTS` / `SPAM_HINTS` / 发送相关常量 | 同文件 |

`LiveInteractFlow` 改成持有一个 `LiveCommentSender`，主循环调用不变 —— 行为等价，
可以用 vc60 的实跑日志逐项对照（目标 1 条 → 1/1、正文不重复、viewId 命中）。

**去重窗口要跨流程共享**：M2 休息时发的评论，M3 再跑时不能撞车。所以 sender 做成
`TaskEngine` 作用域内的单例（随 `EngineController` 生命周期），而不是每次 `run()` 新建。

### A2 开关接线 + 去重（UI 与存储）

1. `content_auto_follow.xml`
   - `sw_idle_live` / `sw_apply_mic` / `sw_continue_after_mic`：删 `android:enabled="false"`、

   - 新增一行「休息时发评论」+ `sw_rest_interact`，紧跟「空闲时直播互动」之下。
2. `MainActivity.bindLive`：把四个开关绑上 `store.edit`，并在启动确认文案里带出来。
3. `Settings`：新增 `restInteract: Boolean = true`（默认开，因为休息期间是纯浪费）；
   `SettingsStore` 补 `KEY_REST_INTERACT = "rest_interact"` 读写。
4. `SettingsStore`：`micRequest` 双 key 读取（见 §1.2），`applyMic` 字段保留但标注「仅作旧 key 兜底」。

**高度账**：删 1 行（重复连麦）+ 加 1 行（休息发评论）= **净 0**。
1.3 倍字号下页面高度不变，`tv_start_live` 底边仍在 1798 < FAB 顶边 1936。

### A3 空闲时直播互动（`idleLive`）

**插入点**：`FollowFromLiveFlow.awaitFreshScan()` 的等待循环内，`scanOnce()` 返回空候选之后。

```
while (true) {
    val scan = scanOnce(...)
    if (scan.candidates.isNotEmpty()) return Scan(...)      // 有活干，正常返回
    ...
    // 新增：空窗期顺手互动
    if (idleInteract.shouldFireNow(now)) {                   // 开关 + 节流 + 额度 三重判定
        idleInteract.fire(ctx)                               // 发一条，失败只记日志不中止
        continue                                             // 重扫，别用发评论前的旧 scan
    }
}
```

`IdleInteractor`（新，`engine/flow/`）负责三重判定：

| 闸门 | 规则 | 理由 |
|---|---|---|
| 开关 | `settings.idleLive` | 用户可关 |
| 节流 | 距上次 ≥ **60 秒**（常量，不给 UI） | 等新评论循环 2~5 秒一轮，不节流会疯狂发 |
| 额度 | `InteractStore.remainingToday(commentDailyLimit) > 0` | 与 M3 共用同一本账 |

**发完必须做的收尾**（缺一不可）：
1. `guard(force = true)` —— 「评论过快」toast 只闪一次；
2. `Actions.back()` 收起键盘/面板 —— 不收起会把评论列表压到看不见，后续 `scanOnce` 读到 0 行，
   进而触发「浮层盖住」误判（`awaitFreshScan` 里有这条分支）；
3. `delay(KEYBOARD_SETTLE_MS ≈ 800ms)` 再继续 —— 键盘收起动画期间读树会读到半截。

### A4 休息时发评论（`restInteract`，新增）

**插入点**：`FollowFromLiveFlow` 主循环里 `ctx.settle(settings.restSeconds * 1_000L)` 那一行
（当前是"关注满 N 个后定时休息"）。

**规则**：
- `settings.restInteract && settings.restSeconds >= 15` 才发（休息太短不值当，弹键盘本身要 2~3 秒）；
- **每次休息最多 1 条**（休息是"降风险"，不能变成"换个姿势继续刷"）；
- 先发评论、再睡剩余时间：`发完 → settle(restSeconds - 已用时间)`，
  这样休息总时长不被拉长；
- 发完同样走 A3 的三步收尾。

### A5 自动连麦（`micRequest`，四态状态机）

**位置**：M2 主循环进入后、开始扫评论之前，**整轮只尝试一次**（`micTried` 标记，与 M3 同语义）。

```
M2 启动 → 〔applyMic 开〕→ 找连麦入口 → 点开 → 点「申请连线」→ 点确认
        → 等主播接受（最长 120 秒）→ 上麦 → 停留 60±20 秒 → 点「下麦」
        → 等回到直播间 → 〔continueAfterMic 开〕→ 恢复关注循环
                                    └─ 关 → 流程正常结束（"连麦完成"）
```

**四态判定**（全部走 `findAny` 候选链，viewId 优先 + 文案兜底，认不出就停在该态）：
| 态 | 判据 | 超时处置 |
|---|---|---|
| 未申请 | 屏上有 `live_mic_button` | 找不到 ⇒ **跳过连麦**并日志说明「本直播间可能未开放连麦」 |
| 已点击、待确认 | 出现 `mic_apply_confirm` | 3 秒内没出现 ⇒ 认为无需确认，进入「等待接受」 |
| 等待主播 | 出现 `mic_waiting`（或仍无上麦特征） | **120 秒**没上麦 ⇒ 放弃本轮，日志记「主播未接受」，不重试 |
| 已上麦 | 出现 `mic_on_seat` / `mic_hang_up` | 上麦后停留 60±20 秒；认不出下麦按钮 ⇒ 只等不点 |

**硬约束（降封号项）**：
- 每轮**只申请一次**，失败不重试（反复申请是最扎眼的行为）；
- 认不出「已成为主播连麦对象」就**绝不去点任何形似「下麦」的东西**（可能是别的东西）；
- 上麦期间**完全不点关注按钮**（界面上没有关注入口，点了会落到画面上弹资料卡）。

### A6 下麦后继续干活（`continueAfterMic`）

下麦动作完成后：

1. `LiveGuard.ensureOnAirOrWait(ctx, allowAutoNavigate = false)` 等回到直播间（下麦时界面会有一跳）；
2. `warmUpCommentList(ctx)` 重新预热评论容器（上麦期间节点缓存全过期）；
3. `delay(MIC_COOLDOWN_MS ≈ 5s)` 让麦位动画走完；
4. 回到主循环继续关注。

`continueAfterMic = false` 时：**不中止流程**，只是跳过连麦（等价于本轮不申请），
避免「开了一半的设置把任务搞停」这种反直觉行为。*（如果你要的是"下麦后直接结束任务"，这里改一行即可。）*

### A7 悬浮窗与日志

- 状态条文案：「申请连麦中」「等主播接受（剩余 xx 秒）」「已上麦 · 停留 xx 秒」「已下麦，继续关注」；
- 日志全部带耗时与命中的定位项（`viewId` 还是文案兜底）；
- 空闲/休息发的评论，日志前缀区分：`[空闲互动]` / `[休息互动]`，方便与服务端日志对账。

## 五、连麦状态识别：最大不确定项

### 5.1 首要任务是真机取证

实施第一步就要把下面这张表填满，**填不满就不写代码**：

| 要取的证据 | 方法 |
|---|---|
| 底栏是否有连线入口（或藏在「更多」里） | 截图 + 点开「更多」面板逐个 dump |
| 「申请连线」按钮的文案/描述/viewId | dump 后 grep `连线|连麦|申请|上麦` |
| 确认弹窗的按钮文案 | 点申请后立刻 dump |
| 上麦后的界面特征（麦位/D BG 文案） | 只能真上麦一次（需要用户配合或主播接受） |
| 下麦按钮文案 | 同上 |

### 5.2 取证失败时的兜底

直播间 dump 大概率持续失败（本轮 7 次全废）。备用路径：
1. 让 App 自己 dump —— 在 `DebugChannel` 加一个「把当前树写到 Downloads」的口令（debuggable 包可用）；
2. 或复用 `LiveInteractFlow` 首次失败时已有的「dump 屏上 text/desc（≤12 字）」日志，
   让它在上麦/下麦前后各打一次，用服务端日志上报取回。

### 5.3 取不到就降级（不许猜）

如果拿不到「已上麦/下麦」的可靠特征：

> **只做"点申请 + 点确认"，不做"到点下麦"**。开关文案改为「自动申请连麦（不含自动下麦）」，
> 并在界面说明「上麦后请自行下麦」。此时 `continueAfterMic` 不生效并标注。

宁可少一个功能，也不能在不知道自己是否在麦上的情况下乱点。

## 六、风险清单

| # | 风险 | 后果 | 对策 |
|---|---|---|---|
| 1 | 发评论弹键盘遮住评论区 | `scanOnce` 读到 0 行 ⇒ 误判浮层 ⇒ 空转/暂停 | 发完 `back()` + 800ms settle（A3 步骤 2/3） |
| 2 | **自己的评论行被当成新用户去关注** | 尝试关注自己 ⇒ 失败累计 ⇒ 触发中止 | `CommentSender.recentBodies` 与扫描结果比对，正文命中则跳过该行 |
| 3 | 空闲互动打断「新评论锚点」 | 自己评论插入列表 ⇒ `seenRows` 记到自己的行 | 同上；且发完 `continue` 而不是复用旧 scan |
| 4 | 每日上限两本账 | 关注额度与评论额度互相影响 | 已分账（`FollowedStore` / `InteractStore`），本轮不动 |
| 5 | 上麦期间界面全变 | 关注按钮定位失败 ⇒ 连续失败中止 | 上麦期间**不进关注循环**（A5 状态机独占） |
| 6 | 连麦入口找不到 | 用户以为开关坏了 | 日志 + 状态条明示「本直播间未开放连麦」，开关保持开 |
| 7 | 定时休息被塞进评论后变长 | 休息失效 | 发评论的时间从休息时长里扣（A4 规则） |
| 8 | 1.3 倍字号布局 | 新增行挤压或遮挡 FAB | 净增 0 行；仍按老规矩切 1.3 倍滚到底复测 |

## 七、验证清单（真机）

按顺序做，前一项不过不往下：

1. **A1 回归**：M3 目标 1 条 → `1/1`、正文不重复、日志出现 viewId 命中（与 vc60 一致）。
2. **开关落库**：四个开关逐个切 → 杀进程重开 → 状态保持；`apply_mic` 与 `mic_request` 同值。
3. **空闲互动**：关注目标设 3、房间冷清（或故意不让它扫到人）→ 观察到 60 秒间隔发 1 条，
   日志有 `[空闲互动]`，且发完评论区恢复扫描（不卡死、不误判浮层）。
4. **休息互动**：关注 1 个 + 休息 30 秒 → 休息期间发 1 条，总休息时长仍是 30 秒。
5. **自己的评论不误关注**：上一步后接着观察是否有「尝试关注自己的昵称」日志（应无）。
6. **连麦（需主播配合）**：开关开 → 点申请 → 确认 → 上麦 → 60±20 秒 → 自己下麦 →
   日志出现「已下麦」，随后关注循环继续。
7. **下麦后继续关**：`continueAfterMic` 关 → 连麦流程仍走完，但下麦后不恢复关注（按 §A6 语义）。
8. **每日上限**：把 `commentDailyLimit` 临时设成「今日已发数」→ 空闲/休息都不再发，关注继续。
9. **1.3 倍字号**：滚动到底，`tv_start_live` 不被 FAB 遮挡，四行开关文字不折行。
10. **断电式停止**：跑在连麦等待中按「结束」→ 无残留手势、悬浮窗正常收起。

## 八、待定事项

   要可配的话得单独占一行输入框，1.3 倍字号下需重新算宽。
